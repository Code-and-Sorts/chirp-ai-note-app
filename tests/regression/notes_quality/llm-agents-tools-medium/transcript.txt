AI systems call this by different names, but most have this basic idea. Training a large language model is not a simple task. It requires a large amount of data and a knowledge of computational statistics, which most people are not exposed to until upper division at a university. However, once you have a trained model in hand, there are two simple concepts to remember. First, there is the predictive side of AI. This is the model itself. Given an input, it predicts what is likely to come next. That ability comes from relationships discovered in data it was trained on. And that data can be almost anything digital. Text, images, audio, video, sensor signals, and so on. Second, there is the deterministic side. This is traditional computer programming. Same input, same operation, same result. No guessing involved. The trained model is not magic by itself. It is a large structure of numbers that ordinary software has to load, run, and interpret. That software runs the model, interprets the output, and decides what happens next. While the two ideas are simple, real systems get complicated quickly. Part of the confusion comes from different names for similar pieces. But the larger issue is that the whole stack is evolving so fast that it can be hard to say, start here. New model releases show up constantly. Inference servers, the software that actually loads and runs those models, change to make the models faster, more efficient, and easier to serve. Over time, they also absorb features that proved useful in clients, scripts, and agent frameworks. The client side changes too. Chat interfaces, coding assistants, and agents adapt to what the inference server can do. But they also push the system forward by discovering new ways to get useful work done. We usually think of the flow this way. A user makes a request to an agent or client. That might be a chat interface, a coding assistant, or a more generic program. And the user does not have to be a human. It could be another program, another service, or even another agent. The agent then shapes the request into the form the inference server expects and sends it along. The inference server prepares a request for the model, runs the model, and returns the result to the agent. The agent then decides what to show the user, what to keep as context, and what to do next. At least that's what it was if you live in the past. Say around 2024. In many earlier tool using systems, most of the tool logic lived in the agent. The agent decided when a tool might help, called the tool, collected the result, and sent that result back to the model as more context. As tool use became common, model creators started training models to understand tool calling more directly. Instead of only producing ordinary text, the model could produce a structured request. Call this tool with these arguments. That changed the job of the inference server and the agent. The inference server could expose tool calling support in a standard format, while the agent still handled the outside work, executing the tool, collecting the result, and deciding what happens next. In the simplest version, the agent has a specific tool built into it. If it needs search, the search tool is part of the agent. That works, but it does not scale very well. Every new tool becomes another custom integration. MCP, the model context protocol, moves this toward a toolbox model. An MCP server is a program that exposes tools in a standard way. The agent can connect to that server, ask what tools are available, and get back the descriptions and input schema it needs to use them. But even with a full toolbox, the agent still decides which particular tools to use for a given request. Now we get to the model-facing part of tool calling. The agent does not just send the user's question by itself. It makes a tool-aware request. Along with the user message, it includes the tools that the model is allowed to use for this turn. The inference server takes that request and applies the model's chat template. template. That template formats the conversation, the instructions, and the tool descriptions into the structure the model was trained to understand. From the model's point of view, the tools are descriptions in text. It sees something like, here is a tool named Web Search, here is what it does, and here are the arguments it accepts. It is important to know that the model does not call the tool. It predicts a request to call the tool. Sometimes the model predicts an ordinary answer, but if the tool looks useful, it predicts text in the shape of a tool call. Call this tool with these arguments. The inference server recognizes that shape and returns it to the agent as a structured tool call, usually as JSON. The agent then does the outside work. It executes the tool, collects the result, and sends that result back to the inference server as more context. Then the model can continue from there, now with the tool result included in the conversation. Once the agent has a toolbox, the next question is how to use those tools well. That is where the skill layer comes in. In this context, a skill provides text instructions for tool use. It tells the model when a tool is useful, what inputs to provide, and how to interpret the result. It can also give the agent the access information needed to reach the tool. Skills can cover many kinds of tasks, but for this video we are focused on tools. The tool is the capability. MCP is the connection. The skill is the operating guide plus the access card. So far, the examples have mostly been single pass agent calls. One bounded request, one tool decision, one response. The same ideas apply when the system has a run loop. In that case, an agent harness keeps the process moving. It sends requests to the model, handles tool calls, adds results back into context, and repeats the cycle until the task is done. This pattern now shows up across frontier model providers, coding assistants, and open agent projects. The implementations differ, but the basic loop is the same.
