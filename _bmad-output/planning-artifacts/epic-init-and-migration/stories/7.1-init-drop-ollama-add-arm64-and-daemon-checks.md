## User story

As a fresh-install Chirp user on an Apple Silicon Mac, I want `chirp init` to verify the machine architecture, confirm the bundled daemon can come up, and tell me exactly which `chirp models add` command to run if I don't have a chat model yet — without ever mentioning Ollama, asking me to pick from an Ollama tag list, or trying to start an `ollama serve` I don't have running.

As a contributor running `chirp init` on an Intel Mac by mistake, I want it to fail at the very first phase with a clear "Apple Silicon required" message and a distinct exit code, instead of wasting time on dependency checks that won't matter.

## Context

`chirp/init_flow.py` is currently structured around Ollama as the model runtime: Phase 1 probes `localhost:11434`, Phase 2 brews+starts the Ollama service, Phase 3 picks a chat + embed model from a hard-coded list of Ollama tags, Phase 4 `ollama pull`s them. The `verify()` function appends an Ollama row plus per-model rows; the `install_missing()` function brew-installs Ollama; `pick_models` / `keep_or_pick` / `pull_and_finalize` orchestrate the pull. None of this survives the migration.

This story does the equivalent of what story 2.3 did for BlackHole: strip the Ollama-shaped verify/install/pick/pull plumbing and replace it with the chirpd-shaped flow.

**The Apple-Silicon check runs first** — before brew/ffmpeg, before the screen-recording probe, before any daemon work. Two reasons: (a) if the machine isn't arm64, every other check is moot; (b) the architecture failure mode is the clearest single-message diagnostic we can give, and burying it under a six-row table would be unfriendly.

**The daemon-readiness check** is a single call: `llm.client.health()`. The client lazy-spawns the daemon if it isn't running, performs the version handshake, and returns OK or raises a typed `LLMTransportError` / `LLMDaemonSpawnFailed`. No init-side logic exists for "is the daemon process running" — that's encapsulated in the client per architecture §Decision: Daemon entrypoint and §Cross-Component Dependencies.

**The registry-empty prompt** uses `llm.registry.read_registry()` to detect whether `default_chat` is set and resolves to a registered alias. If not, the verify table reports `default chat model: not configured` (non-blocking — `installed=False, required=False` semantics) and the post-verify summary offers two options (per OQ1 resolution in epic decision 11):

- **Primary:** `chirp models add mlx-community/gemma-4-4b-it-4bit` (~2 GB, balanced quality and speed)
- **Smaller:** `chirp models add mlx-community/gemma-4-e2b-it-8bit` (Gemma effective-2B at 8-bit; lower resident and activation memory)

The constants `RECOMMENDED_CHAT_REPO` and `SMALLER_CHAT_REPO` live near the top of `chirp/init_flow.py` so other modules (story 7.2's `_print_migration_plan`, story 7.5's README sweep) reference the same source of truth.

The `--switch-model` flag is preserved but routes through registry semantics: when no model is registered, it suggests `chirp models add <hf-repo>`; when one is registered, it interactively flips the default via `chirp models default <alias>`. **No Ollama tag picker** survives. The implementation can shell to those commands or call their underlying functions directly (preferred — avoids a subprocess hop).

Existing `_screen_recording_permission()` (EPIC-AUDIO-CAPTURE story 2.3) stays unchanged. Position in `verify()`: Apple-Silicon → brew → ffmpeg → daemon-readiness → default-chat-model → screen-recording.

## Acceptance criteria

- **AC-1 — Apple-Silicon gate runs first.** `run_init()` (or its delegate) checks `platform.machine() == "arm64"` **before any other phase work**. On non-arm64 (Intel, Rosetta-translated x86_64 Python, etc.): print a single-line message naming the constraint (e.g. `chirp requires Apple Silicon (M1/M2/M3/M4 or newer). Detected: <machine>.` plus a one-line hint about installing an arm64 Python if the user expects to be on Apple Silicon under Rosetta), do **not** print the Phase 1 verify table, do **not** lazy-spawn the daemon, do **not** touch the filesystem, and exit with status code `7`. Implements **FR54, NFR-C2**.

- **AC-2 — `verify()` no longer references Ollama.** The returned `DependencyStatus` list contains, in order: brew (existing), ffmpeg (existing), **daemon readiness** (new), **default chat model** (new), screen-recording permission (existing). No `Ollama` row. No `model: <tag>` rows. The function does not import `requests` (Ollama HTTP probe), and `_ollama_installed`/`_ollama_models`/`_model_installed`/`CHAT_MODELS`/`EMBEDDING_MODELS` are deleted from the module. Implements **FR49**.

- **AC-3 — Daemon-readiness probe uses `llm.client.health()`.** A new helper `_daemon_ready()` returns a `DependencyStatus` named `chirpd`. Mapping:
  - `llm.client.health()` returns OK → `(installed=True, detail=f"healthy · v{daemon_version}")`
  - `llm.client.health()` raises `LLMDaemonSpawnFailed` → `(installed=False, detail="daemon could not be started — run 'chirp daemon logs' for details", required=True)`
  - `llm.client.health()` raises `LLMTransportError` (other subclass) → `(installed=False, detail=f"daemon unreachable: {short_message}", required=True)`
  - The probe must **not** spawn additional daemons beyond what `llm.client` does internally. The client encapsulates lazy-spawn. Implements **FR51**.

- **AC-4 — Default-chat-model check uses the registry.** A new helper `_default_chat_registered()` calls `llm.registry.read_registry()`. If `default_chat` is set and resolves to an alias in the `[models]` table → `(installed=True, detail=f"default chat: {alias}")`. Otherwise → `(installed=False, required=False, detail="not configured — run 'chirp models add mlx-community/gemma-4-4b-it-4bit'")`. Missing-registry-file (`models.toml` absent) is treated the same as `default_chat` unset (non-blocking, points at `chirp models add`). Implements **FR50**.

- **AC-5 — `install_missing()` no longer brew-installs Ollama.** The Ollama brew-install + `brew services start` tasks are removed. `install_missing()` keeps the brew/ffmpeg tasks and the `capture_audio` rebuild task from story 2.3. If the daemon-readiness row is `not installed`, `install_missing()` does **not** try to "install" the daemon — the daemon is part of the pip package and is lazy-spawned by `llm.client`. Instead, on failure, `install_missing()` surfaces the daemon-failure detail and points the user at `chirp daemon logs`.

- **AC-6 — `run_init()` no longer references Ollama anywhere.** The post-Phase-2 "ollama isn't running" red-error branch is gone. The Phase 3 picker is gone. The Phase 4 `ollama pull` is gone. `pull_and_finalize()` is either deleted (preferred) or repurposed to a small `_finalize_paths()` helper that creates `~/.chirp/`, `~/.chirp/chroma/`, and `~/Documents/chirp/` if missing and prints the "your nest is ready" panel — no model pulling. The panel's example commands stay (`$ chirp record` and `$ chirp ask "..."`).

- **AC-7 — `--switch-model` routes through the registry.** With a registered chat model: `chirp init --switch-model` lists registered chat aliases (via `llm.registry.read_registry()`) and prompts the user to pick one; the chosen alias is set as `default_chat` (via the same code path `chirp models default <alias>` uses — preferred: call the function directly, not subprocess). With no registered chat model: print the same "run `chirp models add ...`" hint as AC-4 and exit 0. No Ollama tag picker is shown.

## Dev notes

- **Why exit code `7`.** PRD §Scripting Support reserves codes 0–5. EPIC-WF-ALIGN didn't claim 6 or 7. `7` is far enough from typer's default `2` (usage error) to be distinguishable from "user passed `--bogus`" and from chirp's documented daemon-unreachable (`3`) and model-not-found (`5`).
- **Why Apple-Silicon check goes before `--switch-model`.** Switching models on an Intel Mac is impossible — there's no daemon, there's no MLX runtime, the request would fail downstream anyway. Failing fast at the architecture gate keeps the error message clear instead of layering "you don't have a daemon" on top.
- **Why the daemon-readiness probe is `llm.client.health()` and not custom socket-pinging.** Per architecture §Cross-Component Dependencies, `llm.client` owns the "is the daemon up" abstraction. Duplicating it in `init_flow` would drift. The architecture explicitly states: "Don't write any 'is the daemon process running' logic outside `llm.client`."
- **Why the registry-empty row is `required=False`.** A user who just ran `pip install chirp` and `chirp init` has no model yet — that's a normal first-run state, not a failure. Marking it `required=False` keeps Phase 2 from trying to "install" the registry. The follow-up `chirp models add` is the user's next deliberate step (Maya's journey).
- **Why we don't pre-warm the model in `init`.** OQ4 is open and skews Growth-tier. The decision in this epic is to keep init narrow: verify → install (build helpers if needed) → finalize paths. The model is warmed on `chirp models add` and again on first `chirp ask`. No init-time warm.
- **Why `_run_switch_model` should call the registry function directly rather than subprocessing `chirp models default`.** Same Python process, same settings, same exception types. Subprocessing adds startup cost and complicates error propagation. The `chirp models default` Typer command should be a thin wrapper around a callable in `llm.registry` or `llm.cli.models` — call the underlying function.
- **Recommended model alias choice in the hint.** Per OQ1, we recommend `mlx-community/gemma-4-4b-it-4bit` as the primary option and offer `mlx-community/gemma-4-e2b-it-8bit` as a smaller-footprint alternative (Gemma effective-2B at 8-bit) for tight-RAM users. Same examples the PRD uses throughout and the same ones Devon's migration message points at. If the model landscape shifts, update `RECOMMENDED_CHAT_REPO` / `SMALLER_CHAT_REPO` near the top of `init_flow.py` — single-line change in one place.
- **Lazy imports of `llm.client` and `llm.registry`.** Import inside helper functions, not at module top. Two reasons: (a) `chirp init` is sometimes the user's first invocation, before `llm.client` has been fully initialized in tests; (b) a broken `llm` module shouldn't prevent `chirp --help` from rendering.
