# Story 7.2 — `chirp init --recheck`: Ollama-detection and loud migration plan

- **Status:** Review — implemented on branch `feat/story-7.2-recheck-migration-plan` (stacked on 7.1). All ACs verified; live Devon-scenario smoke ran on a machine with real Ollama remnants (all three heuristics fired). See **Dev Agent Record**.

- **Depends on:** 7.1 (the new `verify()` shape and Apple-Silicon gate must already be in place; the migration plan prints **after** the verify table)

## User story

As a Chirp user who has been running the Ollama-backed version for months, I upgrade chirp, run `chirp init --recheck`, and want a clear multi-line plan telling me: (a) Ollama is still installed on my machine and chirp has not touched it, (b) which model to register with the new chirpd daemon (`chirp models add mlx-community/gemma-4-4b-it-4bit`), (c) that my existing notes / config / chroma index are unchanged, and (d) the manual cleanup steps if I want to free the disk space.

I want to be told, not nagged. Chirp must not run `brew uninstall ollama` for me, must not delete `~/.ollama`, and must not touch `OLLAMA_HOST`. The PRD explicitly forbids modifying my Ollama install.

## Context

This is Devon's journey (PRD User Journey 2). Devon is the principal target of `chirp init --recheck` migration UX. The PRD leaves the messaging strategy open (OQ6: loud vs quiet); this epic resolves it to **loud / multi-line** per Devon's journey, and this story documents that resolution explicitly so future contributors don't quietly flip it.

The migration plan layers on top of story 7.1's new `verify()` flow. Detection runs **after** the verify table is printed (so the user has already seen the chirpd row and the default-chat-model row), and the plan only prints when both: (a) `--recheck` is the active flag, and (b) at least one Ollama heuristic fires.

**Detection heuristics (OR'd together):**

1. `shutil.which("ollama")` returns a path → Ollama CLI is on PATH (Homebrew install or curl-installer install).
2. `(Path.home() / ".ollama").is_dir()` → Ollama data directory exists (covers cases where the CLI was removed but model files remain).
3. The `ollama` Python module is importable → the old chirp's transitive dep still present. (After story 7.4 removes the dep, this branch only fires for users who installed `ollama` directly outside chirp's deps.)

The plan does **not** probe `localhost:11434` — that would be redundant (we already know about Ollama from the above) and would re-introduce a `requests` import in `init_flow.py` that story 7.1 removed.

**The plan is informational only.** No `brew uninstall ollama`. No `rm -rf ~/.ollama`. No `OLLAMA_HOST` unsetting. No service stopping. The PRD's "auto-uninstall of Ollama" out-of-scope item is the binding constraint.

**Recommended cleanup is documented in the printed plan**, not executed: `brew uninstall ollama` (if the user installed via Homebrew), `rm -rf ~/.ollama` to reclaim GGUF disk space (typically 5+ GB for a single 7B model), and unsetting `OLLAMA_HOST` from the shell rc if it was set.

The plan prints once per `--recheck` invocation. If the user has detected-Ollama state but is running `chirp init` *without* `--recheck` (i.e., the full install/finalize flow), the plan does **not** print — only `--recheck` is the migration touchpoint. Rationale: full `chirp init` is a fresh-setup flow; `--recheck` is the migration diagnostic.

Files to touch:

- **`chirp/init_flow.py`** — add `_detect_ollama_install() -> dict[str, bool]` and `_print_migration_plan(console, detection)`. Call the printer from `run_init()` only when `recheck=True` and detection fired.
- **`tests/test_init_flow.py`** — add tests covering each detection branch, the no-detection silent case, and the plan content.

## Acceptance criteria

- **AC-1 — Detection runs only on `--recheck`.** `_detect_ollama_install()` is called inside `run_init` only when `recheck=True` and only after the verify table has been printed. On `chirp init` (no `--recheck`), the detection function is not called and the plan is not printed. Implements **FR53** (recheck-scoped).

- **AC-2 — Detection heuristics.** `_detect_ollama_install()` returns a dict of three bools:
  ```python
  {"cli_on_path": shutil.which("ollama") is not None,
   "data_dir_present": (Path.home() / ".ollama").is_dir(),
   "python_module_importable": _try_import_ollama_module()}
  ```
  Where `_try_import_ollama_module()` does `try: import ollama; return True except ImportError: return False`. The dict is "truthy" when any value is True. The plan prints when `any(detection.values())`.

- **AC-3 — Plan is loud (multi-line) per OQ6.** When detection is truthy, print exactly the following block (final copy may polish wording; structure is binding) via `console.print`:
  ```
  ──────────────────────────────────────────────────────────
   Ollama migration
  ──────────────────────────────────────────────────────────
   chirp 2.x no longer uses Ollama. The bundled chirpd daemon
   (visible in the verify table above) replaces it for chat
   and embeddings.

   Your existing chirp data is unchanged:
     · ~/Documents/chirp/<slug>/        (notes, transcripts, audio)
     · ~/.chirp/config.toml             (settings)
     · ~/.chirp/chroma/                 (search index)

   To finish the migration:
     1. Pick an MLX model (GGUF models do not work):
          chirp models add mlx-community/gemma-4-4b-it-4bit
        (~2 GB, balanced quality and speed)

        Tight on RAM? Use the smaller-footprint variant:
          chirp models add mlx-community/gemma-4-e2b-it-8bit
     2. (Optional) Once you're satisfied with the new setup,
        clean up Ollama manually. chirp will NOT do this for you:
          brew uninstall ollama        # if installed via Homebrew
          rm -rf ~/.ollama             # reclaims ~5 GB of GGUF files
          unset OLLAMA_HOST            # if set in your shell rc

   Detected on this machine:
     [ollama on PATH]            <yes|no>
     [~/.ollama directory]       <yes|no>
     [ollama python module]      <yes|no>
  ──────────────────────────────────────────────────────────
  ```
  The "Detected on this machine" section only lists the heuristics that fired (or shows yes/no for each). Lines about manual cleanup are explicit that **chirp will not do this for you**. Implements **FR53** (loud message; informational-only; OQ6 resolved to loud).

- **AC-4 — No mutation of the user's Ollama install.** No code path in `_detect_ollama_install`, `_print_migration_plan`, or anything called from them runs `subprocess.run(["brew", ...])`, mutates `~/.ollama`, modifies `OLLAMA_HOST`, calls `launchctl unload` on an Ollama plist, or stops a service. The story's tests assert this by patching `subprocess.run` with a strict mock that fails the test if invoked during `--recheck` after the verify table.

- **AC-5 — Plan suppressed when detection is empty.** When `_detect_ollama_install()` returns `{"cli_on_path": False, "data_dir_present": False, "python_module_importable": False}`, `_print_migration_plan` is not called. The `--recheck` flow ends silently after the verify table. (Maya, on a machine that never had Ollama, sees no migration noise.)

- **AC-6 — Plan prints once per invocation.** Even on a slow `--recheck` (e.g. daemon takes a moment to lazy-spawn), the plan prints exactly once. No double-printing on retry paths inside `llm.client.health()`.

- **AC-7 — Recommended models in the plan match the recommendation elsewhere.** Both `chirp models add <repo>` examples in the plan reference the `RECOMMENDED_CHAT_REPO` and `SMALLER_CHAT_REPO` constants introduced in story 7.1. Future model changes are a single-line edit in `init_flow.py`.

- **AC-8 — Tests in `tests/test_init_flow.py`.** Add the following tests, all of which patch `shutil.which`, `Path.home`, and `_try_import_ollama_module` to control detection:
  - `test_recheck_with_no_ollama_detected_prints_no_plan` — all three heuristics return False; assert the captured console output contains the verify table but not the string `"Ollama migration"`.
  - `test_recheck_with_ollama_cli_on_path_prints_plan` — `shutil.which("ollama")` returns `"/opt/homebrew/bin/ollama"`; assert `"Ollama migration"` and the `chirp models add` line appear in the output, and the "Detected on this machine" section shows `[ollama on PATH]  yes`.
  - `test_recheck_with_data_dir_only_prints_plan` — `~/.ollama` exists, others false; plan prints; detected section shows `[~/.ollama directory]  yes` and the other two `no`.
  - `test_recheck_with_python_module_importable_prints_plan` — the import branch fires; plan prints.
  - `test_recheck_plan_does_not_mutate_ollama_install` — patch `subprocess.run` with a `Mock(side_effect=AssertionError("must not call subprocess during recheck migration plan"))`; run `--recheck` with all heuristics True; assert the plan prints and `subprocess.run` was never called.
  - `test_full_init_no_recheck_does_not_print_plan` — run `chirp init` (no `--recheck`) with all heuristics True; assert `"Ollama migration"` does not appear in the captured output. (Detection is `--recheck`-scoped.)
  - `test_plan_recommends_default_chat_repo` — assert the printed plan contains `mlx-community/gemma-4-4b-it-4bit` (or whatever `RECOMMENDED_CHAT_REPO` resolves to).

- **AC-9 — Quality gates.** `make check` and `make test` pass. Coverage on the new functions ≥ 90% line.

- **AC-10 — Manual verification.** On a Mac with Ollama installed via Homebrew: `chirp init --recheck` prints the verify table and the migration plan; the plan's "Detected on this machine" section reflects the real state. `brew uninstall ollama && rm -rf ~/.ollama && unset OLLAMA_HOST && chirp init --recheck` no longer prints the plan (all three heuristics now False).

## Implementation tasks

1. **Add `_detect_ollama_install()`.** Pure function. Returns the three-key dict described in AC-2. Uses `shutil.which`, `Path.home`, and a small `_try_import_ollama_module()` helper that does `try: import ollama as _o; return True; except ImportError: return False`. No I/O beyond `which` and `Path.is_dir()`.

2. **Add `_print_migration_plan(console, detection)`.** Pure rendering. Uses `console.print` with the multi-line block from AC-3. The "Detected on this machine" subsection iterates the detection dict and prints `yes`/`no` per heuristic. Plan body references `RECOMMENDED_CHAT_REPO` from story 7.1 — import it from the same module-level constant, do not duplicate the string.

3. **Hook into `run_init`.** After `verify(...)` returns and **before** the `if recheck: return 0` early-return, call:
   ```python
   if recheck:
       detection = _detect_ollama_install()
       if any(detection.values()):
           _print_migration_plan(console, detection)
       return 0
   ```
   This ensures the plan prints only on `--recheck` and only when detection fires. The plan must print **after** the verify table so the user sees the chirpd row and the default-chat-model row first (Devon's journey: "Chirp detects: Ollama installed; no chirp model registered yet ...").

4. **Confirm no mutation paths.** Audit the story's added code — no `subprocess.run`, no `os.remove`, no `Path.unlink`, no `os.environ.pop`, no `shutil.rmtree`. The test in AC-8 case 5 enforces this via mock.

5. **Tests.** Implement the seven tests in AC-8. Use `capsys` or a Rich console fixture (whichever the existing test suite uses) to capture printed output. Patch `shutil.which` with `unittest.mock.patch`. Patch `Path.home` to point at a tmp dir for the data-dir-present case. Patch `_try_import_ollama_module` via direct attribute replacement.

6. **Documentation note.** Inside `chirp/init_flow.py`, add a single short comment near `_print_migration_plan` referencing PRD §Project Scoping → Out of Scope → "auto-uninstall of Ollama" and PRD OQ6's resolution to "loud" — so a future contributor reading the code understands why the plan is informational and multi-line, not silent.

## Dev notes

- **Why the loud/multi-line message (OQ6 resolution).** Devon's journey describes a multi-line migration plan as the expected output. The alternative — a one-line "Ollama detected; see https://chirp.example/migration" — would (a) require maintaining an external URL, (b) force the user to context-switch to a browser, (c) not work offline. Multi-line costs ~25 lines of terminal output once per `--recheck` and is offline-friendly. Reconsider if user feedback shows it reads as noisy.
- **Why detection runs in `--recheck` only.** Full `chirp init` is the fresh-install path (Maya). Devon's path is `--recheck`. Showing the migration plan on a full `init` would noise up the install flow for users who never had Ollama. Tying detection to `--recheck` keeps the noise scoped to the migration moment.
- **Why three heuristics OR'd.** `which ollama` covers Homebrew installs that are currently on PATH. `~/.ollama` covers cases where the CLI was uninstalled but the data files remain (the user is mid-cleanup). The Python-module import covers cases where chirp's old transitive dep is still resolvable. Any single signal is enough — false positives are tolerable (a one-time noisy message), false negatives are not (Devon needs to see the plan).
- **Why we don't probe `localhost:11434`.** It would mean re-importing `requests` (which story 7.1 cleaned out of `init_flow.py`), and it would only add information we already have. If `ollama` is on PATH, the user has it; whether the daemon is also currently serving is irrelevant to the migration message.
- **Why the plan explicitly says "chirp will NOT do this for you".** Devon needs to trust that running `chirp init --recheck` is a safe diagnostic — that it won't suddenly `brew uninstall` something. Being explicit in the printed copy is cheaper than expecting users to read the PRD.
- **Why `~/.ollama` removal is shown as `rm -rf` (not `chirp` doing it).** Per the PRD §Project Scoping → Out of Scope: "Don't touch the user's system. Surface a recommendation in `chirp init --recheck`; user uninstalls manually." Showing the command lets the user copy-paste it knowingly.
- **Idempotency.** Running `chirp init --recheck` multiple times in a row when Ollama is still installed prints the plan each time. That's intentional — the user can come back to the message after taking partial cleanup steps. We don't persist "user has been shown the plan" state; it's cheap to re-print.
- **Interaction with story 7.4.** When story 7.4 lands and removes the `ollama` Python dep from `pyproject.toml`, the `python_module_importable` heuristic will return False for users who only ever had `ollama` via chirp's transitive dep. Users who installed `ollama` directly (rare) still trip the heuristic. The `which ollama` and `~/.ollama` heuristics keep the detection working for the common Homebrew case.
