## Prerequisites

## User story

As a chirp maintainer, I want every test that previously stubbed the Ollama HTTP API to use either the architecture's `FakeBackend` (via an in-process daemon-under-test) or a mocked `llm.client` at the call-site boundary, so that the test suite reflects the new client surface, mirrors the architecture's stated testing pattern, and is free of dead Ollama-shaped fixtures that would silently rot.

## Context

Architecture §Testing Patterns is explicit:

> **Backend abstraction for unit tests.** The daemon's inference layer sits behind a `LLMBackend` protocol […]. **Unit tests use `FakeBackend`.** No `mlx-lm` import required to run the daemon's unit tests. […] **Integration tests use an in-process socket.** Start the daemon in the same Python process via `asyncio.start_unix_server(...)` against a temp socket; connect from the test with `LLMClient(socket_path=...)`.

And the anti-pattern:

> **Mock the MLX module in unit tests** — don't. Use `FakeBackend` at the `LLMBackend` protocol boundary instead.

Two test-shaping decisions matter:

1. **Where to mock.** Either inject a fake `llm.client` at the call site inside `notes/` or `notes_chat/` (so tests are pure-Python with no socket), **or** stand up an in-process `chirpd` instance with a `FakeBackend` and let tests speak the wire protocol. Per the epic's locked decision 10: pick the simpler option per test — don't over-engineer.

2. **What to retire.** The old fixture shape (mocking `requests.post`/`requests.get` at module level, asserting on JSON request bodies, returning canned Ollama response shapes — `{"response": "...", "done": true}` for generation, `{"embedding": [...]}`/`{"embeddings": [...]}` for embeddings) is dead for the migrated paths after 6.2 / 6.3 / 6.4. This story retires those fixtures.

In practice, **injecting a fake client at the call-site boundary is the simpler option** for almost every test. The in-process daemon pattern is heavier (socket setup, lifecycle, async coordination) and pays off when testing the protocol or the daemon itself — that's `tests/chirpd/` and `tests/llm/` territory under EPIC-CHIRPD-CORE. This story therefore standardizes on the **injected-fake-client** pattern across the LLM-touching tests, with **one** designated integration test using the in-process daemon to exercise the full wire path.

**The real production seams (what tests target):**

- `notes/note_generator.py` — `NoteGenerator(settings, console=None, llm_client=None)`. `_call_llm` does `client.chat_stream_sync(messages, model="default", options={"max_tokens": ...})` and joins the yielded **`str`** tokens. Inject via `llm_client=` or patch `notes.note_generator.LLMClient`.

- `notes_chat/prompting.py` + `notes_chat/interactive.py` — the streaming chat path migrated by story 6.4 (`chat_stream_sync` → `str` tokens, `cancel_sync` for Ctrl-C).

## Dev notes

- **Why inject the fake client rather than patch a module global.** Production never holds a module-level `client`; it constructs `LLMClient()` lazily and accepts injection through `llm_client=` (`NoteGenerator`) and `client=` (`_get_query_embedding`). Injection is the cleanest seam and survives refactors; the fallback is patching the `LLMClient` symbol imported into the module under test (`notes.note_generator.LLMClient`, `notes_chat.retrieval.LLMClient`), not a nonexistent `.client.embed` attribute.
- **Why tokens are `str`, not `_FakeDelta`.** `ChatStream.__anext__` already reads `event[EVENT_DELTA]["text"]` off the wire and returns it as a `str`; `chat_stream_sync` is a sync wrapper over that. Production iterates `for token in client.chat_stream_sync(...)` where `token` is a `str`. A fixture yielding `_FakeDelta(text=...)` would mock a type the code never sees and the `token` strings would become objects, breaking `"".join(...)`. Model token strings directly.
- **Why `fake_embed` asserts length parity.** `embed_sync(inputs, model)` returns one vector per input, in order (story 6.3's contract). Asserting `len(vectors) == len(inputs)` in the fixture keeps a test from silently passing when production sends a different number of inputs than the fixture scripted.
- **Why one integration test, in this epic.** AC-7 gives one end-to-end smoke over the real wire (notes/notes_chat module → `llm.client` → in-process daemon → `FakeBackend` → back), catching integration regressions pure unit tests miss. The daemon's own protocol tests live in EPIC-CHIRPD-CORE; this is a single guardrail, not a second copy of that suite.
- **Why the shared fixtures live in root `tests/conftest.py`.** The LLM-touching tests are flat under `tests/` (there is no `tests/notes/` package), with a few under `tests/notes_chat/`. A root-conftest fixture is visible to all of them via pytest's conftest chain; a `tests/notes_chat/conftest.py` would not reach the flat files.
- **Why a typed fake over `MagicMock`.** A `MagicMock` answers any attribute access, so a test asserting `token`-as-`str` passes even if production starts probing attributes that don't exist. The `fake_llm_client`/`SimpleNamespace` exposes exactly the four methods; unexpected access fails loudly.
- **Why a conventions test.** Without it, a future "let me just patch `requests.post` real quick" test silently re-introduces the dead-fixture shape. ~15 lines prevents the drift; the AC-8 allowlist keeps the genuinely-deferred Ollama-helper tests legal until EPIC-INIT-AND-MIGRATION retires them.
- **Why coverage cannot regress.** PRD NFR-M1: "Coverage on touched existing modules does not regress." This is the first epic story that reshapes the test surface in a way that could shed coverage; the per-file comparison against the pre-6.2 baseline is the gate.
