# Story 6.1 — Regression corpus capture (precondition gate)

- **Status:** Review
- **Epic:** [EPIC-INTEGRATION-CUTOVER](../epic.md)
- **Depends on:** —
- **Blocks:** 6.2, 6.3, 6.4, 6.5, 6.6

## Prerequisites

- The current Ollama-backed pipeline is still wired up and working on the operator's machine. `chirp record`, `chirp transcribe`, and (optionally) `chirp ask` against the existing `ollama` daemon produce `transcript.txt` and `notes.md` files end-to-end. No part of this story exercises `chirpd` — its purpose is to lock in the "before" baseline against the existing pipeline.
- The operator has Ollama installed and the configured `models.llm` is pulled (`ollama list` shows the model named in `~/.chirp/config.toml`). If the Ollama daemon is not running, start it with `brew services start ollama` or `ollama serve` before beginning.
- At least ≥10 candidate audio recordings are available. They can be freshly captured via `chirp record` during this story, repurposed from the operator's existing chirp notes directory, or a mix. They must satisfy the bucket distribution called out in AC-2.

## User story

As the chirp developer authoring the Ollama → MLX migration, I want a held-out corpus of ≥10 representative recordings with their existing Ollama-generated transcripts and notes committed to the repository under `tests/regression/notes_quality/`, so that after the cutover lands I can replay the new MLX pipeline against the exact same inputs and score the new output blindly against the locked baseline.

## Context

PRD §Domain-Specific Requirements → Validation Methodology requires a regression corpus to confirm the migration preserves note quality. The methodology has four mandatory properties:

1. **Coverage** — ≥10 representative recordings spread across length and speaker-count buckets.
2. **Pairing** — each recording is paired with the `notes.md` generated by the **current** Ollama-backed pipeline (the "before" baseline). Both the transcript and the generated notes are committed.
3. **Comparison protocol** — the "after" notes generated by the new MLX pipeline (story 6.6) will be scored blindly against the "before" notes for structure, faithfulness, completeness, and brevity.
4. **Pass threshold** — ≥80% equal-or-better for the new pipeline (recorded at the end of story 6.6).

The readiness report (§Final Note → critical issues) calls out that this capture must happen **before** migration code is written, because once the Ollama call sites in `notes/note_generator.py` and `notes_chat/retrieval.py` are removed (stories 6.2 and 6.3), regenerating the "before" baseline becomes impossible without reverting the branch. This story therefore blocks every other story in EPIC-INTEGRATION-CUTOVER.

The corpus storage layout is locked by architecture §Gap Analysis → Minor clarifications: `tests/regression/notes_quality/<slug>/{transcript.txt, notes_before.md}`. Audio is **not** committed (too large; gitignored). The README documents how an operator can recapture audio locally if needed (e.g., for ad-hoc re-runs on a different machine).

This story produces no production code changes — it produces (1) the directory + README, (2) ≥10 per-recording subdirectories with transcripts and `notes_before.md`, (3) one `.gitignore` rule keeping audio files out, and (4) a small smoke test that asserts the corpus inventory satisfies the bucket distribution. Story 6.6 will append `notes_after.md` files and a `results-<date>.md` after the cutover lands.

## Acceptance criteria

- **AC-1** A new directory `tests/regression/notes_quality/` exists with a `README.md` documenting:
  - The corpus's purpose (regression-test bed for the Ollama → MLX migration; pass threshold ≥80% equal-or-better per PRD §Domain Requirements).
  - The required bucket distribution (3 short, 4 medium, 3 long; mix of single-, two-, multi-speaker; mix of technical and non-technical content).
  - The capture procedure: record audio via `chirp record` (or designate an existing recording), run `chirp transcribe` against the current Ollama-backed pipeline, copy or rename the generated `transcript.txt` and `notes.md` into `tests/regression/notes_quality/<slug>/transcript.txt` and `tests/regression/notes_quality/<slug>/notes_before.md` respectively.
  - The blinded comparison procedure that story 6.6 will follow (referenced — full procedure lives in story 6.6).
  - Why audio is gitignored (size; user-data sensitivity; not needed for replay since transcripts are committed).
  - How to recapture missing audio locally if a developer needs to re-run a recording from scratch — name the source URL or topic descriptor for each entry, where applicable.
- **AC-2** `tests/regression/notes_quality/` contains **≥10 per-recording subdirectories**, satisfying the bucket distribution:
  - At least 3 short recordings (<2 min of audio / <300 words of transcript)
  - At least 4 medium recordings (5–15 min / ~700–2000 words)
  - At least 3 long recordings (>20 min / >3000 words)
  - At least one single-speaker recording, one two-person recording, and one multi-speaker (3+) recording (these can overlap with the length buckets — a single recording satisfies both a length and a speaker bucket).
  - At least one technical recording (code / engineering content) and at least one non-technical recording (general meeting / planning content) (again, can overlap with other buckets).
- **AC-3** Each subdirectory is named with a descriptive lowercase-hyphenated slug (e.g., `tests/regression/notes_quality/team-standup-short/`, `tests/regression/notes_quality/architecture-deep-dive-long/`). Slug names are stable — they are referenced by the results file in story 6.6.
- **AC-4** Each subdirectory contains exactly two committed files at this story's merge:
  - `transcript.txt` — verbatim Whisper transcript from `chirp transcribe` against the recording, encoded UTF-8, no trailing whitespace differences vs. what `chirp transcribe` wrote to `~/Documents/chirp/<slug>/transcript.txt`.
  - `notes_before.md` — verbatim `notes.md` generated by `chirp transcribe` against the **current Ollama-backed pipeline** for that transcript, including its YAML front-matter block (`---` … `---`).
- **AC-5** No `audio.wav` (or any other audio extension — `.m4a`, `.mp3`, `.flac`) is committed under `tests/regression/notes_quality/`. A `tests/regression/notes_quality/.gitignore` blocks audio extensions for future safety: at minimum `*.wav`, `*.m4a`, `*.mp3`, `*.flac`, `*.aiff`, `*.ogg`. `git ls-files tests/regression/notes_quality/` returns only `README.md`, `.gitignore`, and the `<slug>/transcript.txt` + `<slug>/notes_before.md` pairs.

  - `tests/regression/notes_quality/` exists and is a directory.
  - It contains at least 10 subdirectories (excluding files like `README.md`, `.gitignore`).
  - Each subdirectory contains both `transcript.txt` (non-empty, UTF-8 decodable) and `notes_before.md` (non-empty, UTF-8 decodable).
  - No file with an audio extension is present under any subdirectory.

The test asserts ≥3 short, ≥4 medium, ≥3 long. Speaker-count and technical/non-technical buckets are assertion-by-manifest: the test reads a `bucket_manifest.toml` (committed alongside the README) that maps each slug to `speakers` (`single` / `two` / `multi`) and `domain` (`technical` / `non-technical`), and asserts at least one slug per category.

9. **Commit.** Single commit (or small clean series). Message body cites the PRD section and lists the bucket coverage summary.

## Dev notes

- **Why no audio commit.** Audio files are large (~10 MB per minute for 16 kHz mono PCM; multiple GB total for a 10-recording corpus including long ones). They are also user-data-sensitive in some captures (real meeting content). The transcripts and `notes_before.md` are the comparison input for story 6.6 — audio is not needed for the comparison. If a future developer needs to re-run an entire recording (e.g., to test a Whisper-side change), the README's "how to recapture" section names the topic of each capture so they can produce a substitute recording.
- **Why a manifest TOML instead of inferring everything from filenames.** Speaker count and technical/non-technical domain are not inferable from a transcript alone without LLM-class analysis. A manual manifest is small enough to maintain by hand and is the single source of truth for the bucket-distribution test. Recording `notes_before_model` in the manifest makes the "before" baseline self-documenting: a future reader can see which Ollama model produced each `notes_before.md` without spelunking through git history.
- **Why use existing chirp recordings where possible.** The operator likely already has several recordings under `~/Documents/chirp/<slug>/` from day-to-day use. Reusing those saves capture time and grounds the corpus in genuinely representative real-user content. Be conservative about including recordings containing personal or sensitive content — the corpus is committed to the repository.
- **Why a smoke test, not just a README checklist.** The corpus is a regression-bed; if a future developer adds a new slug or moves a file, the smoke test catches mismatches before they cause story 6.6 to fail noisily later. The test is small (~50 lines).
- **Order of operations.** Capture (or designate) and transcribe **all** audio files first, then copy outputs into the corpus, then author the manifest and the smoke test, then verify with `make test`. Doing it in that order avoids the trap of committing partial corpora and re-running them later.
- **Defending against accidental Ollama-pipeline drift.** Make sure the operator captures all `notes_before.md` files using **the same** Ollama model (whatever `models.llm` resolves to in `~/.chirp/config.toml` at capture time). If the operator switches models mid-capture, the resulting corpus has mixed baselines and story 6.6's comparison loses meaning. The `notes_before_model` field in the manifest is the audit trail — if any two entries differ in that field, re-capture the affected entries before merging.
- **Resilience to baseline failures.** If `chirp transcribe` against the Ollama backend fails on a given recording (e.g., Ollama isn't running, model is missing), recapture that recording — do not commit a partial subdirectory. The corpus must be complete at merge time.
- **One developer, blinded scoring (story 6.6 preview).** Story 6.6 will shuffle the `before` / `after` pairs before scoring. This story doesn't blind anything; it just locks in the inputs.
