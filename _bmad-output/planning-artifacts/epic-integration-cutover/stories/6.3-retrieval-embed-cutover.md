# Story 6.3 — Cut over `notes_chat/retrieval.py` and `notes_chat/index.py` embeddings to `llm.client.embed`

- **Status:** Done
- **Epic:** [EPIC-INTEGRATION-CUTOVER](../epic.md)
- **Depends on:** 6.1 (regression corpus committed); EPIC-CHIRPD-CORE 3.6 (`client.embed` available); EPIC-MODEL-REGISTRY (an embed-role model registered as `default_embed`)
- **Blocks:** 6.5 (fixture migration), 6.6 (regression run)

## Prerequisites

- Story 6.1 has merged. The corpus's `transcript.txt` files are committed but the chroma index built against them used the old Ollama embedding model. That's fine — story 6.6 does not require chroma-index parity, only `notes.md` quality parity.
- An embed-role model is registered in `models.toml` via `chirp models add <embed-repo>` (e.g., `mlx-community/bge-small-en-v1.5` per PRD OQ2's working example). The daemon resolves `"default"` to this alias for `embed` ops per FR35.
- `chirpd` is running (lazy-spawn or LaunchAgent).

## User story

As a chirp user running `chirp ask` or `chirp search`, I want the retrieval-time embedding step to route through `chirpd` via `llm.client.embed` instead of the Ollama HTTP API, so that retrieval works without a separately-installed Ollama daemon — while my chroma index continues to live at `~/.chirp/chroma/` with its existing chunk IDs and metadata layout.

## Context

Two modules touch the embedding API today:

1. **`notes_chat/retrieval.py`** — query-time embedding for the user's question, used by `chirp ask` and `chirp search`. The function `_get_query_embedding(config, query)` at L392–410 calls `requests.post(f"{ollama_url}/api/embeddings", json={"model": emb_model, "prompt": query}, timeout=30)`. The result is a single list of floats. Returns `None` on any failure; callers (`_search_chroma`) treat `None` as "skip vector search."
2. **`notes_chat/index.py`** — indexer-time embedding when notes are added to the chroma collection. Around L334 (per the epic doc's call-site inventory), the indexer calls a similar Ollama-backed embedding helper for each new chunk.

Both call sites use the same Ollama `/api/embeddings` endpoint with `model = config.notes_chat.emb_model` (a string from `~/.chirp/config.toml`'s `notes_chat.emb_model` field). After EPIC-CHIRPD-CORE / EPIC-MODEL-REGISTRY, that string is an alias name resolved by the daemon — but the call-site code does not need to know that.

**Shape change.** Ollama's `/api/embeddings` is one vector per call. `llm.client.embed(inputs=[str, ...])` is batched: it takes a list and returns a list-of-vectors in matching order. We preserve the existing per-call semantics in this story — pass a one-element list when we have one input, unpack the single returned vector. Batching beyond one input per call is left as a future optimization (it would speed up `chirp index` builds by ~Nx where N is the chunk count per call, but it changes test fixtures and is not required by the epic's quality bar).

**Chroma layout.** Unchanged (FR47). Chunk IDs, the collection name, the `metadata` shape, and the index location (`~/.chirp/chroma/`) are not touched.

**What about chroma collections built against the old Ollama embedding model?** The new MLX embed model produces vectors in a different vector space — they are not directly comparable. Existing chroma indices continue to function (the chroma collection has fixed dimensions baked into its on-disk schema, and that dimension is determined at first-write). If the new MLX model produces vectors of a different dimension than the user's existing chroma index, chroma will raise on first query — and the documented remedy is `chirp index --force` to rebuild the index with the new embedding model. This story does **not** auto-rebuild; the user runs `chirp index --force` if they want to migrate their index. This matches the user-journey expectation from Devon's path in the PRD ("existing notes index continues to work post-migration") modulo this single one-shot rebuild on dimension mismatch.

## Acceptance criteria

- **AC-1** `notes_chat/retrieval.py` no longer imports `requests`. The `import requests` line at L7 is removed.
- **AC-2** `_get_query_embedding(config, query)` (current L392–410) is rewritten to call `llm.client.embed(inputs=[query], model="default")` and return the single returned vector (or `None` on `LLMError`). Specifically:
  - Resolve the client per the same import path used in story 6.2 (`from llm.client import client` or equivalent).
  - Call `vectors = client.embed(inputs=[query], model="default")`.
  - Return `vectors[0]` if `vectors` is non-empty; otherwise `None`.
  - Catch `LLMError` (the base, or the relevant subclasses `LLMTransportError` / `LLMProtocolError` / `LLMModelError`) and return `None`, mirroring the existing best-effort posture. Log at `logger.debug` like the existing path.
- **AC-3** `notes_chat/index.py`'s indexer-time embedding call site (the one ~L334 that currently posts to Ollama) is rewritten the same way: pass a one-element list to `client.embed`, take the single returned vector, write to chroma exactly as today. Module imports of `requests` (if any are present in this file solely for embeddings) are removed.
- **AC-4** Both call sites preserve insertion order. If a future batched-embed optimization passes `n>1` inputs, the returned vectors must align with the input list 1:1. This story's tests assert ordering on a 1-element list (trivial) and a 3-element list (using a synthetic batch in a unit test) for the embed adapter.
- **AC-5** Empty-input handling: if a caller ever passes an empty query string (`""`), `client.embed` is **not** called and the function returns `None`. The existing Ollama path would have called the API anyway and returned whatever Ollama did; we tighten this to a precondition check because the new client may reject empty inputs at the boundary. The check is one line: `if not query.strip(): return None`.
- **AC-6** `_search_chroma` (current L87–138 in `retrieval.py`) is unchanged. The chroma query call (`collection.query(query_embeddings=[query_embedding], ...)`) still receives one embedding wrapped in a list. The `where` clause, `n_results`, and result-parsing code are untouched.
- **AC-7** `_build_context`, `_merge_and_dedupe`, `format_sources`, `_search_bm25`, `_create_chunk_header`, `_generate_suggestion`, and every other helper in `retrieval.py` are **not modified**. The chroma collection layout, BM25 file, and manifest files are unchanged (FR47).
- **AC-8** Settings fields `config.notes_chat.emb_model` and `config.models.ollama_url` are no longer read from within `retrieval.py` or from the indexer's modified call site. The Pydantic field definitions in `config/settings.py` are not removed by this story (other modules may still read them); the cleanup is owned by EPIC-INIT-AND-MIGRATION.
- **AC-9** `rg -n "ollama|requests\.|/api/embeddings|ollama_url|emb_model" notes_chat/retrieval.py notes_chat/index.py` returns zero matches.
- **AC-10** New unit test `tests/notes_chat/test_embedding_adapter.py` (or additions to an existing test file) asserts:
  - `_get_query_embedding` returns the first vector when `client.embed` returns a list of one vector.
  - `_get_query_embedding` returns `None` when `client.embed` raises `LLMTransportError`, `LLMProtocolError`, or `LLMModelError`.
  - `_get_query_embedding` returns `None` (without calling the client) on an empty / whitespace-only query.
  - `_get_query_embedding` calls `client.embed` with `model="default"` and a one-element `inputs` list whose entry is the query string.
  - The indexer's call site (whichever helper wraps the per-chunk embed in `notes_chat/index.py`) is tested for the same call-shape: `model="default"`, one input per call (or batched if the implementer chose to batch — but the test must assert input-to-output order).
- **AC-11** A targeted ordering test exercises a synthetic 3-element batch: given a fake `client.embed` that returns `[v_a, v_b, v_c]` for `inputs=["a", "b", "c"]`, the indexer-side wrapper assigns each vector to the matching chunk. This protects against a future batched-embed optimization breaking ordering.
- **AC-12** `make check` and `make test` pass. Coverage on `notes_chat/retrieval.py` and `notes_chat/index.py` does not regress vs. the pre-cutover baseline (NFR-M1).
- **AC-13** Manual smoke: with the existing chroma index intact (built against the Ollama embed model on the operator's machine), run `chirp ask "..."`. ## Dev notes

- **Why a one-element input list, not a single-input convenience API.** `llm.client.embed` is batched-by-design (FR22). Wrapping a single input in a list is one extra `[ ... ]` per call and avoids defining a second `embed_one` API at the client level. The current call sites only ever embed one input at a time, but preserving the batched shape at the client makes future batched indexing a drop-in change.
- **Why catch `LLMError` and return `None`.** The existing Ollama path returns `None` on any `requests` failure (connection error, timeout, non-200). Callers — primarily `_search_chroma` — treat `None` as "skip vector search, fall back to BM25-only retrieval." Preserving the `None` return on the new path keeps the fallback intact. Surfacing a typed `LLMTransportError` to the caller would require updating callers' error handling, which is out of this story's scope (and out of the epic's scope per locked decision 13 — we are not changing user-facing error UX beyond what the client surfaces by default).
- **Empty-input precondition (AC-5).** Today's Ollama path silently calls `/api/embeddings` with a blank prompt; Ollama returns some vector anyway. The new client may treat empty input as an error (the architecture doesn't specify either way). Tightening the call site to short-circuit on empty input avoids depending on that unspecified behavior. The cost is one line.
- **Dimension mismatch is a one-time rebuild, not a migration.** A real user upgrading chirp will likely see a chroma error on their first `chirp ask` after the cutover because the new embed model produces vectors of a different dimension than the old. The PRD's Devon journey explicitly covers this — "existing notes and chroma index continue to work post-migration" — and the documented remedy is `chirp index --force`. This story does not auto-detect dimension mismatch; surfacing a "you need to reindex" message lives in EPIC-INIT-AND-MIGRATION's `chirp init --recheck` work. For this story, the manual smoke test simply runs `chirp index --force` if it sees a chroma error.
- **Why the indexer's call site is touched in this story, not in a separate one.** The indexer and the retrieval query share one functional contract (the embed boundary). Splitting them across stories would force two passes through the same review, and the indexer test in story 6.5 (fixture migration) is cleaner if both sides of the embed boundary have already been rewritten.
- **Why not change the chroma `add` / `upsert` shape.** Chroma takes `embeddings: list[list[float]]` natively — it is already batched-compatible. The indexer's existing loop that adds one chunk at a time keeps working without modification. A future optimization could collect all new chunks, embed them in one `client.embed` call, then `collection.add(embeddings=all_vectors, ...)` — but that's a 6.x-or-later follow-up.
- **`config.notes_chat.emb_model`** is a string today (e.g., `nomic-embed-text:latest`). Post-migration, it is an alias-into-`models.toml` (e.g., `bge-small-en-v1.5`). Call sites don't read it after this story — only the daemon resolves model strings to weights. The field stays in `ChirpSettings` for now; EPIC-INIT-AND-MIGRATION decides whether to rename it, redocument it, or drop it.
- **What if `models.toml` has no `default_embed`?** The daemon raises `MODEL_NOT_FOUND` when `"default"` cannot resolve. The client surfaces this as `LLMModelNotFound` — a subclass of `LLMModelError`. Our `except LLMError` in `_get_query_embedding` catches it and returns `None`. The user sees "no documents found matching your query" (the current fallback message), which is suboptimal — they should see "no embed model registered; run `chirp models add <embed-repo>`." Improving that error message is out of scope here; it lives in EPIC-INIT-AND-MIGRATION's UX sweep.

## Dev Agent Record

### Contract verification (real `llm.client.embed` vs. story assumptions)

Verified against `llm/client.py` before coding (cutover stories drift from spec):

- **Client shape.** No module-level `client` singleton / `client.embed`. Reality:
  `LLMClient().embed_sync(inputs: list[str], model="default") -> list[list[float]]`
  (sync wrapper over the async `embed`). Used that, mirroring the
  `notes_chat/prompting.py` precedent. `LLMError` (+ subclasses) come from
  `llm.exceptions`.
- **Injectable clients.** `_get_query_embedding(config, query, client=None)` gains an
  optional `client` param (default → `LLMClient()`); `IndexManager.__init__` gains
  `llm_client=None`, lazily cached in `_get_embeddings`. Both mirror the 6.2 pattern
  and keep existing callers unchanged.

### Decisions / deviations (documented)

- **Indexer batches (AC-4/AC-11).** `_get_embeddings(texts)` is already `list ->
  list`, so it now makes a single `embed_sync(inputs=texts)` call instead of a
  per-chunk loop — simpler, one round-trip, and order-preserving by the client
  contract. Story task 4 sanctions batching; AC-11's 3-element ordering test covers
  it. Empty-input short-circuits to `[]` without calling the client.
- **`config` param now unused in `_get_query_embedding`.** Retained for caller
  signature stability per AC-2 (callers pass `config` positionally). `emb_model` /
  `ollama_url` are no longer read in either module (AC-8); the settings fields stay
  put for EPIC-INIT-AND-MIGRATION.
- **AC-9 grep clean:** `rg "ollama|requests\.|/api/embeddings|ollama_url|emb_model"
  notes_chat/retrieval.py notes_chat/index.py` → zero matches.

### Test changes (AC-10/11/12)

- New `tests/test_embedding_adapter.py`: query-time call-shape (`model="default"`,
  `inputs=[query]`), empty/whitespace short-circuit (client not called), empty-vector
  → None, `LLMError` subclasses → None; indexer 3-element ordering, empty-skip, and
  `LLMError` → None.
- `tests/test_index_manifest.py`: replaced `@patch("requests.post")` HTTP mocking
  with an injected `FakeEmbedClient` (batched), since the indexer no longer uses

- `tests/test_retrieval_coverage.py`: removed the obsolete `TestGetQueryEmbedding`
  class (it asserted Ollama-specific HTTP-status / response-parsing / numeric-
  validation behaviour that no longer exists); coverage now lives in the adapter file.
