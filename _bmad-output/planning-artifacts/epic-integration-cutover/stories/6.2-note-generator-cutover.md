## User story

As a chirp user running `chirp transcribe`, I want the note-generation step to route its LLM call through `chirpd` via `llm.client` instead of the Ollama HTTP API, so that note generation works without a separately-installed Ollama daemon — while my notes continue to follow the same XML structure, prompt template, and front-matter format.

## Context

`notes/note_generator.py` is the chirp module that turns a Whisper transcript into a structured `notes.md` file during the `chirp transcribe` flow. The current implementation:

- Holds the `SYSTEM_PROMPT` block (XML output contract) at module top (lines 20–136). **This stays put** — prompt assembly is owned by chirp per FR48.
- Builds the prompt in `_generate_structured_notes` (lines 329–353) by concatenating `SYSTEM_PROMPT`, a `title_instruction`, and the transcript.
- Sends the prompt to Ollama via `_call_ollama` (lines 355–401) using `requests.post(f"{ollama_url}/api/generate", ...)` with `stream=True`, accumulating tokens by iterating `response.iter_lines()`.
- Parses the streamed-then-joined response as XML via `_parse_xml_response` (lines 403–474). **This stays put** — parsing is owned by chirp.
- Writes the rendered note via `template_engine.render_meeting_section(...)` and front-matter helpers (lines 280–328). **These stay put.**

This story replaces **only** `_call_ollama` (and its `requests` / `json` / `ollama_url` / `num_predict` dependencies) with a call to `llm.client.chat(...)`. Everything else in this module is preserved verbatim.

The new call site uses non-streaming chat for note generation. Note generation is a one-shot batch task — there is no interactive UX where streaming tokens would be useful. The current Ollama path streams internally only to print a "↳ Generating... (N chunks)" progress message every 20 tokens; we preserve that progress UX by switching to `stream=True` on the client side and aggregating tokens locally before XML-parsing the joined result. The user-visible behavior (progress dots while generation proceeds, then the parsed note written to disk) is unchanged.

The Ollama path produces a single prompt string. The `chirp.llm` client takes a `messages: list[dict]` shape. We map the existing single-prompt usage to a one-message list: `[{"role": "user", "content": <full_prompt>}]`. The model's tokenizer applies its chat template at the daemon side per FR8. This is the simplest faithful mapping and preserves prompt content verbatim — the system prompt block remains part of the user message, exactly as today.

## Acceptance criteria

- **AC-1** `notes/note_generator.py` no longer imports `requests`. The `import requests` line at L8 is removed. The `import json` at L366 (inside `_call_ollama`) is also removed; it was only used to parse the Ollama NDJSON stream.
- **AC-2** The `_call_ollama(prompt: str) -> str` method (current L355–401) is replaced by a new method `_call_llm(prompt: str) -> str` with the same signature. The body uses `llm.client`:
  - Instantiate or reuse a module-level client: `from llm.client import client` (or whatever shape `llm.client` exposes per EPIC-CHIRPD-CORE story 3.4 — match the documented public API).
  - Call `client.chat(model="default", messages=[{"role": "user", "content": prompt}], options={"temperature": 0.3, "top_p": 0.9, "max_tokens": <num_predict>}, stream=True)`.
  - Iterate the returned stream, accumulating each delta's `.text` into a list. Every 20 deltas, render the same `[dim]  ↳ Generating... (N chunks)[/dim]` progress line on `self.console` that the current implementation produces (current L389–392).
  - After the stream completes, render the same `[dim]  ↳ Generated N chunks[/dim]` summary (current L398–399) on `self.console`.
  - Return `"".join(deltas).strip()`.
- **AC-3** `_generate_structured_notes` (current L329–353) is updated to call `self._call_llm(prompt)` instead of `self._call_ollama(prompt)`. No other lines in this method change. The prompt-construction step (system prompt + title instruction + transcript) is unchanged.

## Dev notes

- **Why non-streaming output to the user, but streaming under the hood.** Note generation produces a single artifact (one `notes.md` file). The user is not reading tokens one at a time — they are watching a progress indicator. Streaming on the client side gives us the same progress UX as today; the parsed output is the joined result regardless. We avoid `stream=False` because the daemon may have higher first-token latency in non-streaming mode and the existing `[dim]  ↳ Generating...[/dim]` feedback loop is part of the UX.
- **Why a single user-role message.** The current Ollama call uses `/api/generate` with a single `prompt` string. Mapping that to `messages=[{"role": "user", "content": prompt}]` is the most faithful translation. Splitting `SYSTEM_PROMPT` into a separate system message (`messages=[{"role":"system","content":SYSTEM_PROMPT}, {"role":"user","content":transcript_block}]`) could in principle be cleaner, but it would change how the model's chat template handles the prompt — and the regression corpus's "before" baseline was captured against the single-prompt path. Preserving single-user-message shape keeps the comparison in story 6.6 honest. If a future change wants to split system / user roles, it lives outside this epic.
- **Why pass `max_tokens` rather than `num_predict`.** The `chirp.llm` client's `options` dict uses the `max_tokens` field name per architecture §Wire Protocol Naming Conventions. The semantic is identical to Ollama's `num_predict` — both cap generation length. The settings field name (`num_predict`) stays in `config/settings.py` and is renamed (or removed) by EPIC-INIT-AND-MIGRATION as part of the broader settings sweep.
- **Why not catch `LLMError` explicitly.** The existing code catches the broad `except Exception` and treats any LLM-side failure as "structured-notes extraction failed; return `None`." Replacing the catch with a typed `except (LLMTransportError, LLMProtocolError, LLMModelError)` would add precision but change the recovery surface. Out of scope for this story. The typed-catch refactor is a candidate follow-up but is not required by the epic — the existing best-effort posture is preserved verbatim.
- **Why `model="default"`.** Per FR35 the literal `"default"` resolves to `default_chat` for chat ops. This keeps the call site decoupled from any specific alias name and lets the user swap models freely with `chirp models default <alias>` without re-touching the code.
- **Why no per-call timeout argument.** The daemon's streaming chat does not have an outer HTTP-style timeout — it streams as long as the model produces tokens (bounded by `max_tokens`). The current 300 s `requests` timeout disappears with no replacement. If a model hangs mid-generation, `client.cancel(req_id)` is the escape; for one-shot note generation this is acceptable because the user can Ctrl-C the chirp CLI process, which would close the connection and cause the daemon to treat the connection-close as a cancel.
- **Why the progress UX is preserved.** The `[dim]  ↳ Generating... ({N} chunks)[/dim]` rolling line is genuine UX: it tells the user that note generation is making progress on a long transcript. Removing it would feel like the CLI hung. Keeping it costs a few lines of code and one variable.
- **`make check` boundary.** This is one of three independent cutover stories (6.2 / 6.3 / 6.4). Land them in any order — each must leave `make check` and `make test` green on its own. If story 6.3 lands first, this story's tests should not depend on it. If this story lands first, tests in `tests/notes_chat/` continue to use whatever Ollama mocks they currently use.
- **Fixture migration deferred to 6.5.** This story's tests are allowed to mock either `client.chat` (the new path) at its call site inside `notes/note_generator.py`, **or** to mock `requests.post` (if any tests retain the old fixture shape during the transition). Story 6.5 retires the old fixture shape across the suite — do not preemptively refactor every test in this story.

## Dev Agent Record

### Contract verification (real `llm.client` vs. story assumptions)

Per the project pattern that cutover stories drift from the real CHIRPD-CORE
contract, the `llm.client` API was verified against source before coding. Several
story assumptions were stale; the story instructs to "match exactly what the
client module exposes," so the implementation follows reality (and the already-
shipped precedent in `notes_chat/prompting.py`):

- **Client shape.** No module-level `client` singleton and no `client.chat(...,
  stream=True)` returning deltas with `.text`. Reality: `LLMClient` is an async
  class with sync wrappers. Note generation is synchronous, so `_call_llm` uses
  `LLMClient().chat_stream_sync(messages, model="default", options=...)`, which
  yields **plain `str`** token deltas (not objects). This mirrors
  `notes_chat/prompting.py` exactly. The client is injectable via a new optional
  `NoteGenerator(..., llm_client=...)` param for testing.
- **Options / sampling (decision: max_tokens only).** Primary basis: the daemon
  splats `options` straight into `mlx_lm.stream_generate(**options)`, whose only
  honoured generation kwarg is `max_tokens` (verified: signature is
  `(model, tokenizer, prompt, max_tokens=256, **kwargs)`; sampling is configured
  via a `sampler` object, so `temperature`/`top_p` would be ignored or error in
  `generate_step`). Supporting: the migrated client path in
  `notes_chat/prompting.py` (L86/L104) passes no options. (Note: the `num_predict`
  options at `prompting.py` L381/L467 are the *legacy Ollama `requests.post`* path —
  still present pending story 6.4 — where `num_predict` is the correct Ollama key,
  not the client path. Adversarial review H-2 conflated the two; verified false.)
  Decision (confirmed with story owner): pass `options={"max_tokens":
  settings.models.num_predict}` to preserve the 4096-token budget (mlx default is
  256 — would truncate notes), and **omit** `temperature`/`top_p`. Deliberate
  deviation from AC-2/AC-9's literal `temperature=0.3`/`top_p=0.9`.
