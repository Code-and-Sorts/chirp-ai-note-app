# Story 6.4 — Cut over `notes_chat` interactive chat to `llm.client` streaming

- **Status:** Draft
- **Epic:** [EPIC-INTEGRATION-CUTOVER](../epic.md)
- **Depends on:** 6.1 (regression corpus committed); EPIC-CHIRPD-CORE 3.6 (`client.chat_stream` / `chat_stream_sync` streaming + `client.cancel` / `cancel_sync`); EPIC-CHIRPD-CORE 3.7 (one-shot `chirp ask` already routed through `llm.client` — establishes the pattern this story extends); EPIC-MODEL-REGISTRY (default chat model registered)
- **Blocks:** 6.5 (fixture migration), 6.6 (regression run)

> **Spec reconciliation (2026-06-10):** This story was originally drafted against an earlier shape of `notes_chat/prompting.py` and an assumed `client.chat(..., stream=True)` surface that returns `Delta` objects. It has been reconciled with the code as it actually exists on `main`:
> - The shipped client surface is `LLMClient.chat_stream(...)` → `ChatStream` (async iterator of **`str`** tokens) and `chat_stream_sync(...)` → `Iterator[str]`. There is **no `Delta` type**; tokens are plain strings. Cancellation is `cancel(target_id)` / `cancel_sync(target_id)`.
> - Request ids are minted by `llm.protocol.new_request_id()`, which already returns the `r-<12 hex>` format the ACs require — there is no need to hand-roll `secrets.token_hex(6)`.
> - `chat_stream` accepts a `request_id=` kwarg; **`chat_stream_sync` does not forward it yet** (see Task 0).
> - Story 3.7 already migrated the one-shot path: `prompting.generate_answer` now calls `chat_sync`, and a sibling `stream_answer_tokens` helper already wraps `chat_stream_sync`. That helper is the established pattern this story follows.
> - `enhanced_search_and_answer_stream` is **not** a single-LLM-call function. It is a router with three token-streaming branches plus a non-streaming classifier. The original AC-5 claim that `stream_llm_response` "has only one caller" is incorrect — it has three. The scope below reflects this.

## User story

As a chirp user running `chirp ask` without a question (entering interactive chat mode), I want each answer to stream token-by-token from `chirpd` via `llm.client` streaming instead of from the Ollama HTTP API, and I want Ctrl-C during an in-flight answer to cancel cleanly within 200 ms — while my interactive UX (the prompt-toolkit input, the `chirp ›` banner, the Rich Markdown rendering, the two-Ctrl-C-to-exit affordance, slash commands) is unchanged.

## Context

`chirp ask` has two modes:

- **One-shot:** `chirp ask "what did I decide last week?"` — runs once, prints once, exits. Cut over by EPIC-CHIRPD-CORE story 3.7 (`generate_answer` / `stream_answer_tokens`).
- **Interactive:** `chirp ask` (no argument) — enters a REPL via `notes_chat.interactive.InteractiveChatSession.start()`. The user types questions; each answer streams token-by-token into a Rich `Live` block; Ctrl-C in the middle of an answer cancels generation; two Ctrl-Cs in a row (within `interrupt_timeout = 2.0` seconds) exits the session.

This story handles the interactive mode. The key call sites:

- **`notes_chat/cli.py:ask`** — when `question is None`, it instantiates `InteractiveChatSession(config, markdown=markdown).start()` (cli.py L104–112). No code change here; the modification is downstream.
- **`notes_chat/interactive.py:handle_question`** (L171–284) — consumes `enhanced_search_and_answer_stream(self.config, question)` as a generator of events (`thinking`, `token`, `complete`, `error`) and renders them into a Rich `Live` block with a `Progress` spinner.
- **`notes_chat/prompting.py:enhanced_search_and_answer_stream`** (L494–670) — the helper that yields the events `handle_question` consumes.

**`enhanced_search_and_answer_stream` is a router, not a single call.** It does not do "retrieval → one LLM stream." It branches:

1. **Casual chat** (`is_simple_conversational`) → streams via `generate_conversational_response_stream` (L273) → `stream_llm_response`.
2. **Obvious search fast path** (`is_obvious_search`) → retrieval + cache check, then streams via `fast_search_and_answer_stream` (L281) → `stream_llm_response`.
3. **Orchestrated main path** → `orchestrate_search` (non-streaming Ollama classifier, L164) decides the plan, then retrieval + cache check, then streams via a **direct** `stream_llm_response(config, enhanced_prompt, ...)` call (L648).
   - Within this branch there are also conversational fallbacks (no-search-required, no-results) that stream via `generate_conversational_response_stream`.

`stream_llm_response` (defined L231) is the shared Ollama-streaming primitive behind all three branches; it has **three** in-tree callers (`generate_conversational_response_stream` L278, `fast_search_and_answer_stream` L291, and the direct call at L648). It cannot be deleted as "dead code" — every branch must be migrated for it to become unreferenced.

**Cancellation surface.** Today `InteractiveChatSession` handles Ctrl-C via prompt-toolkit's key binding (interactive.py L40–52). Inside `handle_question`, there is no explicit cancellation of an in-flight generator — Ctrl-C raises `KeyboardInterrupt`, which currently falls through to the outer `except (KeyboardInterrupt, RuntimeError, ValueError)` in `start()` (L148). The new behavior must:

1. Track the `req_id` of the in-flight streaming request.
2. On `KeyboardInterrupt` mid-stream, call `LLMClient().cancel_sync(req_id)`, close the generator, close the `Live` block cleanly, and return to the prompt.
3. Preserve the existing "two-press to exit" UX: a single Ctrl-C during an in-flight answer cancels that answer and returns to the prompt; two Ctrl-Cs (one mid-generation, one at the prompt within 2 s) still exits the session.

**Streaming token flush discipline.** Architecture §CLI Output Patterns mandates per-delta flushing for chat output. Today's Rich `Live` block calls `_update_live(target, text)` (interactive.py L192) for each token event — Rich's `Live` is its own buffered renderer with `refresh_per_second=10`. The new code preserves the Rich `Live` rendering and feeds it token `str`s as they arrive from `chat_stream_sync`.

**Retrieval semantics inside `enhanced_search_and_answer_stream`.** Unchanged. The function emits `{type: "thinking", message: "..."}` events while retrieval/orchestration run, then emits `{type: "token", content: "..."}` events as the LLM streams, then a final `{type: "complete", answer: "...", sources: [...], from_cache: bool}` event. We preserve this event shape and add one additive event (`request_started`) carrying the `req_id`.

## Scope decision — which branches migrate

All three token-streaming branches of `enhanced_search_and_answer_stream` are reachable from the user-facing interactive `ask` flow, so all three migrate to `llm.client` streaming:

- `generate_conversational_response_stream`, `fast_search_and_answer_stream`, and the direct main-path stream all route through `chat_stream_sync` and surface the same run-level `req_id`.
- **Stays on Ollama for this epic (per epic §4 call-site inventory):** `orchestrate_search` (non-streaming JSON classifier) and the non-streaming `generate_conversational_response`, `fast_search_and_answer`, `enhanced_search_and_answer`, and `validate_ollama_connection`. These are retired by EPIC-INIT-AND-MIGRATION when the Ollama dependency itself drops. Any remaining `requests.` references in `prompting.py` are itemized in the commit message as deferred (AC-5).

     from llm.exceptions import LLMError
     from llm.protocol import new_request_id

     try:
         for token in client.chat_stream_sync(
             messages,                     # build via build_chat_messages or CONVERSATIONAL_PROMPT.format(...)
             model="default",
             options={"temperature": 0, "top_p": 1},
             request_id=req_id,

             yield {"type": "token", "content": token}

         yield {"type": "error", "message": str(exc)}
         return
     yield {"type": "complete", "answer": "".join(accumulated), "sources": sources, "from_cache": False}

## Dev notes

- **Why a new `request_started` event.** The existing event schema (`thinking` / `token` / `complete` / `error`) didn't carry a request id because Ollama HTTP requests were cancelled by closing the socket. The client surface uses explicit `cancel(req_id)` cooperative cancellation, so the generator must surface the id. A new additive event keeps the four existing event shapes backwards-compatible (existing fixtures checking those types keep working).
- **There is no `Delta` object.** `ChatStream.__anext__` (client.py L107–118) already reads `EVENT_DELTA` wire frames and returns their `text` field as a `str`; `EVENT_DONE` stops iteration (and records `usage` on the stream). So `chat_stream_sync` yields `str` tokens directly — the generator maps each to `{type: "token", content: token}` with no unwrapping.
- **Why `req_id` comes from `new_request_id()`.** `llm.protocol.new_request_id()` returns `"r-" + secrets.token_hex(6)` (protocol.py L66–68) — exactly the `r-<12-hex>` format AC-4/AC-12 assert. Reuse it rather than minting ids ad hoc, and pass the same id into `chat_stream_sync(request_id=...)` so the value surfaced to the session is the one the daemon sees and can cancel.
- **Why `chat_stream_sync` needs the `request_id` kwarg (Task 0).** `chat_stream` accepts `request_id` but `chat_stream_sync` (the wrapper the sync generator uses) does not forward it today. Without threading it, the id surfaced in `request_started` would differ from the id the daemon assigned, and `cancel_sync` would target the wrong request. The fix is a one-line forward, consistent with the existing async signature.
- **Why the cancel goes through `cancel_sync`, not by closing the connection.** Per architecture §IPC Protocol → Connection lifecycle, the daemon treats connection-close as cancel, but `cancel` is the documented, bounded path (NFR-P4 ≤ 200 ms). Closing the connection could leave the Rich `Live` block half-rendered while the daemon cleans up; explicit `cancel_sync` returns control deterministically.
- **Why keep `enhanced_search_and_answer_stream` a sync generator.** `handle_question` is fully synchronous; converting to async would cascade into prompt-toolkit's session loop and Rich's `Live` rendering. Out of scope. `chat_stream_sync` already bridges the async client to a sync `Iterator[str]` (client.py L278–293 / `_sync_iter_async` L655–664), so the generator stays sync.
- **Why the Rich `Live` block is preserved.** Tokens flow into a markdown-rendered block that re-renders at up to 10 Hz. The `Live` rendering is indifferent to whether strings came from Ollama HTTP or `chirpd` — it consumes `str`s as they arrive. The cutover is invisible to it; only the producer changes.
- **Why the cancel path closes the generator.** `stream_gen.close()` raises `GeneratorExit` at the current `yield`, giving the rewritten branches' cleanup a chance to run deterministically rather than waiting on GC.
- **Cancel idempotency.** If the daemon already finished by the time `cancel` arrives, it is a no-op; `cancel`/`cancel_sync` are best-effort. The cancel test mocks the client, so daemon-side idempotency is academic here (asserted in EPIC-CHIRPD-CORE).
- **Why the two-press exit affordance is unaffected.** Prompt-toolkit's `c-c` handler (L40–52) only fires when the prompt is active. During an in-flight chat, `_session.prompt(...)` has already returned the question and `handle_question` is rendering, so a Ctrl-C there raises `KeyboardInterrupt` inside `handle_question` (what we now catch). The two paths share no state — `self.last_interrupt_time` is touched only by the prompt-toolkit handler, never by the cancel branch.
- **Per architecture §Streaming output for `chat`/`ask`:** explicit `sys.stdout.flush()` applies in non-Rich contexts (e.g. cli.py's `--no-markdown` one-shot path, L174–175). The Rich `Live` block handles its own flushing — no per-token flush is needed for the interactive path, which goes through `Live`.
