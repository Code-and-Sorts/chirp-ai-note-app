## User story

As a chirp user running `chirp ask` without a question (entering interactive chat mode), I want each answer to stream token-by-token from `chirpd` via `llm.client.chat(stream=True)` instead of from the Ollama HTTP API, and I want Ctrl-C during an in-flight answer to cancel cleanly within 200 ms — while my interactive UX (the prompt-toolkit input, the `chirp ›` banner, the Rich Markdown rendering, the two-Ctrl-C-to-exit affordance, slash commands) is unchanged.

## Context

`chirp ask` has two modes:

- **One-shot:** `chirp ask "what did I decide last week?"` — runs once, prints once, exits. Cut over by EPIC-CHIRPD-CORE story 3.7.
- **Interactive:** `chirp ask` (no argument) — enters a REPL via `notes_chat.interactive.InteractiveChatSession.start()`. The user types questions; each answer streams token-by-token into a Rich `Live` block; Ctrl-C in the middle of an answer cancels generation; two Ctrl-Cs in a row (within `interrupt_timeout = 2.0` seconds) exits the session.

This story handles the interactive mode. The key call sites:

- **`notes_chat/cli.py:ask`** at L98–103 — when `question is None`, it instantiates `InteractiveChatSession(config, markdown=markdown).start()`. No code change here; the modification is downstream.
- **`notes_chat/interactive.py:handle_question`** at L171–283 — consumes `enhanced_search_and_answer_stream(self.config, question)` as a generator of events (`thinking`, `token`, `complete`, `error`) and renders them into a `Live` block with a `Progress` spinner.
- **`notes_chat/prompting.py:enhanced_search_and_answer_stream`** — the helper that yields the events `handle_question` consumes. Today it does retrieval, builds the prompt, and streams Ollama tokens via `stream_llm_response` (~L252). This is the function we rewrite to use `client.chat(stream=True)`.

**Cancellation surface.** Today `InteractiveChatSession` handles Ctrl-C via prompt-toolkit's key binding (L40–52). Inside `handle_question`, there is no explicit cancellation of an in-flight generator — Ctrl-C raises `KeyboardInterrupt`, which falls through to the outer try/except. The new behavior must:

1. Track the `req_id` of the in-flight `client.chat` request.
2. On `KeyboardInterrupt` mid-stream, call `client.cancel(req_id)`, wait up to NFR-P4's 200 ms budget for the daemon to stop emitting deltas, close the `Live` block cleanly, and return to the prompt.
3. Preserve the existing "two-press to exit" UX: a single Ctrl-C during an in-flight answer cancels that answer and returns to the prompt; two Ctrl-Cs (one mid-generation, one at the prompt within 2 s) still exits the session.

**Streaming token flush discipline.** Architecture §CLI Output Patterns mandates per-delta flushing for chat output. Today's Rich `Live` block calls `_update_live(target, text)` for each token event — this is functionally equivalent (Rich's `Live` is its own buffered renderer with `refresh_per_second=10`). The new code preserves the Rich `Live` rendering and feeds it `Delta.text` strings as they arrive from `client.chat(stream=True)`.

**Retrieval semantics inside `enhanced_search_and_answer_stream`.** Unchanged. The function emits `{type: "thinking", message: "..."}` events while retrieval runs, then emits `{type: "token", content: "..."}` events as the LLM streams, then a final `{type: "complete", answer: "...", sources: [...], from_cache: bool}` event. We preserve this event shape — `interactive.py` is not modified except to plumb a `req_id` through for cancellation.

     ```python
     req_id = "r-" + secrets.token_hex(6)
     yield {"type": "request_started", "req_id": req_id}
     accumulated: list[str] = []
     for delta in client.chat(
         model="default",
         messages=[{"role": "user", "content": prompt}],
         options={"temperature": 0, "top_p": 1},
         stream=True,
         request_id=req_id,  # if client.chat accepts an explicit id; else read from result handle
     ):
         accumulated.append(delta.text)
         yield {"type": "token", "content": delta.text}
     yield {"type": "complete", "answer": "".join(accumulated), "sources": sources, "from_cache": False}
     ```

## Dev notes

- **Why a new `request_started` event.** The existing event schema (`thinking` / `token` / `complete` / `error`) didn't carry a request id because Ollama HTTP requests are cancelled by closing the HTTP socket — no id needed. The new client surface uses an explicit `client.cancel(req_id)` for cooperative cancellation. Surfacing the id from the generator to the session via a new event keeps the existing event shapes backwards-compatible (existing test fixtures that check for the four established event types continue to work; the new event is purely additive).
- **Why the cancel goes through `client.cancel`, not by closing the connection.** Per architecture §IPC Protocol → Connection lifecycle, the daemon does treat client connection-close as cancel, but `client.cancel` is the documented and bounded path (NFR-P4 ≤ 200 ms). Closing the connection from the interactive session might leave the Rich `Live` block half-rendered while the daemon takes longer to clean up; explicit `cancel` returns control to us deterministically.
- **Why pre-generate the request id (or read it from a handle).** The exact pattern depends on `client.chat`'s shipped signature in EPIC-CHIRPD-CORE story 3.6. If the client returns a streaming iterator that also has a `.request_id` attribute, use that — it is the cleaner pattern. If the client expects the caller to pass `request_id=` and only generates one if you don't, pre-generate it. The test (AC-12 first bullet) asserts the id format regardless of which path the implementation takes.
- **Why `temperature=0, top_p=1` here.** Matches the current Ollama call's deterministic settings (visible in `generate_answer` at L82–84). Deterministic answers are desirable for chat-over-notes — the question is "what did I say," not "compose me something creative." If the user wants creativity they can switch to a more general model and rephrase the question.
- **Why keep `enhanced_search_and_answer_stream` as a generator rather than an `async def`.** `notes_chat/interactive.py:handle_question` is fully synchronous; converting it to async would cascade into prompt-toolkit's session loop (async-capable but currently synchronous in this codebase) and into Rich's `Live` rendering. Out of scope. The generator-of-events shape is preserved; `client.chat(stream=True)` is invoked synchronously by the generator (the client's underlying socket I/O is hidden behind a sync iterator interface per the architecture's client surface). If the client surface only offers an async generator, wrap it in `asyncio.run(...)` inside `enhanced_search_and_answer_stream` — but check the client's API first; story 3.6's plan is to expose a sync iterator for ease of consumption by existing sync call sites.
- **Why the Rich `Live` block is preserved.** The existing UX feels good: tokens flow into a markdown-rendered block that grows and re-renders at up to 10 Hz. Switching to per-token `print` would lose the markdown rendering and the smooth append-and-rewrap behavior. The `Live` rendering is independent of the streaming source — it consumes strings as they arrive, indifferent to whether they came from Ollama HTTP or `chirpd` NDJSON. The cutover is invisible to it.
- **Why the cancel path closes the generator.** `stream_gen.close()` raises `GeneratorExit` inside the generator at its current `yield` point, which gives the rewritten `enhanced_search_and_answer_stream`'s `try/except LLMError` cleanup a chance to run (e.g., to release any retained state). Without this close, the generator would be garbage-collected eventually but not deterministically.
- **Cancel idempotency.** If the daemon has already completed generation by the time `client.cancel` reaches it, the cancel is a no-op. The client surface should swallow this silently (per architecture, `cancel` is best-effort and never raises on "no such request"). The cancel test mocks the client so this is academic — the daemon-side idempotency is asserted in EPIC-CHIRPD-CORE.
- **Why the two-press exit affordance is unaffected.** Prompt-toolkit's `c-c` handler at L40–52 only fires when the prompt is active (i.e., the user is typing or has hit Enter and is at the input). During an in-flight chat, the prompt is dormant — `_session.prompt(...)` has returned (it returned the user's question) and `handle_question` is rendering. So a Ctrl-C during streaming raises `KeyboardInterrupt` inside `handle_question` (which is what we now catch); a Ctrl-C *at the prompt* still flows through prompt-toolkit's handler. The two paths don't share state — `self.last_interrupt_time` is touched only by the prompt-toolkit handler, not by `handle_question`'s new cancel branch.
- **Stream-event shape under the hood.** The exact attribute names on the delta object (`.text` vs `.content` vs `.delta`) depend on EPIC-CHIRPD-CORE story 3.6's shipped API. Architecture § Wire Protocol Naming Conventions specifies `text` as the delta field name on the wire (`"event": "delta", "text": "..."`), so the client-side object is most likely `Delta(text=...)`. Confirm at implementation time.
- **Per architecture §Streaming output for `chat`/`ask`:** stdout flushing applies in non-Rich contexts. The Rich `Live` block handles its own flushing — we don't need an explicit `sys.stdout.flush()` per token when going through `Live`. The architecture rule is in force for any chat output that bypasses `Live`, which this story does not introduce.
