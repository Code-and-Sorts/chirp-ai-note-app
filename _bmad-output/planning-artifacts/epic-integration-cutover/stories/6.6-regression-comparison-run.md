# Story 6.6 — Run the regression comparison; verify ≥80% equal-or-better; close the epic

- **Status:** Draft
- **Epic:** [EPIC-INTEGRATION-CUTOVER](../epic.md)
- **Depends on:** 6.1 (regression corpus committed), 6.2 (note generation cutover), 6.3 (embedding cutover), 6.4 (interactive chat cutover), 6.5 (fixture migration); EPIC-MODEL-REGISTRY (`chirp models add` works so the operator can register the MLX chat model used for "after" generation)
- **Blocks:** EPIC-INIT-AND-MIGRATION's Ollama-removal story (the dependency can only come out of `pyproject.toml` once this story has confirmed the quality bar is met)

## Prerequisites

- Stories 6.1, 6.2, 6.3, 6.4, 6.5 all merged.
- A chat-role MLX model is registered via `chirp models add <mlx-chat-repo>` and is the `default_chat` per `chirp models list`.
- An embed-role MLX model is registered and is the `default_embed`.
- `chirpd` is running and reachable (`chirp daemon status` if EPIC-DAEMON-LIFECYCLE has landed — otherwise verify via a manual `chirp ask "ping"` or a `chirpd --help` sanity check).
- The chroma index has been rebuilt against the new embed model (`chirp index --force`) if a dimension mismatch was raised on the operator's machine after story 6.3's cutover. (This rebuild is operator hygiene, not part of this story's scope.)

## User story

As the chirp developer closing out the Ollama → MLX migration, I want to replay the 10-recording regression corpus through the new MLX-backed pipeline, generate `notes_after.md` for each recording, score the `before` / `after` pairs blindly per the PRD's validation methodology, and verify the new pipeline rates equal-or-better on ≥80% of the comparisons — so that the epic can close with documented evidence that note quality has not regressed.

## Context

PRD §Domain-Specific Requirements → Validation Methodology defines a four-step protocol:

1. Capture ≥10 representative recordings with their existing Ollama-generated notes — owned by story 6.1.
2. Generate notes for each recording via the new MLX pipeline using the same Whisper transcript and equivalent prompt templates — this story's first half.
3. Score `before` vs. `after` notes blindly against the criteria the prompts target (structure, faithfulness, completeness, brevity) — this story's second half.
4. Record the result against a ≥80% equal-or-better threshold — this story's deliverable.

PRD §Success Criteria → User Success names the same bar:

> **No regression in note quality.** On a held-out regression set of ≥10 representative recordings, blinded comparison of notes generated before vs. after migration shows MLX outputs rated equal-or-better on at least 80% of cases.

If the threshold is not met, the PRD §Scoping Risks → MLX quality regression mitigation says: "If quality fails, escalate model size (8-bit 7B or 4-bit 14B) before declaring the migration done." This story's AC-9 codifies that escalation path. The epic does not close until the threshold is met.

**This story produces three artifacts:**

1. `tests/regression/notes_quality/<slug>/notes_after.md` for each slug — the regenerated note from the new MLX pipeline.
2. A blinding manifest (sealed during scoring, opened after — see AC-5).
3. `tests/regression/notes_quality/results-<YYYY-MM-DD>.md` — the scored results, the aggregate percentage, the model used, and (if applicable) the escalation history.

**Blinding methodology.** Story 6.6 must be honest about the fact that one developer is both the implementer of the migration and the scorer of the comparison. The methodology cannot eliminate this conflict but can reduce it: shuffle the `before` / `after` ordering per pair, replace the slugs with anonymized labels (e.g., `pair-01-A` / `pair-01-B`), score each pair without consulting the mapping, and only open the mapping after all scoring is complete. The mapping is committed alongside the results so a future reader can verify the audit trail.

**Equivalent-class model.** The PRD insists the "after" model is in the same class as the "before" model — the comparison is not "7B vs. 70B." If the `notes_before.md` files were captured against a 7B-class Ollama model (`llama3.2:7b` or similar — recorded in `bucket_manifest.toml`'s `notes_before_model` field per story 6.1), the "after" model is also 7B-class (e.g., `mlx-community/gemma-4-4b-it-4bit`). If the bucket manifest shows a smaller "before" model (e.g., `llama3.2:3b`), use a 3B-class MLX model for the "after" run. The model alias used is recorded in the results file.

## Acceptance criteria

- **AC-1** For each slug in `tests/regression/notes_quality/`, a `notes_after.md` is committed alongside the existing `transcript.txt` and `notes_before.md`. The file is generated by routing the slug's `transcript.txt` through `notes/note_generator.NoteGenerator._generate_structured_notes` with the new MLX-backed `client.chat` call — i.e., the same code path that `chirp transcribe` exercises in production. **The generation must use the current `main` branch's code with stories 6.2–6.5 merged.** Reproducing the run with the same model alias and the same transcript must produce a structurally similar file (model outputs vary by seed, but the YAML front-matter + section structure must be present).
- **AC-2** Each `notes_after.md` has the same YAML front-matter shape as its corresponding `notes_before.md`:
  - `---` opening / closing delimiters present.
  - Front-matter keys present: `chirp_source: generated`, `readonly: true`, `generated_at: <ISO timestamp>`, `note_date: <YYYY-MM-DD>`. (`note_date` is set from the transcript's slug timestamp or the day of regeneration — for corpus replay, "day of regeneration" is acceptable since the original recording date is no longer in scope.)
  - Below the front-matter, the rendered note body contains the standard sections (`## Executive Summary`, `## Agenda`, `## Action Items`, `## Next Steps`, `## Decisions`, `## Open Questions`, `## Discussion Highlights`). Empty sections render as `None` or are omitted per the existing `template_engine.render_meeting_section` behavior. No raw XML bleed-through (no literal `<MEETING_NOTES>` text in the body).
- **AC-3** A new script `tests/regression/generate_notes_after.py` (or a `Makefile` target — implementer's choice) automates the regeneration. The script reads each slug's `transcript.txt`, calls into the production `NoteGenerator` with a `NoteRecord`-like shim, writes the output to `tests/regression/notes_quality/<slug>/notes_after.md`. Running the script twice is idempotent (overwrites the file each time). The script does **not** call into `~/Documents/chirp/` — it operates entirely under `tests/regression/notes_quality/`. The script is committed and reusable for future re-runs (e.g., after a model escalation per AC-9).
- **AC-4** A blinding manifest `tests/regression/notes_quality/.blinding-<YYYY-MM-DD>.toml` is generated alongside the results file. Schema:
  ```toml
  schema_version = 1
  generated_at = "2026-05-19T14:32:00Z"
  scorer = "Colby"
  notes_after_model = "gemma-4-4b-it-4bit"  # alias in models.toml
  notes_after_model_repo = "mlx-community/gemma-4-4b-it-4bit"  # for forward reproducibility

  [pairs.pair-01]
  slug = "team-standup-short"
  side_A = "before"  # which file (before/after) was shown as A
  side_B = "after"

  [pairs.pair-02]
  slug = "architecture-deep-dive-long"
  side_A = "after"
  side_B = "before"

  # ... one entry per slug, A/B sides shuffled per pair
  ```
  The shuffling is deterministic by `random.seed(<chosen-seed>)`; the seed is recorded in the manifest header. The mapping is **not committed until scoring is complete** — during scoring, the manifest is kept on disk locally but not staged.
- **AC-5** Scoring procedure executed and documented:
  - The scorer (the operator) opens each anonymized pair (`pair-01-A.md` and `pair-01-B.md`, rendered from the corresponding `notes_before.md` / `notes_after.md` per the blinding manifest) and reads them side by side.
  - For each pair, the scorer records a single judgement: `A_better`, `B_better`, or `equal`. The four criteria (structure, faithfulness, completeness, brevity) are considered holistically — the scorer does not produce four sub-scores; just one overall judgement per pair.
  - Judgements are written to `tests/regression/notes_quality/.scoring-<YYYY-MM-DD>.json` (or similar) **before** the blinding manifest is opened. This file is also not committed during scoring.
  - Once all pairs are scored, the blinding manifest and the scoring file are merged into the final results file (AC-6) and the intermediate files are committed alongside the results file as audit trail.
- **AC-6** `tests/regression/notes_quality/results-<YYYY-MM-DD>.md` is committed. It contains:
  - **Header:** date of run, operator name, `notes_after_model` alias and HF repo, `notes_before` model (cross-referenced from `bucket_manifest.toml`'s `notes_before_model` fields — ideally a single value across all entries; if mixed, list per-slug), random seed used for blinding.
  - **Per-pair table:** slug, before-model, side-A-was, side-B-was, scorer judgement, derived `after_equal_or_better` (a boolean: True if judgement was `B_better` and side B was `after`, OR `A_better` and side A was `after`, OR `equal`).
  - **Aggregate:** count of pairs, count of `after_equal_or_better == True`, percentage, threshold (80%), pass/fail.
  - **Conclusion:** one paragraph. If pass, names the model alias and recommends closing the epic. If fail, names the escalation candidate (per AC-9) and indicates a re-run is required.
- **AC-7** The aggregate percentage (`after_equal_or_better / total`) is **≥ 80%** for the epic to close. The results file states the threshold and whether it was met.
- **AC-8** The blinding manifest, the raw scoring file, the generation script, and the results file are all committed. `git ls-files tests/regression/notes_quality/` after this story shows: `README.md`, `.gitignore`, `bucket_manifest.toml`, `generate_notes_after.py` (if implementer chose the script approach), each `<slug>/transcript.txt`, each `<slug>/notes_before.md`, each `<slug>/notes_after.md`, the `.blinding-<DATE>.toml`, the `.scoring-<DATE>.json`, and `results-<DATE>.md`.
- **AC-9** **Escalation path if AC-7 fails.** If the first run's percentage is < 80%, the story does **not** close. Instead:
  - Document the failure in `results-<YYYY-MM-DD>.md` (AC-6) with the per-pair scores and conclusion paragraph naming the next candidate model.
  - Choose an escalation candidate per the PRD's mitigation: 8-bit quantization of the same architecture (e.g., `mlx-community/Qwen2.5-7B-Instruct-8bit`), OR a 14B-class 4-bit model (e.g., `mlx-community/Qwen2.5-14B-Instruct-4bit`).
  - Register the new model: `chirp models add <new-repo>`. Set as default: `chirp models default <new-alias>`.
  - Re-run AC-3 to regenerate `notes_after.md` for every slug against the new model.
  - Re-run AC-4 + AC-5 with a **new random seed** for blinding (do not reuse the prior shuffle — that would let the scorer's memory of the previous run leak into the new judgement).
  - Produce a second results file `results-<NEW-DATE>.md` with the same shape, plus a "Previous run" header section referencing the earlier results file.
  - Repeat until the threshold is met or the operator decides the escalation path is exhausted and falls back to engineering follow-up (e.g., revisiting the prompt template, the chat-template handling, or the comparison methodology). The epic does **not** close on an exhausted-escalation-with-fail path — that is an explicit escalation to the broader project review, not a "ship it anyway."
- **AC-10** The final (passing) `results-<YYYY-MM-DD>.md` is referenced from the corpus README (`tests/regression/notes_quality/README.md`) — append a "Most recent regression run" link to that section. This makes the latest result discoverable without git-log spelunking.
- **AC-11** `make check` and `make test` pass after this story merges. The corpus inventory smoke test from story 6.1 (`tests/regression/test_corpus_inventory.py`) is extended to assert that every `<slug>/` subdirectory also contains a `notes_after.md` after this story merges (i.e., a new AC-6 added to the smoke test).
- **AC-12** Manual smoke: after the results file is committed, run `chirp transcribe` on one fresh out-of-corpus recording end-to-end. The resulting `~/Documents/chirp/<slug>/notes.md` is structurally identical (same front-matter shape, same sections) to the `notes_after.md` files produced under `tests/regression/notes_quality/`. This sanity-checks that the corpus replay used the same code path as production.

2. **Author the regeneration script.** `tests/regression/generate_notes_after.py`:
   - For each subdirectory in `tests/regression/notes_quality/`:
     - Read `transcript.txt`.
     - Construct a `NoteRecord` shim with the transcript content available. Reuse `notes/note_generator.NoteGenerator._generate_structured_notes(transcript_text, provided_title=None)` for the LLM call.
     - Render the result via the same `template_engine` and `_apply_front_matter` helpers that production uses (`NoteGenerator._format_generated_note`).
     - Write to `tests/regression/notes_quality/<slug>/notes_after.md`.
   - Print one line per slug as it runs ("✓ <slug>" / "✗ <slug>: <error>").
   - Idempotent: overwrites `notes_after.md` if it exists.
   - Does not touch `~/Documents/chirp/` or `~/Library/Application Support/chirp/`.

3. **Generate `notes_after.md` for every slug.** Run the script. Confirm each subdirectory now has all three files. Inspect three random `notes_after.md` files manually for structural sanity (front-matter present, sections present, no XML-tag bleed).

4. **Author the blinding manifest.** Pick a random seed (e.g., `int(time.time())`). For each slug, `random.choice([("before", "after"), ("after", "before")])` decides which file is side A vs side B. Write the resulting mapping into `.blinding-<DATE>.toml` per AC-4's schema. **Do not stage this file yet.**

5. **Prepare anonymized pair files.** For each slug, create two temp files (e.g., under `/tmp/regression-scoring/`):
   - `pair-NN-A.md` — content of either `notes_before.md` or `notes_after.md`, per the blinding mapping.
   - `pair-NN-B.md` — the other one.
   No metadata in the filenames betrays which is which. The scorer opens these for reading.

6. **Score each pair.** For each pair NN:
   - Read both `pair-NN-A.md` and `pair-NN-B.md` side by side.
   - Compare against the four criteria the prompt targets: structure (does the YAML + section layout work?), faithfulness (do statements reflect the transcript verbatim, with no fabricated claims?), completeness (are action items, decisions, and open questions captured?), brevity (does the note avoid restating the transcript verbatim?).
   - Record one of `A_better`, `B_better`, `equal` in `.scoring-<DATE>.json`.
   - Do not open the blinding manifest during scoring.
   - Pace the scoring: at least 5 minutes per pair, with a break between groups of three pairs, to reduce judgement drift.

7. **Compute the result.** Open the blinding manifest. For each pair, derive `after_equal_or_better` per AC-6's rule. Compute the aggregate percentage. Compare to the 80% threshold.

8. **Author the results file.** Per AC-6's schema. Include the per-pair table, the aggregate stats, and the conclusion paragraph. If pass: name the model and recommend closing the epic. If fail: name the escalation candidate per AC-9 and indicate a re-run is required.

9. **If the threshold is met:** commit all artifacts per AC-8 (the blinding manifest, the scoring file, the regeneration script, the results file, and every `notes_after.md`). Update the corpus README (AC-10) to link the results file. Extend the smoke test in `tests/regression/test_corpus_inventory.py` to require `notes_after.md` per slug. Run `make test`. Open the PR.

10. **If the threshold is not met:** follow AC-9's escalation procedure. Document the failure, register the next model, re-run from task 3 with a fresh blinding seed. Repeat until pass or escalation exhaustion. Do not merge a failing run as final.

## Dev notes

- **Why blind the comparison even though the scorer wrote the migration.** The PRD insists on blinding because note quality is qualitative and one developer's "I expect the new pipeline to win" prior is a real source of bias. Anonymizing labels and shuffling sides per pair reduces (but does not eliminate) the bias. Documenting the seed and committing the blinding manifest makes the audit trail visible to anyone reading the repo later.
- **Why "equal" counts as a pass.** "Equal or better" is the PRD's threshold language. A pure parity outcome (50% A-wins / 50% B-wins) is operationally fine for a migration: we are not asking "is the new model better than Ollama," we are asking "is it not worse." The 80% threshold gives margin so a small absolute regression (a few pairs where Ollama clearly wins) is still acceptable.
- **Why holistic judgement, not four sub-scores.** Sub-scoring is more rigorous but slower and harder to do honestly when one person scores all pairs. The four criteria (structure, faithfulness, completeness, brevity) are reminders to the scorer, not separate gradings. If a pair is clearly better on three criteria and clearly worse on one, the scorer integrates and records one judgement; the results file's conclusion paragraph can note specific patterns ("Qwen2.5 is consistently more concise; Llama is consistently more faithful to verbatim quotes") if they emerge.
- **Why a new random seed per re-run after escalation.** If the scorer remembers "pair 7 had a longer side A in the first run," that knowledge leaks into the re-run. Reseeding shuffles side assignments and breaks the memory cue. The seed is committed each time, so the audit trail across multiple runs is reconstructable.
- **Why the regeneration script is committed.** Future maintenance — if a new MLX version changes generation quality, or if a future epic wants to spot-check the corpus against a different model — the script makes that one-line. Recreating it from memory each time is a foot-gun.
- **Why the smoke test gets extended (AC-11).** Story 6.1's smoke test asserts the corpus has `transcript.txt` and `notes_before.md` per slug. After this story, it should also assert `notes_after.md`. A future commit that deletes a `notes_after.md` (e.g., during a careless rebase) fails the smoke test loudly.
- **Why `chirp transcribe` is the equivalent code path, not a stripped-down replay.** The whole point of the regression run is to exercise the production path end-to-end. Using `_generate_structured_notes` directly with a `NoteRecord` shim is the closest we can get to "production minus the filesystem-mutation side effects" — the shim avoids touching `~/Documents/chirp/`, but every line of LLM-touching code is the production line.
- **`notes_after_model` and reproducibility.** Recording both the alias name (`gemma-4-4b-it-4bit`) and the HF repo (`mlx-community/gemma-4-4b-it-4bit`) in the blinding manifest means a future reader can re-pull the same model even if the operator's local alias name changes (`models.toml` is per-machine; the HF repo is the world's-canonical reference).
- **What if the model produces deterministic outputs?** MLX `mlx_lm.stream_generate` is stochastic at temperature > 0 by default. Story 6.2's call site uses `temperature=0.3, top_p=0.9` for note generation. Reproducing identical `notes_after.md` files across runs is not expected and not required — the comparison is between one new-pipeline output and one old-pipeline output, not between multiple new-pipeline outputs. If the operator wants to re-roll a specific pair (e.g., the model produced a clearly malformed XML response on first try), they can re-run the regeneration for that single slug and document the re-roll in the results file.
- **Operator workload.** Approximately: regeneration is a few minutes per slug (model load + generation; first slug is cold, subsequent are warm); blinding is one minute; pair preparation is 5 minutes; scoring is ~5 minutes per pair × 10 pairs = ~50 minutes; results-file authoring is ~30 minutes. Total ~2 hours for a clean first run. Add ~1.5 hours if an escalation is triggered.
- **What if `make check` fails because the `.blinding-*.toml` file isn't valid TOML or the `.scoring-*.json` isn't valid JSON?** Story 6.1's smoke test reads `bucket_manifest.toml` with `tomllib` and a corrupt sibling file would not break it. But: if the new artifacts use names that pytest discovers by pattern (e.g., starting with `test_`), pytest could try to import them. Avoid that by using leading-dot filenames (`.blinding-...`, `.scoring-...`) — pytest skips dot-prefixed files by default. The smoke test (AC-11) explicitly excludes those files from its directory iteration.
