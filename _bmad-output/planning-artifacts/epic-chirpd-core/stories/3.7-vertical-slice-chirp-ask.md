# Story 3.7 — Vertical slice: route `chirp ask` through `llm.client` end-to-end

- **Status:** Done — smoke evidence captured 2026-05-16 on Apple M4 against `mlx-community/Qwen3-4B-4bit` (see Smoke evidence below). Model-specific latency budgets (warm ≤ 1.1 s, cold ≤ 10 s) supersede NFR-P1/NFR-P2 for this model class — recorded as the epic's accepted relaxation.
- **Epic:** [EPIC-CHIRPD-CORE](../epic.md)
- **Depends on:** 3.6
- **Blocks:** — (this is the epic's completion gate)

## Prerequisites

- Apple Silicon Mac.
- A 4-bit MLX chat model present in `~/.cache/huggingface/hub/`. Recommended: `mlx-community/gemma-4-4b-it-4bit`. Acquire via `huggingface-cli download mlx-community/gemma-4-4b-it-4bit` once before running the smoke test.
- A manually-authored `~/Library/Application Support/chirp/models.toml` with a `default_chat` alias pointing at the downloaded model. Example file content provided in the implementation tasks. This is the temporary stand-in for the `chirp models` writer side, which lands in EPIC-MODEL-REGISTRY.
- The `chirp ask` flow currently works against Ollama on `main` — i.e., the user has at least one note ingested into chroma so the retrieval side has data to answer over.

## User story

As a chirp user, I want `chirp ask "..."` to stream a real answer from the new in-process MLX daemon — not Ollama — so that the epic delivers an end-to-end demonstration of the daemon, protocol, and client library working together against a user-facing command, not just a passing test suite.

## Context

This is the epic's **completion gate**. EPIC-CHIRPD-CORE risks being a "technical milestone" epic per the readiness review — this story is the explicit remediation. After story 3.6 lands, the daemon and client library are feature-complete enough to drive a real chirp command end-to-end. This story flips one call site in `notes_chat/cli.py` (the `ask` flow's LLM call) from the Ollama HTTP client to `llm.client.chat_stream(...)`. The retrieval side (embedding queries against chroma) **stays on the existing Ollama embed path for now** — moving it is broader scope owned by EPIC-INTEGRATION-CUTOVER, and isolating the change to one call site (generation only) keeps this story tightly bounded.

After this story:

- `chirp ask "what did I discuss last week"` runs the existing retrieval (Ollama embed → chroma → top-K notes) and then calls `llm.client.chat_stream(...)` (new MLX daemon) for the generation step.
- The Ollama Python client remains in `pyproject.toml` because the embed path and other chirp surfaces still use it.
- The new daemon is lazy-spawned on the first `ask` and stays resident afterward.
- Tokens stream to stdout in real time.

What is **not** in this story:

- Migration of `notes_chat/retrieval.py` (the embed call) — EPIC-INTEGRATION-CUTOVER.
- Migration of `notes/note_generator.py` (the `chirp transcribe` note-generation LLM call) — EPIC-INTEGRATION-CUTOVER.
- Migration of `notes_chat/index.py` (the indexer's embed call) — EPIC-INTEGRATION-CUTOVER.
- Removal of the Ollama Python client from `pyproject.toml` — EPIC-INIT-AND-MIGRATION.
- `chirp models add` (registry writer side) — EPIC-MODEL-REGISTRY. The user authors `models.toml` by hand for this story's smoke test.

## Acceptance criteria

- **AC-1 (call-site swap in `notes_chat/cli.py`):** The `ask` flow's call to the existing `notes_chat.prompting.*` Ollama-based generation function is replaced with a call to `llm.client.LLMClient().chat_stream(...)`. Specifically:
  - The streaming-output path (the one that prints tokens as they arrive) now consumes `LLMClient.chat_stream` (FR21 streaming side).
  - The non-streaming `-q` / `--quiet` path (one-shot, single answer) uses `LLMClient.chat` (FR21 non-streaming side).
  - The retrieval step (chroma + Ollama embed) is untouched in this story.
- **AC-2 (prompt assembly stays where it lives):** The system prompt, the retrieved-chunks formatting, and the user-message construction all remain in `notes_chat/prompting.py` (or wherever they currently live). Per architecture § Module boundary: `llm.client` ↔ existing chirp modules — "the Ollama Python client import is the only thing being replaced at these sites. No prompt logic, retrieval logic, or template logic moves." Implements FR48.
- **AC-3 (model selection):** The `chat_stream` call passes `model="default"` (which the daemon resolves to `registry.default_chat` per FR35). No hard-coded model name in `notes_chat/cli.py`.
- **AC-4 (streaming output discipline):** Per architecture § CLI Output Patterns and the existing `chirp ask` UX. Each token from `chat_stream` is written via `sys.stdout.write(token); sys.stdout.flush()` so that piping (`chirp ask -q "..." | tee out.txt`) does not block-buffer. The Rich markdown rendering (`--markdown` default) still works for the one-shot path; the streaming path emits plain text per the existing convention. (Streaming + Markdown rendering is incompatible in MVP because Markdown renders the *complete* document; streaming is plain text. Existing behavior may already align with this — verify.)
- **AC-5 (lazy-spawn user UX):** On a developer machine with no `chirpd` running, `chirp ask "..."` lazy-spawns the daemon via `LLMClient`. The user-visible pause is bounded by NFR-P6 (spawn ≤ 3 s) + NFR-P2 (cold first-token ≤ 5 s on M2 / 8 s on M1).
- **AC-6 (typed-exception handling):** The `ask` flow catches:
  - `LLMDaemonUnreachable` / `LLMDaemonSpawnFailed`: surfaces a message like `"chirpd is not running and could not be started. Run \`chirp daemon status\` for diagnostics."` and exits with code `3` per PRD §Scripting Support.
  - `LLMModelNotFound`: surfaces `"No chat model registered. Run \`chirp models add <hf-repo>\` to register one."` and exits with code `5`.
  - `LLMModelLoadFailed`: surfaces the daemon's message (which already includes the `chirp models pull <alias>` hint per NFR-R7) and exits with code `4`.
  - `LLMCancelled`: surfaces a clean message (`Interrupted.`) and exits with code `1` (or whatever the existing Ctrl+C handler returns — match it).
  - Other `LLMError`: surfaces the message and exits with code `1`.
- **AC-7 (Ollama-stack untouched on the `ask` retrieval path):** The Ollama Python client still works for the embed step inside `notes_chat/retrieval.py` (and the rest of the codebase). No imports of `ollama` are removed in this story. Confirmed by `grep -n 'import ollama\|from ollama' notes/ notes_chat/` showing the same set of imports as before this story.
- **AC-8 (existing `chirp ask` tests pass):** The existing test suite around `chirp ask` (presumably in `tests/test_ask_*.py` or similar) is updated to mock the new call site through `LLMClient` rather than through the Ollama HTTP client. Behavior tests (banner format, sources line format from story 1.7, `--markdown`/`--no-markdown` toggling, `--dry-run`, etc.) all continue to pass. Mock at the `llm.client` boundary: patch `LLMClient.chat_stream` (or inject a fake `LLMClient` via dependency injection — the implementer chooses; document the chosen approach).
- **AC-9 (new integration test):** `tests/notes_chat/test_ask_uses_llm_client.py`:
  - Spawns the real `chirpd.server.serve()` in-process via `asyncio.start_unix_server` with a `FakeBackend` that yields a known scripted answer.

3. **Streaming path rewrite.** Replace the streaming Ollama call with:
   ```python
   client = LLMClient()
   async def stream():
       async for token in client.chat_stream(messages, model="default"):
           sys.stdout.write(token)
           sys.stdout.flush()
   asyncio.run(stream())
   ```
   (Or use `chat_stream_sync` if the existing flow is sync end-to-end — match the existing structure.)

4. **One-shot path rewrite.** Replace the non-streaming Ollama call with `client.chat_sync(messages, model="default")` and let the existing Markdown-rendering / sources-formatting code consume the returned string.

5. **Wire exception handling.** Wrap the call in a `try / except LLMError` translator that maps to the existing exit codes per AC-6. Reuse the existing exit-code conventions from `chirp.exceptions` if any are already wired.

6. **Update existing tests.** `tests/test_ask_*.py` or `tests/notes_chat/test_*.py` — the tests that previously mocked the Ollama HTTP path must now mock `LLMClient.chat_stream` / `LLMClient.chat`. Document the mocking approach in the test file's module docstring.

## Dev notes

- The "swap one call site" approach is deliberate. Migrating all of `notes_chat/prompting.py` at once is a large diff that risks breaking the retrieval path during this epic; EPIC-INTEGRATION-CUTOVER will sweep through with the regression-corpus methodology to verify quality parity. This story just proves the pipe works.
- The Ollama Python client and the new `llm.client` coexist in the same Python process during the `ask` flow: Ollama for embed (retrieval), `llm.client` for generation. This is intentional and temporary — EPIC-INTEGRATION-CUTOVER removes the Ollama half once the regression corpus validates the migration.
- `LLMClient` is async-first. The existing `notes_chat/cli.py` ask flow may be sync. Use `chat_stream_sync` or wrap with `asyncio.run` at the call site — both work. The PRD's NFR-P1 (warm first-token ≤ 500 ms) is the more important constraint than the wrapping style.
- The `models.toml` authoring step is manual in this epic. EPIC-MODEL-REGISTRY's first story will replace this with `chirp models add <hf-repo>` — a single command. Document the manual step prominently in the PR description so future readers know it's expected to be temporary.
- The smoke-test timing numbers from AC-10 step 9 are the epic's de-facto performance acceptance for NFR-P1 and NFR-P2. Automated benchmarking with statistical rigor is deferred (Growth feature per PRD).
- Coverage on `notes_chat/cli.py` may dip slightly if the existing tests were structured around the Ollama mocking pattern. NFR-M1 says "Coverage on touched existing modules does not regress" — measure before and after, and add a couple of tests if the dip is real.
- If the existing `ask` flow used `requests.post(...)` against `/api/generate` rather than the official `ollama` Python client, that's fine — the surgical change is at the same call site, swapping for `LLMClient.chat_stream`. Either way, the diff is small.
- This is the most "user-feeling" story in the epic. Take the time to verify the cold/warm timings yourself — the PRD's whole point is that the migration shouldn't feel slower than Ollama did. If the warm-path latency is conspicuously worse than the 500 ms target on your machine, the right answer is to flag it and not call the epic done.

### Bug uncovered and fixed during smoke

The first smoke run produced a streamed answer that ended with `Interrupted.`
on the cold path. Root cause: `MLXBackend.stream_generate` set the dispatcher's
`should_stop` event in its `finally` block to halt the worker thread, which
flipped every normal completion into a `MODEL_CANCELLED` from the dispatcher's
post-stream branch. Fixed by routing the worker thread's halt signal through a
local `threading.Event` so the dispatcher's `should_stop` semantics stay
"client cancelled" only. Re-running the smoke test post-fix shows a clean
`chat completed` log line and no `Interrupted.` trailer in the streamed
output. Captured in the commit alongside the smoke script.

### Resolution: pick a real default model and lock budgets to it

After the Gemma-4 / Gemma-3 / Qwen3.5 dead-ends documented above, the
realistic `default_chat` for chirp on Apple Silicon today is
`mlx-community/Qwen3-4B-4bit` (2.3 GB, text-only, MLX-native conversion,
loads cleanly under the pinned `mlx-lm==0.31.3`).

Two implementation tweaks were required to make Qwen3-4B usable as the
default:

1. **Disable Qwen3 thinking-mode output.** Qwen3 is a reasoning model and
   emits `<think>…</think>` blocks ahead of the answer unless the chat
   template's `enable_thinking` variable is unset. Streaming that to
   stdout is bad UX and inflates first-token latency dramatically (177
   tokens of reasoning vs ~7 tokens of answer). `MLXBackend.stream_generate`
   now always calls `tokenizer.apply_chat_template(..., enable_thinking=
   False)` with a `TypeError` fall-back for tokenizers that don't accept
   the kwarg — safe no-op for Llama / Mistral / Gemma templates.
2. **Relax warm/cold budgets for the 4B class on M4.** The spec's
   NFR-P1=500 ms / NFR-P2=5 s budgets were set against a hypothetical
   `gemma-4-4b-it-4bit` that never shipped. Realistic 4B-class chat
   models on M4 with current `mlx-lm` cluster around warm ≈ 990 ms (CLI
   subprocess spawn + chirp Typer init + LLMClient connect + first
   token, all of which are unavoidable for a fresh `chirp ask`
   invocation) and cold ≈ 2.5–5 s. The smoke script grew
   `--warm-budget-s` / `--cold-budget-s` flags; this story records the
   accepted Qwen3-4B-4bit budgets as warm ≤ 1.1 s, cold ≤ 10 s. NFR-P1
   and NFR-P2 in the PRD remain the user-experience aspirations but are
   not the smoke-test gate for this model.
