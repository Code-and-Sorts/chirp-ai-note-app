# Story 3.6 — Backend inference: `chat` (streaming), `embed`, `cancel` ops; chat-template handling; cancellation event plumbing

- **Status:** Draft
- **Epic:** [EPIC-CHIRPD-CORE](../epic.md)
- **Depends on:** 3.5
- **Blocks:** 3.7

## User story

As a chirp client, I want to send a `chat` request with a list of messages and read back a stream of token deltas terminated by a `done` event, send a batched `embed` request and read back one vector per input, and send a `cancel` for an in-flight chat that halts generation within 200 ms, so that the daemon can actually answer questions and feed the existing `chirp ask` flow.

## Context

This story makes the daemon actually do inference. It implements:

1. **`MLXBackend.stream_generate`** and **`MLXBackend.embed`** filled in (the load/unload halves landed in story 3.5).
2. **`chat` op handler** in `chirpd/dispatcher.py`: applies the model's chat template (FR8), runs `MLXBackend.stream_generate` in an `asyncio.to_thread`, streams `delta` events through an `asyncio.Queue` back to the connection's writer, terminates with `done` + token-usage metadata. Implements FR1, FR8, FR21.
3. **`embed` op handler**: batched embed against a pinned embed model, returns one vector per input in a single `done` event. Implements FR2, FR22.
4. **`cancel` op handler** + cancellation event plumbing: per-request `should_stop: asyncio.Event` checked by the inference thread per token; setting the event halts generation within 200 ms. Implements FR3, NFR-P4.
5. **Client-side streaming + non-streaming chat methods, batched embed method, cancel method** in `llm/client.py`.

After this story, the daemon is fully featured. The next story (3.7) wires it into `chirp ask`.

## Acceptance criteria

### Backend inference (`chirpd/backend.py`)

- **AC-1 (`MLXBackend.stream_generate`):** Signature per architecture § Testing Patterns:
  ```python
  async def stream_generate(
      self,
      handle: Any,                        # the (model, tokenizer) tuple from load()
      messages: list[dict],
      options: dict,
      should_stop: asyncio.Event,
  ) -> AsyncIterator[str]:
  ```
  - Applies the model's chat template: `tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)` to produce the prompt string. FR8.
  - Wraps `mlx_lm.stream_generate(model, tokenizer, prompt, **options)` in `asyncio.to_thread` so it doesn't block the event loop. Architecture § Async Patterns.
  - Cancellation: passes a callback (or per-token check) into `mlx_lm.stream_generate` that consults `should_stop.is_set()` between tokens. On set, exits cleanly. The exact `mlx_lm` API for this depends on the pinned version — implementer chooses the right hook (`callback`, manual loop break, or generator-close). NFR-P4 budget: ≤ 200 ms.
  - Token streaming: the worker thread pushes tokens into an `asyncio.Queue` via `loop.call_soon_threadsafe(queue.put_nowait, token)`. The async iterator `await queue.get()`s and yields each token.
  - Token-usage tally: counts `prompt_tokens` (from the tokenized prompt length) and `completion_tokens` (from the number of streamed tokens). Available to the dispatcher after the iterator completes.
  - Implements FR1, FR3, FR8, FR21 (streaming side); NFR-P3 (≥ 30 tok/s throughput target validated in manual smoke).
- **AC-2 (`MLXBackend.embed`):**
  ```python
  async def embed(self, handle: Any, inputs: list[str]) -> list[list[float]]: ...
  ```
  - Wraps the model's embed call in `asyncio.to_thread`.
  - Returns one float vector per input string, preserving order.
  - Embed models are pinned (FR6 — already enforced by `DaemonState.schedule_idle_unload` in story 3.5).
  - Implements FR2, FR22.
- **AC-3 (`FakeBackend` extensions):**
  - `stream_generate` yields a scripted sequence of tokens injected via the constructor (e.g., `FakeBackend(chat_tokens=["hello", " world"])`). After each yield, it checks `should_stop.is_set()` — if set, exits early.
  - `embed` returns a deterministic per-input vector (e.g., `[len(s), hash(s) % 100]` padded out to the configured dim). Used to assert ordering and shape without caring about actual embedding semantics.
  - `FakeBackend(generation_delay_s=0.05)` lets tests script a slow generation so cancellation can be timed.

### Dispatcher ops

- **AC-4 (`chat` op handler):** Per FR1, FR8, FR21. Request envelope:
  ```json
  {
    "id": "r-...",
    "op": "chat",
    "model": "<alias-or-default>",
    "messages": [{"role": "user", "content": "..."}, ...],
    "options": {"temperature": 0.7, "max_tokens": 2048, ...},
    "keep_alive": null
  }
  ```
  - Resolves the model via `DaemonState.load(...)` (lazy-load if not resident; FR5).
  - Acquires `LoadedModel.lock` per architecture § Process & Concurrency Model → Request execution model (single in-flight chat per chat-model; concurrent same-model requests serialize via the lock; concurrent different-model embed proceeds in parallel).
  - Creates a `should_stop = asyncio.Event` and registers it in a per-request map keyed by `request_id` so the `cancel` op can find it.
  - Updates `model.last_used` and (re)schedules `schedule_idle_unload(model, keep_alive)` after the response completes.
  - Emits events in order: `{event: "loading"}` (if a load was triggered) → token deltas as `{event: "delta", text: "<token>"}` → `{event: "done", usage: {"prompt_tokens": N, "completion_tokens": M, "ms": <int>}}`.
  - On cancellation completion: emits `{event: "error", code: "MODEL_CANCELLED", message: "cancelled by client"}` instead of `done`. The client maps this to `LLMCancelled`.
  - On `mlx_lm` exception mid-stream: emits `{event: "error", code: "MODEL_GENERATION_FAILED", ...}`.
  - Schedules the post-completion idle-unload via `state.schedule_idle_unload(model, keep_alive)` (story 3.5 AC-7).
- **AC-5 (`embed` op handler):** Per FR2, FR22. Request:
  ```json
  {"id": "r-...", "op": "embed", "model": "<alias-or-default>", "inputs": ["text1", "text2", ...]}
  ```
  - Resolves the model (`role="embed"`); lazy-load if absent.
  - Acquires `LoadedModel.lock`.
  - Calls `backend.embed(handle, inputs)` in `asyncio.to_thread`.
  - Emits one `{event: "done", vectors: [[...], [...], ...]}`.
  - On exception: emits `error` with code `MODEL_GENERATION_FAILED`.
- **AC-6 (`cancel` op handler):** Per FR3, NFR-P4. Request:
  ```json
  {"id": "r-...", "op": "cancel", "target_id": "r-<id-of-in-flight-request>"}
  ```
  - Looks up the `should_stop` event for `target_id` in the per-request map.
  - If not found: emits `error` with code `MODEL_NOT_FOUND` (re-used for "request not in flight"; alternatively a new `REQUEST_NOT_FOUND` code — implementer chooses, story 3.2's error codes are extensible).
  - If found: calls `should_stop.set()` and emits `{event: "done"}` immediately.
  - The cancelled request's handler observes the event between tokens, halts, and emits its own `MODEL_CANCELLED` error event (per AC-4).
  - End-to-end cancellation time (from `cancel` arrival to `should_stop` observed and inference halted) ≤ 200 ms. NFR-P4.
- **AC-7 (per-request cancellation map):** `DaemonState` (or `Dispatcher`, implementer's choice — but document it) holds a `dict[str, asyncio.Event]` mapping request id → `should_stop`. Registered at chat-handler entry, cleared in a `finally` at exit. The `cancel` op consults this map.
- **AC-8 (connection-close = cancel):** Per architecture § IPC Protocol → Connection lifecycle. If the client closes the connection while a chat is streaming (broken pipe on the writer), the handler:
  1. Catches `BrokenPipeError` / `ConnectionResetError` on its next `await writer.drain()`.
  2. Sets `should_stop`.
  3. Cleans up and exits the handler. The cancellation map entry is cleared.
  Tested in `tests/chirpd/test_dispatcher_chat_ops.py`.

### Client extensions (`llm/client.py`)

- **AC-9 (`chat` streaming async):**
  ```python
  async def chat_stream(
      self,
      messages: list[dict],
      model: str = "default",
      options: dict | None = None,
      keep_alive: int | None = None,
  ) -> AsyncIterator[str]: ...
  ```
  - Sends the chat envelope; iterates events from `_request`.
  - For each `{event: "delta", text: "..."}`: yields `text`.
  - On `{event: "done", usage: {...}}`: completes the iterator. Optionally stashes `usage` on the iterator object so the caller can introspect afterward (`async for token in stream: ...; usage = stream.usage`).
  - On `{event: "error", code: "MODEL_CANCELLED"}`: raises `LLMCancelled`.
  - On other error: raises the typed exception via `CODE_TO_EXCEPTION`.
  - Implements FR21 (streaming side).
- **AC-10 (`chat` non-streaming convenience):**
  ```python
  async def chat(self, messages, model="default", options=None, keep_alive=None) -> str:
      tokens = [t async for t in self.chat_stream(messages, model, options, keep_alive)]
      return "".join(tokens)
  ```
  Implements FR21 (non-streaming side).
- **AC-11 (`embed` batched):**
  ```python
  async def embed(self, inputs: list[str], model: str = "default") -> list[list[float]]: ...
  ```
  - Single envelope, single `done` event, returns `event["vectors"]`.
  - Implements FR22.
- **AC-12 (`cancel`):**
  ```python
  async def cancel(self, target_id: str) -> None: ...
  ```
  - Opens a **separate** connection (one-request-per-connection rule still applies), sends `cancel`, reads `done`.
  - Implements FR3 from the client side.
- **AC-13 (sync wrappers):** `chat_sync`, `chat_stream_sync` (returns a regular generator that iterates over an `asyncio.run`-driven async iterator — implementer wraps with `asyncio.run_until_complete` carefully), `embed_sync`, `cancel_sync`.

## Implementation tasks

1. **`FakeBackend` first.** Implement `stream_generate` and `embed` in the existing `chirpd/backend.py`. Tests for cancellation, ordering, generation_delay, and the should_stop discipline drive the design.

2. **`Dispatcher.chat` handler.**
   - Resolve model via `DaemonState.load`.
   - Acquire `LoadedModel.lock`.
   - Create `should_stop = asyncio.Event()` and register in cancellation map.
   - Iterate `backend.stream_generate(...)` → write `delta` events.
   - On completion: write `done` with token-usage metadata.
   - Schedule idle-unload.
   - Cleanup in `finally` (release lock, clear cancellation map entry).
   - Connection-close branch: catch `BrokenPipeError`/`ConnectionResetError` and set `should_stop`.

3. **`Dispatcher.embed` handler.** Simpler — no streaming, no cancel registration in MVP (an embed batch is short).

4. **`Dispatcher.cancel` handler.** Look up the cancellation map; set the event; emit `done`.

5. **Cancellation map storage.** Add to `DaemonState`: `cancellation_events: dict[str, asyncio.Event] = field(default_factory=dict)` with `register(request_id, event)` and `clear(request_id)` helpers. Or hold it on `Dispatcher`. Document the choice.

6. **`MLXBackend.stream_generate`.**
   - Tokenizer chat template via `tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)`.
   - Spawn the inference in `asyncio.to_thread`. The worker thread pushes tokens into a queue via `loop.call_soon_threadsafe(queue.put_nowait, token)`.
   - The async wrapper iterates `queue.get()` and yields. Per-token check on `should_stop.is_set()` inside the worker (the actual hook point depends on the pinned `mlx_lm` version — `mlx_lm.stream_generate` typically supports a per-token callback or a generator interface).
   - Track token usage; expose via an attribute or return value the dispatcher can read after the iterator drains.

7. **`MLXBackend.embed`.** Straightforward `asyncio.to_thread` wrap of the model's embed call.

8. **`llm/client.py` extensions.** Implement `chat`, `chat_stream`, `embed`, `cancel`, and sync wrappers. Map `MODEL_CANCELLED` → `LLMCancelled`.

9. **Tests.** Per AC-14 and AC-15. The cancellation timing test in `test_cancel_halts_generation_within_200ms` is the trickiest — verify it on the developer machine multiple times to ensure it isn't flaky. If it is, widen the slack to 300 ms with a comment.

10. **Manual smoke against real MLX.** Per AC-16. Capture the timings and post in the PR.

11. **Run gates.** `make check`, `make test`.

## Dev notes

- **Cancellation timing budget.** NFR-P4 is 200 ms end-to-end. The 200 ms is "cancel arrival → inference halted." In test, we observe "cancel sent → daemon emits `MODEL_CANCELLED` error event." Wall-clock-measured at the client. The dominant cost is the inference loop's per-token check cadence; `mlx_lm.stream_generate` cycles fast enough that the budget is comfortable.
- **Chat template caching.** The tokenizer is part of the loaded model handle (architecture § Chat Template Handling). The chat template is part of the tokenizer. No separate cache needed — applying the template per request is cheap. If profiling shows it's hot, cache the templated prefix; not in MVP.
- **`keep_alive` semantics.** FR7 fully realized here: `null` = use default idle timer; `-1` = pin; `0` = unload immediately; `N > 0` = use `N` seconds for the next idle window. The dispatch handler hands `keep_alive` directly to `state.schedule_idle_unload`.
- **Per-model lock vs single-in-flight constraint.** Architecture § Process & Concurrency Model → Request execution model is unambiguous: one chat-in-flight per chat model. The lock serializes concurrent chats against the same model. Different-model concurrency is naturally allowed (different `LoadedModel.lock`s). Embed has no equivalent constraint — it doesn't acquire its lock for the duration; just for the load/unload bracketing.
- **Connection-close-as-cancel.** When the client disconnects mid-stream, the daemon's writer raises `BrokenPipeError` on its next `drain()`. The dispatcher must catch this and translate to `should_stop.set()`, then unwind. The pattern is in the `chat` handler's `try/except/finally`.
- **Streaming flush discipline.** Story 3.7 is responsible for the CLI-side `sys.stdout.write(token); sys.stdout.flush()` per architecture § CLI Output Patterns. This story just gets tokens to the client; the client method returns them via the async iterator with no buffering on its side.
- **Token-usage `ms` field.** Measure wall-clock from chat handler entry to last token via `time.perf_counter()`. Round to integer milliseconds. Useful for `chirp daemon status` later (EPIC-DAEMON-LIFECYCLE).
- **Privacy invariant (NFR-S5).** The dispatcher logs `req_id`, `op`, `model`, `duration_ms`, `tokens` — **not** `messages`, `prompt`, `delta_text`, or any user content. The structured logger's allow-list from story 3.3 enforces this passively; story 3.6 is the first story that handles user content, so it's the first story that has a real chance to violate the invariant. Code review check: grep the dispatcher's log calls for any reference to `messages`, `content`, `prompt`, or `text` and confirm they're absent.
