# Story 3.8 — Enable embed-model loading and pooled inference in `MLXBackend`

- **Status:** In Review — implemented on branch `feat/story-3.8-embed-model-load`; all ACs satisfied, integration test passes against real MLX (`mlx-community/bge-small-en-v1.5-bf16`)
- **Epic:** [EPIC-CHIRPD-CORE](../epic.md)
- **Depends on:** 3.6
- **Blocks:** EPIC-INTEGRATION-CUTOVER 6.3 (retrieval/index embedding cutover)
- **Remediates:** [`bug-chirpd-registry-reread-and-embed-load.md`](../../../implementation-artifacts/bug-chirpd-registry-reread-and-embed-load.md) Issue 1 — escaped defect in story 3.6

## User story

As a chirp client, I want to register an embedding model (e.g. a `bge`-class model) and have the daemon load it and return correct pooled sentence vectors from `embed`, so that the retrieval and indexing call sites can run their query/document embeddings through `chirpd` instead of Ollama.

## Context

Story 3.6 filled in `MLXBackend.stream_generate` and `MLXBackend.embed`, but `MLXBackend.load` (`chirpd/backend.py:49`) routes **every** role through `mlx_lm.load` (`chirpd/backend.py:82`). `mlx_lm.load` only constructs causal-LM architectures, so warming any embedding model fails before inference is ever reached:

```
$ chirp models add mlx-community/bge-small-en-v1.5-bf16
Warming bge-small-en-v1.5-bf16...
Error: Model registered but warm failed: mlx_lm.load failed for
'mlx-community/bge-small-en-v1.5-bf16': Model type bert not supported.
```

A second, latent problem hides behind the first: the embed inference path is also wrong. `MLXBackend.embed` (`chirpd/backend.py:170`) delegates to `_invoke_embed` (`chirpd/backend.py:189`), which calls `model.embed(token_ids)` or `model.embed_tokens(token_ids)`. On a transformer, `embed_tokens` is the **input-embedding lookup table** — it returns one vector *per token*, not a pooled sentence vector. Even if a bert model loaded, `embed` would return the wrong shape and semantics. Both halves were never exercised end-to-end: `MLXBackend.load`/`embed`/`_invoke_embed` are all marked `# pragma: no cover` and have no integration coverage.

This story makes the embed role actually work: branch `load` on role using an MLX-native embedding loader, and rework `embed` to produce correctly pooled, order-preserving sentence vectors. It does **not** touch the `chat` path (3.6) or any call site (those cut over in EPIC-INTEGRATION-CUTOVER 6.3).

### Why this is a separate story, not an inline bug-fix

The fix introduces a new runtime dependency and a new inference contract, and per the project's testing discipline (`feedback_unit_test_mocking.md`) the real-MLX layer is not unit-tested — it is validated by an opt-in `@slow @integration` test plus manual smoke against a real model. There is also no consumer of the daemon `embed` op in the shipped CLI yet (`client.embed` has zero production callers), and no `default_embed` model is locked. So the loader and its first real consumer (cutover 6.3) should be validated together: this story delivers the daemon-side capability; 6.3 proves it end-to-end against the retrieval/index pipeline with a registered embed model.

## Locked decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Embed models load via **`mlx-embeddings`** (`from mlx_embeddings import load, generate`), not `mlx_lm.load`. Added to `pyproject.toml` as an arm64/darwin-gated dependency, pinned like `mlx-lm`. | MLX-native (no PyTorch/`sentence-transformers`, preserving the daemon's lightweight footprint); supports the `bge`/`bert` family directly. `mlx_lm.load` structurally cannot build these architectures. |
| 2 | `MLXBackend.load` branches on `role`: `chat` → `mlx_lm.load` (unchanged); `embed` → `mlx_embeddings.load`. The returned handle keeps the same dict shape (`repo`, `role`, `local_path`, plus the model + processor/tokenizer the embed path needs). | Keeps `DaemonState`/dispatcher handle-agnostic; only the backend knows the loader difference. |
| 3 | `MLXBackend.embed` produces **pooled sentence vectors** via `mlx_embeddings.generate(model, processor, texts=inputs)` → `output.text_embeds`, one vector per input, insertion order preserved. The token-level `_invoke_embed` path is removed. | Correct embedding semantics. The prior `model.embed_tokens(...)` path returned per-token lookup vectors — wrong shape and wrong meaning. |
| 4 | Real-MLX `load`/`embed` paths stay excluded from unit coverage (`# pragma: no cover`); correctness is proven by one opt-in `@pytest.mark.slow @pytest.mark.integration` test against a small real embed model, plus manual smoke. | Consistent with story 3.6 AC-17 and `feedback_unit_test_mocking.md`. |
| 5 | End-to-end verification (a real query/document embedded through the full retrieval/index pipeline) is owned by **EPIC-INTEGRATION-CUTOVER 6.3**, which registers a `default_embed` model. This story's manual smoke is the daemon-in-isolation check. | Avoids verifying a loader with no consumer; the embed-model selection is a cutover concern. |

## Acceptance criteria

### Dependency (`pyproject.toml`)

- **AC-1:** `mlx-embeddings` is added to `dependencies` with the same platform gate as `mlx-lm` (`; sys_platform == 'darwin' and platform_machine == 'arm64'`) and a pinned version. `uv.lock` is regenerated. On non-arm64/non-darwin the dependency is absent and nothing imports it at module load time (the import stays lazy, inside `load`/`embed`, mirroring the existing `mlx_lm`/`huggingface_hub` lazy imports).

### Backend load (`chirpd/backend.py`)

- **AC-2 (`MLXBackend.load` branches on role):**
  - `role == "chat"`: unchanged — `snapshot_download(local_files_only=True)` then `mlx_lm.load(local_path)`; handle dict `{repo, role, local_path, model, tokenizer}`.
  - `role == "embed"`: `snapshot_download(local_files_only=True)` then `mlx_embeddings.load(local_path)`; handle dict `{repo, role, local_path, model, processor}` (key naming follows the `mlx_embeddings` return; if it returns `(model, tokenizer)`, store under `processor` for clarity and document it).
  - The `LocalEntryNotFoundError` → "run `chirp models pull`" mapping and the `LLMModelLoadFailed` wrapping (with `repo`/`role`/`local_path`/`exception_type` details) apply to **both** branches.
  - A `mlx_embeddings` `ImportError` raises `LLMModelLoadFailed` with the same "requires Apple Silicon dependencies" shape as the existing `mlx_lm`/`huggingface_hub` guards.

### Backend embed inference (`chirpd/backend.py`)

- **AC-3 (`MLXBackend.embed` pooled vectors):**
  - Calls `mlx_embeddings.generate(model, processor, texts=inputs)` inside `asyncio.to_thread`, reads the pooled `text_embeds`, and returns `list[list[float]]` — one vector per input, **insertion order preserved**.
  - Vector conversion reuses `_vector_to_floats` (handles `.tolist()` / iterable).
  - Empty `inputs` returns `[]` without calling the model.
  - `_invoke_embed` (the token-level lookup path) is deleted; any reference to `model.embed` / `model.embed_tokens` is gone.
  - On a `mlx_embeddings` exception: surfaces as `LLMGenerationFailed` (consistent with the dispatcher embed handler at `chirpd/dispatcher.py:469`).

### FakeBackend

- **AC-4:** `FakeBackend.embed` is unchanged (still returns deterministic `embed_dim`-length vectors, order-preserving). The dispatcher/embed unit tests under `tests/chirpd/test_dispatcher_embed_ops.py` continue to pass untouched — this story does not change the backend protocol surface.

### Tests

- **AC-5 (opt-in integration test):** `tests/chirpd/test_backend_embed_integration.py` marked `@pytest.mark.slow @pytest.mark.integration`, skipped unless the model is in the HF cache:
  - Loads a small real embed model (`mlx-community/bge-small-en-v1.5-bf16`) via `MLXBackend.load(repo, "embed")`.
  - Calls `embed(handle, ["the cat sat", "machine learning"])` and asserts: two vectors returned; both the same fixed dimensionality (the model's hidden size); order preserved (a repeated input yields an identical vector); a near-duplicate pair scores higher cosine similarity than an unrelated pair (sanity that pooling is real, not random).
  - Documented run command in the test module docstring; mirrors story 3.6's opt-in MLX test convention.
- **AC-6 (no unit-coverage regression):** `make test` passes. The real-MLX `load`/`embed` branches remain `# pragma: no cover`; coverage on the non-MLX code (FakeBackend, conversion helpers) does not regress. NFR-M1.

### Manual smoke (real MLX, arm64)

- **AC-7:** With `bge-small-en-v1.5-bf16` in the HF cache and registered:
  ```
  chirp models add mlx-community/bge-small-en-v1.5-bf16   # daemon up → warms without "bert not supported"
  ```
  then via `llm.client`:
  ```python
  import asyncio
  from llm.client import LLMClient
  async def main():
      vecs = await LLMClient().embed(["hello world", "hello world", "totally different"])
      assert len(vecs) == 3 and len(vecs[0]) == len(vecs[2])
      assert vecs[0] == vecs[1]            # order + determinism
  asyncio.run(main())
  ```
  Tail `~/Library/Logs/chirp/chirpd.log` and confirm an `op=embed` line with **no input text** (NFR-S5 redaction holds).

- **AC-8 (`make check` and `make test` pass).** Mypy clean.

## Implementation tasks

1. **Add the dependency.** `mlx-embeddings` in `pyproject.toml` `dependencies`, arm64/darwin-gated and pinned; `uv lock`.
2. **Branch `MLXBackend.load` on `role`.** Extract the shared `snapshot_download` + error-mapping prologue; fork only the loader call and the handle's model/tokenizer keys. Lazy-import `mlx_embeddings` inside the embed branch.
3. **Rework `MLXBackend.embed`.** Replace the `_invoke_embed` loop with a single `mlx_embeddings.generate(...).text_embeds` call in `asyncio.to_thread`; map to `list[list[float]]` via `_vector_to_floats`; handle empty input; delete `_invoke_embed`.
4. **Integration test.** `tests/chirpd/test_backend_embed_integration.py` per AC-5, cache-gated skip.
5. **Manual smoke** per AC-7; capture the log line (redacted) in the PR.
6. **Run gates.** `make check`, `make test`.

## Dev notes

- **`mlx_embeddings` API shape.** Verify the exact return of `mlx_embeddings.load()` and the attribute on `generate(...)` output against the pinned version at implementation time (`text_embeds` is the documented attribute, but pin-and-check — it is a pre-1.0 package). If the loader returns `(model, tokenizer)`, store the second element under the handle key the embed path reads; keep the key name consistent between `load` and `embed`.
- **No consumer yet.** `client.embed` has zero production callers today; the shipped `notes`/`search` still embed via the legacy Ollama path. This story is deliberately daemon-side only. Do not wire any call site here — that is EPIC-INTEGRATION-CUTOVER 6.3, which also locks the `default_embed` model and runs the full end-to-end check.
- **Privacy invariant (NFR-S5).** Same rule as 3.6: the embed handler logs `op`/`model`/`duration_ms`/vector count — never the input text. The dispatcher's existing embed log call (`chirpd/dispatcher.py:478`) already follows this; do not add input text to any log line.
- **Idle behavior unchanged.** Embed models remain pinned (no `idle_unload_task`) per story 3.5; this story does not touch the lifecycle scheduler.
- **Dependency footprint.** `mlx-embeddings` is pre-1.0; pin exactly (`==`) like `mlx-lm==0.31.3` so a transitive bump can't silently change embedding output. Renovate will surface upgrades as reviewable PRs.
