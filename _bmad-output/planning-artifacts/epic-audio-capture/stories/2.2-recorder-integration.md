# Story 2.2 — Recorder integration: route `audio_recorder` and `live_audio` through `AudioCapture`

- **Status:** Done
- **Epic:** [EPIC-AUDIO-CAPTURE](../epic.md)
- **Depends on:** 2.1
- **Blocks:** 2.3

## User story

As a Chirp user on macOS, I want `chirp record` (both the offline and live-dashboard variants) to capture system audio without my having to install BlackHole or set up an Audio MIDI multi-output device, so that the first time I run `chirp record` it just works after a single permission prompt.

## Context

Story 2.1 delivered the `audio_capture` module. This story rewires the two existing PyAudio capture call sites to consume `AudioCapture` frames instead. The on-disk contract — `~/Documents/chirp/<slug>/audio.wav` written as a 16-bit PCM WAV at 16 kHz, plus `meta.toml` with `mic` field — does not change. Downstream (`transcribe`, the live dashboard, the meeting monitor) is unaffected.

Two call sites change:

1. **`recorder/audio_recorder.py`** — `AudioRecorder.start_recording`. Today it opens a `pyaudio` stream against `device_manager.get_recommended_device()` and accumulates int16 frames into `self.frames`. After this story, it opens `AudioCapture()` and accumulates the mixed system + mic float32 frames, converting to int16 only at WAV-write time.
2. **`recorder/live_audio.py`** — `LiveAudioStream`. Today it opens a `pyaudio` stream and pushes `AudioFrame` chunks at a 32 ms cadence into a `queue.Queue` for the live dashboard / VAD / live transcriber. After this story, it consumes `AudioCapture.frames()` in a background thread, mixes the two sources sample-by-sample, re-windows into 32 ms `AudioFrame`s, and pushes the same `AudioFrame` shape into the same queue. The dashboard, VAD chunker, and live transcriber stay untouched.

Mixing for v1 is the simplest possible thing: a sample-aligned `np.add` with clipping to `[-1.0, 1.0]`, then conversion to int16 via `np.int16(samples * 32767)`. Stream alignment uses the per-frame `timestamp_us` from `audio_capture` — when the two iterators get out of sync by more than one frame's worth (32 ms), pad the lagging stream with silence rather than blocking. This is the same "lossy alignment" approach the BlackHole multi-output device used implicitly (the hardware did the mixing).

PyAudio is **not** removed in this story. `recorder/device_manager.py:list_devices()` still uses it for `chirp devices` enumeration. Story 2.3 will revisit whether `device_manager` can shrink further once BlackHole-specific code is gone.

## Acceptance criteria

- **AC-1** `recorder/audio_recorder.py:AudioRecorder.start_recording` no longer calls `pyaudio.PyAudio().open(...)`. Capture is driven by `with AudioCapture() as cap:` and a worker thread that pulls `cap.frames()` and appends mixed float32 frames to a buffer until `self.is_recording` flips false.
- **AC-2** The on-disk output is byte-for-byte compatible at the wave-file level: 16-bit signed little-endian PCM, 16 kHz, mono, written via the existing `wave` module call. Conversion is `np.clip(mixed, -1.0, 1.0) * 32767` cast to `int16`.
- **AC-3** `meta.toml`'s `mic` field is set from the `microphone=enabled device="…"` line in the helper's stderr diagnostics (parsed by `audio_capture` and exposed as `cap.mic_device_name: str | None`). If absent (mic disabled or parsing failed), fall back to `"default"` — the current behavior.
- **AC-4** `recorder/live_audio.py:LiveAudioStream.start()` no longer calls `pyaudio.PyAudio().open(...)`. A new background thread named `audio-capture-mixer` pulls from `cap.frames()`, mixes by source, re-windows into 32 ms frames at 16 kHz mono float32, converts the mono float32 to mono int16 (since downstream `live_dashboard` / `vad_chunker` / `live_transcriber` consume int16 today), and pushes `AudioFrame(data=int16_bytes, timestamp=<seconds since start>, duration=0.032, level=<peak>)` into `frame_queue`.
- **AC-5** The level callback (`level_callback` in `AudioRecorder.start_recording`, and the `level_queue` in `LiveAudioStream`) continues to receive a float in `[0.0, 1.0]` representing peak amplitude of the most recent mixed frame. Computed from the float32 buffer as `min(1.0, float(np.max(np.abs(mixed))))`.
- **AC-6** Pause / resume during live recording (the existing dashboard feature in `recorder/live_session.py`) continues to work. Implementation note: pausing flips an internal `paused` event; the mixer thread keeps draining `cap.frames()` (so the helper subprocess doesn't fill its stdout pipe and stall) but discards frames while paused.
- **AC-7** Stream alignment: the mixer holds two small ring buffers (one per source, ~8 frames each). On each loop iteration it consumes one frame from whichever source has the older head timestamp and aligns the pair by `timestamp_us`. If one source's buffer is empty for more than 100 ms (3+ frames), the mixer fills the gap with silence for that source rather than stalling.
- **AC-8** On a non-macOS host, importing `recorder.audio_recorder` or `recorder.live_audio` does **not** crash at import time. `AudioRecorder.start_recording` and `LiveAudioStream.start()` raise `RuntimeError("chirp record requires macOS 13 or later")` when invoked. Other commands (`notes`, `ask`, `search`, `about`) continue to import and run on Linux.
- **AC-9** `chirp record "smoke test 2.2"` on macOS produces `~/Documents/chirp/smoke-test-2-2-YYYY-MM-DD/audio.wav` containing both speech and any system audio playing during the recording. Verified manually by playing a YouTube video while speaking, then listening to the WAV.
- **AC-10** Live dashboard: `chirp record` interactive flow (no `--duration`) shows live VU level moving in response to speech, live transcript chunks appearing every few seconds, and pause/resume working. Stop with `q` → WAV is saved → smoke `chirp transcribe` produces non-empty `transcript.txt`.
- **AC-11** Tests:
  - `tests/test_audio_recorder.py` — update existing tests to mock `AudioCapture` instead of `pyaudio.PyAudio`. Add `test_start_recording_writes_int16_wav_at_16khz` that feeds 5 fake stereo float32 frames through a fake `AudioCapture`, asserts the resulting WAV has the right sample width / rate / frame count.
  - `tests/test_live_audio.py` — new file. Mock `AudioCapture`, feed paired (mic, system) frames with controlled timestamps, assert the mixer produces the expected number of `AudioFrame`s in the queue and that mid-stream gap on one source produces silence-padded mixed frames rather than blocking.
  - `tests/test_audio_recorder_mixer.py` — new file. Pure unit test for the alignment helper (`recorder/audio_mixer.py` extracted in implementation task 3): feed two streams with different timestamps, assert the pair-up logic, assert silence-padding on a stalled source.
- **AC-12** `uv run pytest` passes. `uv run ruff check .` reports no issues. `uv run mypy chirp config notes notes_chat recorder transcriber utils audio_capture` passes (or doesn't regress if it currently has known issues).
- **AC-13** No `import pyaudio` statement remains in `recorder/audio_recorder.py` or `recorder/live_audio.py`. `device_manager.py` keeps its PyAudio import.

## Implementation tasks

1. **Extract a small mixer helper.** Add `recorder/audio_mixer.py` with one class `StereoToMonoMixer` (rename if a better name surfaces during implementation):
   - `__init__(self, frame_ms: int = 32, sample_rate: int = 16000, gap_ms: int = 100)`
   - `feed(self, source: int, timestamp_us: int, samples: np.ndarray)` — push a frame from one source.
   - `drain(self) -> Iterator[tuple[int, np.ndarray]]` — yield `(timestamp_us, mixed_float32)` for every fully-paired output frame, padding with silence when one source has stalled past `gap_ms`.
   - Internal state: two `collections.deque[tuple[int, np.ndarray]]` capped at 8 each.
   - Pure: takes no I/O, no threads. Easy to unit-test.

2. **Rewire `recorder/audio_recorder.py`.**
   - Drop the `pyaudio.PyAudio()` initialization in `__init__` and `__del__`. The PyAudio instance for capture is gone.
   - In `start_recording`: replace the `self.audio.open(...)` block with `with AudioCapture() as cap:` + a worker thread (`audio-recorder-capture`) that pulls `cap.frames()`, feeds the `StereoToMonoMixer`, and appends drained mixed frames to `self.frames` (now `list[np.ndarray]` of float32 samples).
   - On `stop_recording` / KeyboardInterrupt: flip `self.is_recording = False`, join the worker, exit the `with` block (which `SIGTERM`s the helper).
   - In `_save_recording`: concat `self.frames` → `np.concatenate(...)` → clip → `(samples * 32767).astype(np.int16)` → `wave.writeframes(samples.tobytes())`. Drop the `_mixdown_channels` helper (no longer needed; mixer already produced mono).
   - Replace `_resolve_mic_name(device_index)` with reading `cap.mic_device_name` from the `AudioCapture` after `__enter__` returns. Drop the `device_manager.get_recommended_device()` call (no longer used here).
   - The `level_callback` still polls `self.current_level`; the worker updates it after each drained frame.

3. **Rewire `recorder/live_audio.py:LiveAudioStream`.**
   - Drop the PyAudio fields (`self._stream`, `self._audio`) and the rate-fallback loop in `start()` (no longer needed — `AudioCapture` is fixed at 16 kHz).
   - `start()` enters `AudioCapture()` and starts the `audio-capture-mixer` thread. The thread runs the same mixer as task 2 and converts each drained float32 frame to int16 bytes for the queue.
   - `stop()` sets `stop_event`, joins the mixer thread, exits the `AudioCapture` context.
   - `save_recording` already takes `self._frames` (raw bytes) and writes a WAV — keep it, but `self._frames` now collects the int16 bytes the mixer produced (so the live-saved WAV path is the same shape as before).
   - Drop the `debug_dir` separate-mono debug WAV path? Keep — it still works against the mixer output.

4. **Plumb `mic_device_name` from `audio_capture`.** In `audio_capture/__init__.py` (story 2.1 baseline), have the stderr drainer thread parse the `microphone=enabled device="…"` line and set `self.mic_device_name`. Expose as a public attribute. If the line never arrives (mic disabled / parsing failed), the attribute stays `None`.

5. **Non-macOS guard.** At the top of both `audio_recorder.start_recording` and `live_audio.LiveAudioStream.start`, add:
   ```python
   import sys
   if sys.platform != "darwin":
       raise RuntimeError("chirp record requires macOS 13 or later")
   ```
   (Don't gate the import — see AC-8.)

6. **Tests.**
   - Move existing `tests/test_audio_recorder.py` mocks from `pyaudio.PyAudio` to `audio_capture.AudioCapture`. The mock's `__enter__` returns an object whose `frames()` yields a fixed list of `(source, ts, np.ndarray)` tuples; this drives `start_recording` deterministically.
   - Add `tests/test_audio_recorder_mixer.py` exercising `StereoToMonoMixer` in isolation. Cover: paired alignment, gap-padding, queue capacity (oldest frame dropped when buffer full).
   - Add `tests/test_live_audio.py` mirroring the recorder tests for the live path.

7. **Smoke-test on real hardware.** Run end-to-end:
   - `uv run chirp record "smoke 2.2"` → speak for 10s with a YouTube video playing → stop → verify WAV plays back both sources.
   - `uv run chirp transcribe` → verify `transcript.txt` is non-empty and includes words from both speech and video.
   - Live dashboard variant: same recipe with the interactive flow; verify VU level, live chunks, pause/resume.

## Dev notes

- **Why convert to int16 inside the live path.** The downstream live consumers (`vad_chunker.py`, `live_transcriber.py`, `live_dashboard.py`) all assume int16 today. Converting at the mixer boundary keeps the diff localized to `recorder/`. A future story can push float32 deeper if it pays off (avoids one round-trip), but that's not this story.
- **Why a separate mixer thread instead of mixing in the dashboard.** The helper subprocess's stdout pipe will fill and block the Swift side if Python doesn't drain it fast enough. The mixer thread guarantees a steady drain even when the dashboard is busy redrawing or VAD is computing. The downstream queue (`frame_queue`) absorbs short stalls.
- **Why silence-pad rather than block on a stalled source.** ScreenCaptureKit emits frames only when there's audio to deliver; a silent system (no apps playing audio) produces no frames. Blocking the mixer waiting for a frame that will never arrive would freeze recording. Padding with silence is the same behavior the BlackHole multi-output device produced (a silent system feeding through BlackHole still made noise = silent samples).
- **Stop-recording latency.** Worst case is one helper-frame's worth of buffering (~256 ms for the mic at 4096 samples / 16 kHz). Acceptable; the existing PyAudio path had similar latency.
- **`device_manager.get_recommended_device()` becomes unused for capture** but stays for the (still useful) `chirp devices` enumeration. Story 2.3 decides whether to delete it; leaving it for now keeps story 2.2 a focused diff.
- **Mock strategy.** `AudioCapture` is a context manager + iterator, both trivially mockable. The mixer is pure. End-to-end record→transcribe verification stays manual / integration-marked because real audio hardware is involved. This matches the testing pattern story 1.4 used for `BatchProcessor`.
