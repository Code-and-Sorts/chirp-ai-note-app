# Story 2.1 — `audio_capture` module: Swift helper + Python wrapper + packaging

- **Status:** Done
- **Epic:** [EPIC-AUDIO-CAPTURE](../epic.md)
- **Sequencing:** blocks 2.2 and 2.3

## Prerequisites

- Xcode Command Line Tools installed (`xcode-select --install`); `swiftc --version` reports Swift 5.9 or newer.
- Apple-silicon Mac for the default build (Intel via `make ARCH=x86_64`).
- macOS 13.0+ at runtime (ScreenCaptureKit audio-only support is 13+).
- The user can grant screen-recording permission to an unsigned binary (UX varies across macOS 13 → 14 → 15; the helper ships unsigned in v1).

## User story

As a Chirp developer, I want a self-contained `audio_capture` module that bundles a Swift `capture_audio` helper, exposes a `with AudioCapture() as cap:` Python context manager, and yields tagged `(source, timestamp_us, np.ndarray)` PCM frames from system audio and microphone simultaneously, so that the rest of the codebase has a single, BlackHole-free way to read live audio on macOS.

## Context

This story builds the foundation. Nothing in the Chirp CLI consumes the new module yet — that's story 2.2's job. The deliverable here is a buildable, importable, testable `audio_capture` package whose contract matches the spec exactly:

```python
from audio_capture import AudioCapture
with AudioCapture() as cap:
    for source, timestamp_us, chunk in cap.frames():
        ...  # 1 = system audio, 2 = microphone; chunk is np.float32, 16 kHz mono
```

Layout:

```
audio_capture/
  __init__.py              # AudioCapture class
  build.py                 # python -m audio_capture.build → swiftc + bundle assembly
  swift/
    capture_audio.swift    # the Swift source
    Info.plist             # NSMicrophoneUsageDescription, NSScreenCaptureUsageDescription
    Makefile               # builds the .app bundle locally
  CaptureAudio.app/        # built artifact (gitignored; shipped as wheel package data)
    Contents/
      Info.plist
      MacOS/
        capture_audio
```

The Swift binary writes the framing protocol on stdout and parseable diagnostics on stderr. The Python wrapper launches it via `subprocess.Popen`, reads stderr in a background thread to surface permission errors, and parses stdout frames lazily as the consumer iterates.

## Acceptance criteria

- **AC-1** A new top-level Python package `audio_capture/` exists and is added to `[tool.hatch.build.targets.wheel]` packages in `pyproject.toml`. `numpy` is already a dep; no new Python deps.
- **AC-2** `audio_capture/swift/capture_audio.swift` implements the spec's two capture engines:
  - System audio via `SCStream` (audio-only configuration on macOS 13+: `capturesAudio = true`, `sampleRate = 16000`, `channelCount = 1`; **no dummy video filter** — `SCStreamConfiguration` is set up audio-only). `excludesCurrentProcessAudio` is **not** set (it would exclude the helper itself, which is semantically wrong — the goal is to capture the parent app/meeting audio, not the helper's own audio).
  - Microphone via `AVAudioEngine` input-node tap (4096-sample buffer, 16 kHz mono float32 tap format).
  - Both callbacks write to stdout through a single shared serial `DispatchQueue` to prevent interleaving.
- **AC-3** Wire format on stdout exactly matches the spec:
  ```
  [source: u8] [timestamp: u64 LE] [length: u32 LE] [pcm: bytes]
  ```
  `source = 0x01` for system audio, `0x02` for microphone. Length is the byte count of the float32 PCM payload that follows.

  **Timestamp clock unification (load-bearing for story 2.2 alignment).** Both sources derive timestamps from a single host-time microsecond clock with one shared anchor:
  1. At startup, **before** `SCStream.startCapture` and `AVAudioEngine.start`, capture `let anchorHostTime = mach_absolute_time()` and read `var timebase = mach_timebase_info_data_t(); mach_timebase_info(&timebase)`.
  2. For each frame, derive `host_time_at_emit` from the buffer's presentation timestamp (`CMSampleBuffer` → `mach_absolute_time` units; `AVAudioTime.hostTime` is already in those units).
  3. Compute `timestamp_us = (host_time_at_emit - anchorHostTime) * UInt64(timebase.number) / UInt64(timebase.denom) / 1000`.

  This guarantees: monotonic per source; a single common anchor across both sources; microseconds since the anchor. These are stable contracts consumed by story 2.2.
- **AC-4** Startup sequence on the Swift side:
  1. `signal(SIGPIPE, SIG_IGN)` before any I/O.
  2. Capture the timestamp anchor (`mach_absolute_time()` + `mach_timebase_info`) per AC-3 — must happen **before** any capture engine starts.
  3. `AVCaptureDevice.requestAccess(for: .audio)` — if the TCC dialog is up, emit `capture: awaiting_permission\n` to stderr first (this resets the Python-side startup timeout per AC-9). On denial, write `error: microphone_denied\n`, call `try? FileHandle.standardError.synchronize()`, and `exit(1)`.
  4. `SCShareableContent.excludingDesktopWindows(...)` — same pattern: emit `capture: awaiting_permission\n` if TCC is prompting; on failure write `error: screen_recording_denied\n`, synchronize stderr, `exit(1)`.
  5. Write the diagnostic lines to stderr in order. The **startup sentinel** that gates Python `__enter__` returning is the literal line `capture: started\n`. Subsequent diagnostic lines are informational only:
     ```
     capture: started
     capture: sample_rate=16000 channels=1 format=float32
     capture: system_audio=enabled
     capture: microphone=enabled device="<name>"
     ```
  6. Start both engines and begin streaming frames on stdout.
- **AC-5** Signal handling on the Swift side: `SIGTERM` and `SIGINT` both stop `SCStream` and `AVAudioEngine` cleanly, then `exit(0)`. After `signal(SIGPIPE, SIG_IGN)`, **every** `FileHandle.write` call (stdout frames and stderr diagnostics) is wrapped to detect `EPIPE`/`POSIXErrorCode.EPIPE` (or the `errno == EPIPE` equivalent on the underlying write) and trigger a graceful shutdown: stop both engines, flush stderr via `try? FileHandle.standardError.synchronize()`, `exit(0)`.
- **AC-6** `audio_capture/swift/Info.plist` declares `CFBundleIdentifier = com.codeandsorts.chirp.capture-audio`, `CFBundleExecutable = capture_audio`, `LSUIElement = true` (no Dock icon for the helper), `NSMicrophoneUsageDescription = "Chirp uses your microphone to transcribe what you say in meetings."`, `NSScreenCaptureUsageDescription = "Chirp captures system audio for transcription. No screen contents are recorded."`
- **AC-7** `audio_capture/swift/Makefile` has a `build` target that:
  1. Creates `CaptureAudio.app/Contents/MacOS/` if missing.
  2. Accepts `ARCH ?= arm64` and runs `swiftc capture_audio.swift -framework ScreenCaptureKit -framework CoreMedia -framework AVFoundation -target $(ARCH)-apple-macos13 -O -o CaptureAudio.app/Contents/MacOS/capture_audio`. Intel builds via `make ARCH=x86_64`.
  3. Copies `Info.plist` to `CaptureAudio.app/Contents/Info.plist`.
  4. Sets the executable bit on the helper binary (`chmod +x`) so the wheel preserves it (see AC-13).
  Also exposes a `clean` target that removes the `.app` bundle.
- **AC-8** `python -m audio_capture.build` is a thin Python wrapper around the Makefile that:
  - Runs `swiftc --version` first and parses the output; if `swiftc` is missing or the reported Swift version is below 5.9, prints `xcode command-line tools missing or out of date — run \`xcode-select --install\` (Swift 5.9+ required)` and exits 1.
  - Shells out to `make -C audio_capture/swift build` and surfaces non-zero exit codes. Forwards `ARCH` if set in the environment.
  - Prints the resulting binary path on success.
- **AC-9** `audio_capture/__init__.py` exports `AudioCapture` with the spec's signature. `__enter__`:
  1. Resolves the binary path via `importlib.resources.as_file(importlib.resources.files("audio_capture") / "CaptureAudio.app" / "Contents" / "MacOS" / "capture_audio")` (materializes a real filesystem path that survives the `with` block for the subprocess lifetime — required when the package is installed inside a zipped wheel).
  2. Launches `subprocess.Popen([binary_path], stdout=PIPE, stderr=PIPE, bufsize=0)`.
  3. Starts a daemon thread that drains stderr line-by-line into a `queue.Queue[str]`.
  4. Waits up to **5 seconds** for one of the gating stderr lines: the sentinel `capture: started` (success → return), an `error: …` line (raise — see below), or `capture: awaiting_permission` (reset the 5-second timeout once and keep waiting; the user is interacting with a TCC dialog).
  5. On timeout, raise `AudioCaptureStartTimeout(RuntimeError)` with the last few stderr lines included in the message.
  6. On `error: microphone_denied`, raise `PermissionError("Chirp needs microphone access. Open System Settings → Privacy & Security → Microphone and grant access to CaptureAudio.app, then try again.")`. On `error: screen_recording_denied`, the same with "Screen Recording".
- **AC-10** `__enter__` failure cleanup: any exception raised inside `__enter__` **after** `subprocess.Popen` has launched the helper (timeout, PermissionError, or anything else) must, before re-raising, call `proc.terminate()`, then `proc.wait(timeout=2.0)`, then `proc.kill()` if still alive, and join the stderr drain thread with `timeout=1.0`. The exception is re-raised only after the subprocess is reaped.
- **AC-11** `__exit__` sends `SIGTERM`, calls `proc.wait(timeout=5.0)`, then sends `SIGKILL` if still alive. Joins the stderr drain daemon thread with `timeout=1.0`. An `atexit` handler does the same as a safety net for callers who forget the context manager; the atexit body is wrapped in `try/except Exception: pass` to avoid shutdown tracebacks during interpreter teardown.
- **AC-12** `frames()` is an iterator that yields `(source: int, timestamp_us: int, audio: np.ndarray)` tuples until the subprocess exits cleanly (`returncode == 0`) or its stdout closes. `system_frames()` and `mic_frames()` are convenience iterators that filter by source and yield `(timestamp_us, audio)` only.

  **Crash semantics:** if the helper exits with a non-zero return code, `frames()` raises `AudioCaptureCrashed(RuntimeError)` whose message contains the last stderr lines captured by the drain thread.

  **Back-pressure semantics:** expected steady-state throughput is ~64 KB/s combined (16 kHz mono int16 system + 16 kHz mono int16 mic), well under the OS pipe buffer. There is **no in-process drop policy in 2.1**. The OS pipe applies back-pressure to the Swift side if the consumer (story 2.2) falls behind, slowing capture rather than dropping frames. Story 2.2's consumer is responsible for keeping up.
- **AC-13** Frame parser is a private `_read_frame()` that returns `None` on EOF or partial reads (treat partial as end-of-stream). Uses `struct.unpack('<Q', ...)` for the 8-byte timestamp and `struct.unpack('<I', ...)` for the 4-byte length. Audio is decoded via `np.frombuffer(data, dtype=np.float32)`.
- **AC-14** Binary path resolution uses `importlib.resources.as_file(importlib.resources.files("audio_capture") / "CaptureAudio.app" / "Contents" / "MacOS" / "capture_audio")` to materialize the path before `subprocess.Popen`. If the binary doesn't exist, raise `FileNotFoundError` with the message: `"capture_audio binary not found. Build it with: python -m audio_capture.build"`. The wheel must preserve the executable bit on the helper binary; a packaging test asserts `os.access(path, os.X_OK)` after install.
- **AC-15** Non-macOS import guard: `audio_capture/__init__.py`, on `import` (top of the module, before class definitions execute any platform calls), raises `RuntimeError("audio_capture requires macOS 13+")` when `sys.platform != "darwin"`. The wheel platform tag stays generic, but the import-time guard is mandatory so non-macOS hosts fail loudly and immediately. (Non-recording commands that never import `audio_capture` continue to work on Linux/Windows per the epic.)

## Dev notes

- **Why a `.app` bundle for a CLI helper.** macOS scopes microphone and screen-recording permissions per executable. A bare CLI binary is granted permissions to its parent terminal app (Terminal.app, iTerm, the IDE), which is both confusing and brittle. Wrapping `capture_audio` in a minimal `.app` with proper usage descriptions makes the prompt name "Chirp" (via `CFBundleName`) and ties the grant to the helper itself.
- **Why ScreenCaptureKit, not CoreAudio process taps.** macOS 14.4+ has a private `AudioHardwareCreateProcessAggregateDevice` API that captures specific apps without screen-recording permission. It is undocumented, App-Store-hostile, and breaks across point releases. Apple's first-party answer is ScreenCaptureKit; the spec accepts the screen-recording permission scope as the cost of stability.
- **Why a separate top-level package, not under `recorder/`.** The spec calls this a building block independent of any consumer. A future side project (e.g. a clipboard transcriber) should be able to depend on `audio_capture` without dragging in PyAudio, ChromaDB, Ollama, etc. Top-level placement keeps the contract clean.
- **Why bufsize=0 on Popen.** The default is line-buffered, which is wrong for binary framed stdin/stdout. The Swift side writes raw bytes; we read raw bytes; no newline assumption ever applies.
- **Why an `atexit` net.** A `with` block exits cleanly on exceptions, but a raw `KeyboardInterrupt` mid-iteration of `frames()` followed by a hard kill of the Python process can leave `capture_audio` running. The atexit handler is the safety belt; it's a no-op when `__exit__` already cleaned up.
- **What the timestamps are good for.** Two streams arrive on independent threads; their first-frame timestamps differ by a few hundred microseconds (engine warmup). Consumers that need to align (e.g. a future "speaker labels" feature) can use the timestamps to interleave or to detect a stall in one source. Story 2.2 will use them for the simplest possible offline mix; downstream features can do more.

## Handoff to story 2.2

Story 2.2 consumes this module. The following are stable contracts locked by 2.1:

- **Frame format and source tagging** (`[u8 source][u64 LE timestamp_us][u32 LE length][float32 PCM]`, `0x01` system / `0x02` mic) — a stable wire contract.
- **Timestamp guarantee:** monotonic per source; a single common `mach_absolute_time`-derived anchor across **both** sources captured before any engine starts; values are microseconds since that anchor (per AC-3). 2.2 can align system and mic streams using these timestamps directly.
- **Back-pressure policy:** OS-pipe-buffered, no in-process drop policy in 2.1. The 2.2 consumer **must keep up**; falling behind slows the helper rather than dropping frames.
- **Crash surfacing:** `frames()` raises `AudioCaptureCrashed` on non-zero helper exit, with the last stderr lines included. 2.2 can rely on this for error reporting.
