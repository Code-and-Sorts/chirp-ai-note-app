## User story

As a Chirp user on macOS, I want `chirp init` and `chirp devices` to surface the *real* gating dependency for the new ScreenCaptureKit capture path — Screen Recording permission for `CaptureAudio.app` — so first-run setup tells me exactly what to grant and where, instead of leaving me to guess after a failed `chirp record`.

## Dev notes

- **Why a `--check-permissions` Swift flag instead of a Python-side check.** `CGPreflightScreenCaptureAccess()` is a CoreGraphics call. Calling it from Python requires PyObjC plus ctypes shims that drift across macOS versions. The Swift binary already imports the right frameworks, and — more importantly — *it is the binary whose permission state we're asking about*. TCC tracks permission per code-signing identity; checking from `python` would query a different bundle. Adding ~30 lines of Swift to the existing helper is strictly smaller than the PyObjC bridging it would replace.
- **Why the sentinel-file workaround for screen-recording tri-state.** `CGPreflightScreenCaptureAccess()` returns `Bool`, conflating "denied" with "never asked." The clean alternatives are unappealing: private TCC APIs would risk App Store / future macOS rejection, and `SCShareableContent.current` is async, heavier (it actually inspects shareable content), and itself can trigger UI side effects on some macOS versions. The sentinel — a zero-byte file written the first time `runMain()` actually launches capture — captures exactly what the user means by "has macOS already asked me?" without private APIs or async dancing. Edge case to document in support: if the user manually deletes `~/Library/Application Support/Chirp/.permission-prompted`, a previously-denied state will be reported as `undetermined` until they next attempt `record`. That's an acceptable degradation — the next `record` will recreate the sentinel and re-flip the probe — and we're not adding code to defend against it.
- **Why the screen-recording permission check goes last in `verify()`.** Phase 1 is ordered cheapest-and-most-local first, flakiest-and-most-external last: brew/ffmpeg/ollama binary presence (file-existence checks) → model availability (talks to a local Ollama HTTP server) → screen-recording permission (shells out to a Swift binary that pokes TCC). When something flakes, the user sees the earlier, more diagnostic rows first; a Swift-probe blip doesn't obscure a missing `ffmpeg`. The table also reads naturally as tools → models → permissions.
- **Why non-Darwin returns a visible non-blocking row instead of dropping silently.** On Linux (CI, contributor laptops), an absent row is mysterious — was the check skipped? did it fail? Returning `installed=True, required=False, detail="not applicable on Linux"` keeps the row visible and explicit, makes the platform skip self-documenting, and never blocks Phase 2.
- **Why `undetermined` is non-blocking.** The first `chirp record` triggers the OS prompts; that's the right moment for the user to be asked. Blocking `chirp init` on a permission they haven't been prompted for yet is bad UX — they'd have nothing to grant. Phase 1 should report "will prompt on first record" and move on.
- **Why we don't auto-launch the capture binary from `init`.** Doing so would trigger the macOS permission prompt during `init`, which feels like a bait-and-switch (the user ran `init`, not `record`). Leaving the prompt for first-record is the principle of least surprise. The `--check-permissions` mode reads TCC state without triggering a prompt.
- **Why `chirp devices` survives.** It still answers a real diagnostic question — "which microphone is my system default?" — that the new capture path doesn't expose elsewhere (the helper always grabs the system default mic). PyAudio enumeration of input devices is the right tool for that.
- **Idempotency.** Story 1.5 introduced re-run behavior in `init`. A second `chirp init` on a healthy box must still emit `phase 2 · everything's already installed — skipping.` and skip to Phase 3. The new dispatch branch in `install_missing()` only fires when the binary is genuinely absent, so a healthy machine takes the no-op path.
- **Order of operations.** Land the Swift `--check-permissions` flag (task 1) and the Python helper (task 2) before touching `init_flow.py` and `cli.py`. That way the new code path can be exercised against a real binary before anything depends on it.
