# Story 2.3 — BlackHole removal: strip from init flow, devices command, tests, and docs

- **Status:** Draft
- **Epic:** [EPIC-AUDIO-CAPTURE](../epic.md)
- **Depends on:** 2.1, 2.2
- **Blocks:** —

## User story

As a Chirp user on a fresh macOS box, I want `chirp init` and `chirp devices` to make no mention of BlackHole, Audio MIDI Setup, or multi-output devices, and I want the README to advertise a single-permission-prompt setup, so that the first-run experience matches the new ScreenCaptureKit reality and there is no stale documentation pointing me at a driver I no longer need to install.

## Context

Stories 2.1 and 2.2 built and integrated the `audio_capture` module. The old BlackHole code path is now dead — recorder no longer reaches for it, init no longer needs to install it, the `devices` command no longer needs to detect it. This story is the cleanup pass: delete the dead code, replace it with the single screen-recording-permission verification check, and update the docs.

## Implementation tasks

1. **Add the `--check-permissions` flag to the Swift helper.**
   - In `audio_capture/swift/capture_audio.swift`, parse `CommandLine.arguments` early. If `--check-permissions` is present, call `CGPreflightScreenCaptureAccess()` and `AVCaptureDevice.authorizationStatus(for: .audio)`, print one line per permission (`permission: screen_recording=granted|denied|undetermined`, `permission: microphone=granted|denied|undetermined`), then `exit(0)` without starting either capture engine. No frames are emitted in this mode.
   - Rebuild: `python -m audio_capture.build`.
   - This keeps the permission probe out of Python (no PyObjC, no private API) and reuses the same `.app` bundle that handles authorization.

2. **Add `audio_capture.check_permissions() -> dict[str, str]`.** A small public helper next to `AudioCapture` that runs `subprocess.run([binary_path, "--check-permissions"], capture_output=True, text=True, timeout=3)`, parses the two `permission:` lines, and returns `{"screen_recording": "granted|denied|undetermined", "microphone": "..."}`. Raises `FileNotFoundError` with the build instruction if the binary is absent (reuse the message from story 2.1's AC-13).

3. **Rewrite `chirp/init_flow.py:_blackhole_installed` → `_screen_recording_permission`.**

## Dev notes

- **Why a `--check-permissions` flag instead of a separate Python check.** macOS exposes screen-recording authorization state through `CGPreflightScreenCaptureAccess()` (a CoreGraphics call). Calling it from Python requires PyObjC + ctypes incantations that are fragile across macOS versions. The Swift binary already has the right framework imports and is the correct identity for the permission grant — adding a 30-line `--check-permissions` mode is much smaller than the PyObjC bridging it replaces. Same reasoning the spec used for the capture path itself.
- **Why `undetermined` is non-blocking.** The first `chirp record` will trigger the OS prompt; that's the right time for the user to be asked. Blocking `chirp init` on a permission they haven't been prompted for yet is bad UX — the user has no idea what to grant. Phase 1 should report "will prompt on first record" and move on.
- **Why we don't auto-launch the capture binary from `init`.** Doing so would trigger the macOS permission prompt during `init`, which feels like a bait-and-switch (the user ran `init`, not `record`). Leaving the prompt for first-record is the principle of least surprise. The `--check-permissions` mode reads state without triggering a prompt.
- **Why `chirp devices` survives.** It is still genuinely useful for users debugging "which microphone is my system default?" — answers a question the new capture path doesn't cover (it always uses the default). PyAudio enumeration of input devices is the right tool for that; no reason to delete it.
- **Idempotency check.** Story 1.5 introduced re-run behavior in init. Verify this story's changes preserve it: a second `chirp init` on a healthy box should still emit `everything's already installed — skipping.` from Phase 2 and skip straight to Phase 3.
- **Order of operations during the change.** Land the Swift `--check-permissions` flag (task 1) and the Python helper (task 2) before touching `init_flow.py`, so the new code path can be tested against a real binary before the old code is deleted. This avoids a dead-zone state where neither check works.

## Testing

- **Unit:** the four new `tests/test_init_flow.py` cases plus the trimmed `tests/test_device_manager.py` suite.
- **Manual fresh-box:** revoke screen recording permission in System Settings, run `chirp init`, expect the red `✗ screen recording permission · denied` line and the System Settings hint. Re-grant, re-run, expect green check.
- **Manual idempotency:** run `chirp init` twice on a healthy box; second run hits the "everything's already installed — skipping." path with no prompts.
- **Manual end-to-end:** on a fresh macOS account, `pip install` Chirp, run `chirp init`, then `chirp record "doc smoke test"`, then `chirp transcribe`. Verify exactly two macOS prompts (mic, screen recording) appear during the first `record` and no prompts during `init`. Verify the WAV and the transcript are non-empty.
- **Doc audit:** `cat README.md` end-to-end, ensure the BlackHole references are gone and the new copy reads cleanly. Re-render the README on GitHub if possible.
