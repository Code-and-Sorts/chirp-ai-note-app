# Story 4.6 — Typer registration and alias tab completion

- **Status:** Draft
- **Epic:** [EPIC-MODEL-REGISTRY](../epic.md)
- **Depends on:** 4.3, 4.4, 4.5 (the six subcommand handlers all exist on `llm/cli/models.py`'s Typer app)
- **Blocks:** —

## User story

As a Chirp user, I want `chirp models` to appear in `chirp --help` under a visible panel, so I can discover the model-management surface without reading docs. As a shell-completion user, I want `<TAB>` after `chirp models default `, `chirp models remove `, `chirp models show `, and `chirp models pull ` to autocomplete against my registered aliases, so I never mistype a model name and have to backspace through it.

## Context

Stories 4.3–4.5 built the six `chirp models` subcommands on a stand-alone Typer app inside `llm/cli/models.py`. To users, none of those commands exist yet — the top-level `chirp` Typer app in `chirp/cli.py` hasn't been told about them. This story makes the surface real:

1. Register the `models` sub-app under the top-level `chirp` app.
2. Add it to the new `MODELS_PANEL` (visible panel) so `chirp --help` lists it alongside `record`, `transcribe`, etc.
3. Wire a Typer completion callback on the alias arguments of `default`, `remove`, `show`, and `pull` so `<TAB>` resolves against `models.toml` keys.

The Typer-panel scheme is established by EPIC-WF-ALIGN (the visible 7-command panel + hidden maintenance commands). This story extends that scheme by adding a new panel name (`MODELS_PANEL`) for the model-management group. The `daemon` group is a separate epic and uses the same panel-registration mechanism but for a hidden panel — out of scope here.

Implements the user-facing wiring portion of FR24–FR30 (the surface exists in `chirp --help`) and the tab-completion portion of PRD §Scripting Support → "The `<alias>` argument on `models default|remove|show|pull` uses a completion callback that reads `models.toml` to suggest registered aliases."

## Acceptance criteria

- **AC-1** `chirp/cli.py` registers the `models` Typer sub-app:
  ```python
  from llm.cli.models import app as models_app
  app.add_typer(models_app, name="models", rich_help_panel=MODELS_PANEL)
  ```
  where `MODELS_PANEL = "Models"` (or whatever stable string matches the existing panel-naming convention from EPIC-WF-ALIGN's `MAIN_PANEL`). `MODELS_PANEL` is declared in `chirp/cli.py` next to the existing panel constants.
- **AC-2** `uv run chirp --help` shows a `Models` panel containing `models`. The existing seven-command `Commands` panel (from EPIC-WF-ALIGN) is preserved unchanged. Hidden commands (`config`, `devices`, `index`) remain hidden.
- **AC-3** `uv run chirp models --help` shows six subcommands: `add`, `default`, `list`, `pull`, `remove`, `show` (Typer's natural alphabetical order is acceptable; the table need not be re-sorted).
- **AC-4** A new completion callback in `llm/cli/models.py`:
  ```python
  def _complete_alias(incomplete: str) -> list[str]:
      ...
  ```
  Behavior:
  1. Read `models.toml` via `llm.registry.read_registry()` — reusing CHIRPD-CORE 3.5's reader. If the file is missing or unreadable, return `[]` (no suggestions; the completion silently does nothing rather than erroring on every `<TAB>`).
  2. Return `[alias for alias in registry.models if alias.startswith(incomplete)]`. Sorted alphabetically for stable ordering across shells.
  3. Bounded: if the registry has more than 200 aliases (defensive cap), truncate the result. No realistic user will hit this.
- **AC-5** The completion callback is wired into the `alias` argument of:
  - `chirp models default <alias>` — story 4.5's `default` command.
  - `chirp models remove <alias> [--purge]` — story 4.5's `remove` command.
  - `chirp models show <alias> [--json]` — story 4.5's `show` command.
  - `chirp models pull <alias> [--no-warm]` — story 4.5's `pull` command.

  Use Typer's standard `Argument(..., shell_complete=_complete_alias)` (or `autocompletion=...` for older Typer; check the project's `typer` version). The `add` command's argument is `hf_repo`, not an alias — no completion is wired there.
- **AC-6** Completion callback is **read-only and side-effect-free**. It must not lazy-spawn the daemon, must not write the registry, and must not raise. Any exception inside the callback is swallowed and the function returns `[]` — a `<TAB>` press is interactive and brittle; a noisy traceback breaks the shell.
- **AC-7** Tests in `tests/llm/test_cli_models.py` (extend the existing file):
  - `test_completion_returns_matching_aliases` — seed registry with `gemma-4-4b`, `bge-small-en-v1.5`; assert `_complete_alias("qw") == ["gemma-4-4b"]` and `_complete_alias("") == sorted(both)`.
  - `test_completion_no_registry_returns_empty` — no registry file; assert returns `[]`.
  - `test_completion_unreadable_registry_returns_empty` — pre-seed `models.toml` with bad TOML; reader raises; assert callback swallows and returns `[]`.
  - `test_completion_does_not_spawn_daemon` — assert `llm.client.*` modules are not imported by the callback (a no-op import check or a `mock.patch("llm.client.model_load")` with `assert_not_called()`).
  - `test_models_subapp_registered_under_chirp` — invoke `chirp --help` via `CliRunner`; assert `models` appears in the output under a panel labeled `Models` (or matching the AC-1 constant).
  - `test_chirp_models_help_lists_six_subcommands` — invoke `chirp models --help`; assert all six command names appear.
- **AC-8** `uv run chirp --help` output is updated in any doc that captures it (typically `tests/test_cli_help.py` or a snapshot file). If no such snapshot test exists, this AC is satisfied by AC-7's `test_models_subapp_registered_under_chirp`.
- **AC-9** `uv run pytest tests/llm/test_cli_models.py` and `uv run pytest tests/test_cli.py` (or whatever covers `chirp/cli.py` help output today) pass. `ruff` and `mypy` clean.
- **AC-10** Manual smoke verification:
  - `uv run chirp --install-completion` (Typer's standard installer); restart shell or `source` the produced rc file.
  - With at least one registered alias: type `chirp models default <TAB><TAB>` and verify the alias is offered as a completion. Type `chirp models remove <prefix><TAB>` and verify only aliases starting with `<prefix>` appear.
  - Type `chirp models add <TAB><TAB>`: confirm **no** alias completions appear (the argument is `hf_repo`, not an alias) — `add` is intentionally not aliased-tab-completed.

## Dev notes

- **Why panel-level visibility for `models`.** Per PRD §CLI Tool Specific Requirements, `models` is user-facing because users must add a model before chirp is functional. The Maya journey requires the command to be discoverable in `chirp --help`. Contrast with `daemon` which is maintenance-tier and lives on a hidden panel.
- **Why the completion callback is silent on failure.** Shell completion runs in a tight loop as the user types. A traceback on every `<TAB>` would be incredibly noisy and would also fail in shells that don't display completion errors (most). Returning `[]` on any exception is the standard Typer-idiomatic pattern.
- **Why the completion doesn't spawn the daemon.** Same reason `chirp models list` doesn't (story 4.4): completion is a passive read. A daemon-spawn on `<TAB>` would surprise the user and could create slow / hung completions.
- **Why we sort the completions.** Stable ordering across shells (bash, zsh, fish) makes user experience consistent. Most shells alphabetize implicitly, but doing it explicitly removes the dependency on shell behavior.
- **Why cap at 200.** A safety belt. Reading a 1 MB TOML file on every `<TAB>` press is fine; iterating 200k aliases would not be. No real user has more than a dozen models registered.
- **`add`'s argument is intentionally unaliased.** `hf_repo` is freeform user input — completing against the registry would only help if the user is re-adding an existing repo, which is rare and idempotent. Completing against HuggingFace's catalog is out of scope (and would require network, violating the "completion must not lazy-spawn or net-call" rule).
