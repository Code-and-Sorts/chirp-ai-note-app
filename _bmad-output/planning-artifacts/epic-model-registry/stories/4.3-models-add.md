# Story 4.3 — `chirp models add` subcommand

- **Status:** Done
- **Epic:** [EPIC-MODEL-REGISTRY](../epic.md)
- **Depends on:** 4.1 (registry writer), 4.2 (HF wrapper), EPIC-CHIRPD-CORE story 3.6 (`llm.client` library + `model.load` daemon op)
- **Blocks:** 4.6

## User story

As a Chirp user on a fresh Mac, I want one command — `chirp models add mlx-community/gemma-4-4b-it-4bit` — to download a model from HuggingFace, register it in the local registry, set it as my default chat model, and warm it on the daemon so that my next `chirp ask` runs without any further setup. As a power user, I want `--alias`, `--role`, and `--no-warm` flags so I can override the inferred alias, force a role when the inferred one is ambiguous, and skip the warm step when I'm batch-adding multiple models.

## Context

This is the Maya journey's single load-bearing command, called out by PRD §Success Criteria → User Success → "Single-command model add." It pulls together the three pieces of plumbing this epic adds:

1. **Validation + role + download** (story 4.2's `validate_repo`, `infer_role`, `download_model`).
2. **Registry write** (story 4.1's `upsert_model`, `set_default_for_role`, `write_registry`).
3. **Auto-warm** via `llm.client.model_load` (CHIRPD-CORE story 3.6) — lazy-spawns the daemon if needed, issues `model.load`, surfaces the result.

The ordering rule, from epic §3 decision 8: validate → resolve role → download → write registry → warm. If any step before the registry write fails, the registry is **not** touched. If the warm step fails, the registry write is **not** rolled back — the user can retry warming with `chirp models pull` (story 4.5) or diagnose with `chirp daemon logs` (DAEMON-LIFECYCLE epic).

Implements FR24, FR25, FR32 (role inference), FR33 (auto-default on first-of-role), FR34 (auto-warm unless `--no-warm`), FR38 (HF cache reuse), and partial FR55 (the `huggingface_hub` direct dep added by 4.2 is the registry-side half of the dep swap).

## Acceptance criteria

- **AC-1** Module `llm/cli/models.py` exists with a Typer `app = typer.Typer(name="models", help="Manage chirp's MLX model registry")` and an `add` subcommand registered on it. The module is the eventual home of all six `chirp models` subcommands; this story adds the first.
- **AC-2** Command signature:
  ```
  chirp models add <hf_repo>
                  [--alias <name>]
                  [--role chat|embed]
                  [--no-warm]
  ```
  - `hf_repo` is required (Typer `Argument`).
  - `--alias` is optional; default is `None` → fall through to inferred alias via `alias_for_repo(hf_repo)` from story 4.1.
  - `--role` is optional Typer `Option` of type `Optional[Literal["chat", "embed"]]`; default `None` → fall through to `infer_role` from story 4.2.
  - `--no-warm` is a boolean flag (`False` by default → warm is attempted). Setting it skips the `model.load` step.
- **AC-3** Execution order (each step gated by the previous; any failure before step 5 aborts and does **not** touch the registry):
  1. **Validate repo.** Call `llm.hf.validate_repo(hf_repo)`. On `HfRepoNotFound`, print to stderr `Error: HuggingFace repo not found: <repo>. Check the repo name and try again.` and exit code 5 (model not found). On `HfNetworkError`, print `Error: Could not reach HuggingFace (<original>). Check your connection and try again.` and exit code 1.
  2. **Resolve role.** If `--role` was passed, use it. Else call `llm.hf.infer_role(metadata)`. On `RoleInferenceAmbiguous`, print `Error: Could not infer role for <repo>. Pass --role chat or --role embed explicitly.` and exit code 2.
  3. **Resolve alias.** If `--alias` was passed, use it. Else call `llm.registry.alias_for_repo(hf_repo)`. If the alias has a length / charset issue, the helper raises `ValueError` → catch and print `Error: Could not infer alias from <repo>. Pass --alias <name> explicitly (lowercase letters, digits, dot, dash, underscore).` exit 2.
  4. **Download.** Call `llm.hf.download_model(hf_repo, progress=<Rich progress callback>)`. On TTY, render a Rich progress bar with bytes-downloaded and ETA. Off TTY (or `--json` mode, though this command has no `--json`), print one `Downloading <repo>...` line to stderr at start and `Downloaded <repo> (<bytes> bytes)` line at done. On `HfDownloadFailed`, print `Error: Download failed: <original>. Try again, or run \`chirp models pull <alias>\` after fixing the cause.` exit 1.
  5. **Read existing registry.** Call `llm.registry.read_registry()` (CHIRPD-CORE 3.5). If the file does not exist yet, the reader returns an empty `Registry()` — **not** an error. If the file exists with an unsupported `schema_version`, the reader raises `RegistryUnsupportedSchemaVersion` — surface as `Error: Existing models.toml has unsupported schema version <n>. Delete ~/Library/Application Support/chirp/models.toml and re-run.` exit 1.
  6. **Mutate.** `registry = upsert_model(registry, alias, ModelEntry(hf_repo=hf_repo, role=resolved_role, options={}))`. Then **conditionally** `registry = set_default_for_role(registry, alias)` — only if the corresponding `default_chat` or `default_embed` was `None` before this step (FR33 — auto-default only when no default exists).
  7. **Write registry.** Call `llm.registry.write_registry(registry)`. On `RegistryWriteError`, print `Error: Could not write models.toml: <original>. Check directory permissions.` exit 1. **No rollback of the downloaded weights** — the HF cache is durable across registry mutations and a future retry will reuse it.
  8. **Auto-warm** (skip if `--no-warm`). Call `llm.client.model_load(alias)` (CHIRPD-CORE 3.6). Print to stderr `Warming <alias>...` before, `Ready.` on success, `Error: Model registered but warm failed: <message>. Run \`chirp models pull <alias>\` to retry or \`chirp daemon logs\` to diagnose.` on `LLMModelError` / `LLMTransportError`. **Warm failure is exit code 4** (model load failure), but the registry write is preserved.
  9. On full success (or `--no-warm`), exit 0.
- **AC-4** Output discipline (architecture §CLI Output Patterns):
  - All progress, status, and error messages go to **stderr**. Stdout is empty unless future extensions add structured output. This keeps the command pipe-friendly (e.g., `chirp models add … && chirp models list --json` works cleanly).
  - Rich progress bar uses the **shared Rich console** instance (architecture §CLI Output Patterns), not a per-call instantiation.
  - The Rich progress callback adapter implements the `ProgressCallback` Protocol from story 4.2.
- **AC-5** Idempotency contract:
  - Running `chirp models add <repo>` twice with no flags: the second run validates again, downloads (HF cache hit → fast no-op), reads the registry (now containing the alias from run 1), `upsert_model` replaces the entry (idempotent — same content), and skips `set_default_for_role` because the default is already set. Auto-warm runs again (also idempotent on a warmed daemon). Final exit 0 in both runs. Result on disk is the same.
  - Running `chirp models add <repo> --alias other` after a previous `chirp models add <repo>` (no `--alias`): the second invocation creates a **second** entry under `other` pointing at the same `hf_repo`. Both aliases coexist in the registry. The user can later remove either.
- **AC-6** Role conflict on re-add: if the user passes `--role embed` for a repo previously registered under the same alias as `chat` (rare but possible if they're correcting a misregistration), `upsert_model` replaces the entry's role atomically. The `default_*` keys are **not** touched by `upsert_model` directly, so the default may now point at a role-changed alias — this is the user's responsibility to fix with `chirp models default`. Surface a one-line warning to stderr: `Note: alias <name> role changed from chat to embed; defaults unchanged — verify with \`chirp models list\`.`

## Dev notes

- **Why the warm step is post-write, not pre-write.** Two reasons. First, the warm requires the registry to already contain the alias so the daemon's `model.load` lookup resolves. Second, the user's mental model is "the model is registered the moment download completes" — a failed warm should not erase that fact, especially because the most common warm failure mode (unsupported MLX architecture) is a model-side issue, not a registry-side issue. The user wants the alias preserved so they can `chirp models remove` it.
- **Why exit code 4 (and not 1) on warm failure.** PRD §Scripting Support → exit codes locks `4 = model load failure`. The user's `&&` pipelines should be able to distinguish "couldn't reach daemon" (code 3) from "model file is broken" (code 4) from "wrong repo name" (code 5). One code per failure mode is the contract.
- **Why no `--json` on `add`.** The command is interactive by design (progress bar, status lines). A `--json` mode would emit a single JSON document at the end, but neither the Maya nor the Priya journey calls for it. Adding it later is non-breaking. The two read-only commands (`list`, `show`) get `--json` — that's where machine-readable output earns its keep.
- **Why no rollback on warm failure.** Architectural decision in epic §3 #8. Rollback is symmetric: if warm fails, we'd have to also delete the downloaded weights (which the user paid time to fetch), and the cache deletion is a separate disk op that itself can fail. Better to leave the registered state visible and give the user `chirp models pull` and `chirp models remove --purge` as explicit follow-ups. The error message names both.
- **Why role inference is its own step (not folded into validation).** Two reasons. First, `--role` overrides skip the inference, but `validate_repo` runs unconditionally — separating the two keeps the logic linear. Second, the role-inference heuristic in story 4.2 is the most likely thing to need tuning post-launch; isolating it in its own call lets us swap the implementation without touching the validate path.
- **Why `set_default_for_role` is conditional.** PRD FR33 specifies auto-default only "when no default for that role is currently set." This implements that exactly: read the existing registry's `default_chat` / `default_embed`, and only call `set_default_for_role` when the corresponding field is `None`. If the user wants to flip the default, that's what `chirp models default` (story 4.5) is for.
