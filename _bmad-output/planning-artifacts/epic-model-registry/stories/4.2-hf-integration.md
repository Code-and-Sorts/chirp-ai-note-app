# Story 4.2 — `llm/hf.py`: HuggingFace download wrapper and role inference

- **Status:** Draft
- **Epic:** [EPIC-MODEL-REGISTRY](../epic.md)
- **Depends on:** —
- **Blocks:** 4.3, 4.5

## User story

As a Chirp developer, I want a single module that owns every outbound HuggingFace call — repo validation, snapshot download with progress, and role inference from repo metadata — so that the rest of the codebase consumes a small typed API instead of `huggingface_hub` directly, and so that the only file in the project doing network I/O for model weights is one well-bounded module that's easy to mock at the test boundary.

## Context

Per architecture §HuggingFace boundary, every `huggingface_hub` import in the CLI process lives in `llm/hf.py`. This story builds that module. It is independent of story 4.1 (registry writer) — `llm/hf.py` doesn't read or write `models.toml`. The two come together in story 4.3, which uses 4.2 to fetch and validate a model before using 4.1 to register it.

The module has three responsibilities:

1. **Validate the repo exists** on HuggingFace and fetch its metadata, used by `chirp models add` to fail fast if the user typed a wrong name. Wraps `HfApi.repo_info`.
2. **Download with progress feedback**, used by `chirp models add` and `chirp models pull`. Wraps `snapshot_download` with a tqdm-style callback the CLI converts into a Rich progress bar (TTY) or stderr line (non-TTY).
3. **Infer role** (`chat` vs. `embed`) from repo metadata, used by `chirp models add` to populate the `ModelEntry.role` field without forcing the user to pass `--role` for unambiguous cases.

The daemon's separate use of `huggingface_hub` (cache-path lookup with `local_files_only=True`, used at `model.load` time) is in CHIRPD-CORE's scope, not this story.

## Role-inference heuristic (locked here for traceability)

Given an `HfRepoMetadata` (the typed result of `repo_info`), `infer_role` returns `"chat"`, `"embed"`, or raises `RoleInferenceAmbiguous`. Rules, checked in order — first match wins:

1. **Tag-based hit on embed:** if any of `sentence-transformers`, `feature-extraction` is in `metadata.tags`, return `"embed"`.
2. **Name-pattern hit on embed:** the repo basename (lowercased, after `<org>/` stripped) contains any of `bge-`, `e5-`, `gte-`, `mpnet`, `minilm`, `sentence-transformers`. Return `"embed"`.
3. **Tag-based hit on chat:** if any of `text-generation`, `conversational` is in `metadata.tags`, return `"chat"`.
4. **`config.json` architecture hit:** if `metadata.config.architectures` contains a known causal-LM marker (`*ForCausalLM`, `*ForConditionalGeneration`), return `"chat"`. If it contains a known embedding marker (`*Model` from sentence-transformers config, or `BertModel` with `pooling_mode_*` in config), return `"embed"`.
5. **Fallback:** raise `RoleInferenceAmbiguous(repo, hint="pass --role chat or --role embed explicitly")`.

The heuristic is intentionally biased toward false-negatives (raise) rather than false-positives (guess wrong) — a wrong role at registry time leads to confusing behavior much later (chat model pinned as embed, or embed model auto-unloading). Forcing `--role` for ambiguous cases is the safer default.

## Acceptance criteria

- **AC-1** `huggingface_hub` is added to `[project.dependencies]` in `pyproject.toml` with a minimum pin compatible with `mlx-lm`'s requirement (consult `mlx-lm`'s `pyproject.toml` at story-execution time and pin to the same floor). Run `make dev-install`.
- **AC-2** A new module `llm/hf.py` exists. **No other module in the codebase imports `huggingface_hub`** — this is a hard contract enforced by `tests/test_conventions.py` (an AST-grep check planned in architecture §Enforcement). The daemon-side `local_files_only=True` lookup planned for CHIRPD-CORE is the one allowed exception and will live in `chirpd/backend.py` — out of scope for this story.
- **AC-3** Typed data classes (Pydantic or dataclass — implementer's choice; dataclass is fine since these are internal):
  - `HfRepoMetadata` with fields `repo_id: str`, `tags: list[str]`, `siblings_count: int`, `architectures: list[str]` (empty list if no `config.json`), `sha: str | None`.
  - `DownloadResult` with fields `repo_id: str`, `local_path: Path`, `bytes_downloaded: int`, `cache_hit: bool`.
- **AC-4** Function `validate_repo(repo_id: str) -> HfRepoMetadata`:
  - Calls `HfApi().repo_info(repo_id=repo_id)` (no auth token — public repos only in MVP).
  - On `huggingface_hub.errors.RepositoryNotFoundError`, raises `HfRepoNotFound(repo_id)`.
  - On any other `HfHubHTTPError`, raises `HfNetworkError(repo_id, original=<chained>)`.
  - On success, attempts to fetch `config.json` via `hf_hub_download(repo_id, "config.json", ...)` to extract `architectures`. If `config.json` is absent (some repos lack it), `architectures` is the empty list — **not** an error.
  - Returns the populated `HfRepoMetadata`.
- **AC-5** Function `infer_role(metadata: HfRepoMetadata) -> Literal["chat", "embed"]`:
  - Implements the 5-step heuristic exactly as documented in the §Role-inference heuristic section.
  - On step-5 fallback, raises `RoleInferenceAmbiguous(repo_id=metadata.repo_id, hint=...)`.
- **AC-6** Function `download_model(repo_id: str, *, progress: ProgressCallback | None = None) -> DownloadResult`:
  - Calls `huggingface_hub.snapshot_download(repo_id=repo_id, allow_patterns=None, local_dir=None, ...)` letting `huggingface_hub` use the standard cache (`~/.cache/huggingface/hub`, honoring `HF_HOME` automatically per FR38).
  - Returns `DownloadResult` with `local_path` set to the resolved snapshot path, `bytes_downloaded` from the API (or `0` if the API doesn't surface it on cache-hit), and `cache_hit: bool` set by comparing pre- vs. post- cache state (or using whatever `huggingface_hub` exposes on the current pin — implementer documents which signal is used).
  - On `huggingface_hub.errors.RepositoryNotFoundError`, raises `HfRepoNotFound`.
  - On `OSError` (disk full, permission denied), raises `HfDownloadFailed(repo_id, original=<chained>)`.
  - On any other `HfHubHTTPError`, raises `HfNetworkError`.
- **AC-7** The `ProgressCallback` protocol:
  ```python
  class ProgressCallback(Protocol):
      def on_start(self, total_bytes: int | None) -> None: ...
      def on_progress(self, bytes_downloaded: int, total_bytes: int | None) -> None: ...
      def on_done(self) -> None: ...
  ```
  The implementation wires `huggingface_hub`'s `tqdm`-class callback into these three calls. If `huggingface_hub`'s callback shape changes between minor versions, the seam is here and changes are isolated.
- **AC-8** Typed exception hierarchy at module top:
  ```
  HfError(Exception)
  ├── HfRepoNotFound       — repo_id; the user typed the wrong name
  ├── HfNetworkError       — repo_id; chained original; transient connectivity / 5xx
  ├── HfDownloadFailed     — repo_id; chained original; disk / permission / partial
  └── RoleInferenceAmbiguous — repo_id; hint with the suggested flag
  ```
  Subclasses set `.repo_id`, `.original` (where applicable), and a clean `__str__`. They are **not** subclasses of the `LLMError` hierarchy from CHIRPD-CORE — they belong to the registry layer, not the daemon-IPC layer. The CLI subcommands in story 4.3 / 4.5 catch these and convert to user-friendly stderr messages.
- **AC-9** Unit tests in `tests/llm/test_hf.py` mock at the `huggingface_hub` boundary using `unittest.mock.patch`. **No real network call is made by any unit test.** Required cases:

## Dev notes

- **Why isolate `huggingface_hub` to one module.** Two reasons. First, it is the only network-touching dependency in the CLI process (NFR-S3, daemon emits no network) — concentrating it in one module makes the privacy contract easy to audit. Second, `huggingface_hub`'s API shifts between minor versions; concentrating use in one module means upgrades are a one-file diff.
- **Why no auth token in MVP.** PRD §User Journeys treat models as public HF repos in `mlx-community`. Private-repo support is a Growth-tier feature. If a user passes a private repo today, `validate_repo` will surface `HfRepoNotFound` (HF returns 401 → 404-like response for unauthenticated access to private repos) — story 4.3's error message points them at HF's docs.
- **Why a Protocol for progress instead of a callable.** Three named methods (`on_start` / `on_progress` / `on_done`) map cleanly to Rich's `Progress` lifecycle and to a stderr "start/done" line in non-TTY mode (architecture §CLI Output Patterns). A single callable would force the consumer to switch on a "phase" arg, which is uglier.
- **Why role inference is conservative.** A wrong role at registry time creates a confusing failure mode much later: a chat model pinned as embed never auto-unloads; an embed model auto-unloads mid-batch. The cost of "raise `RoleInferenceAmbiguous` and force `--role`" is one extra command-line flag in rare cases — much cheaper than the debug session a wrong inference creates.
- **Cache layout** is owned by `huggingface_hub`. Chirp does **not** know the cache directory structure beyond "the path `snapshot_download` returns is a directory containing the model weights." The daemon-side `local_files_only=True` lookup (CHIRPD-CORE story 3.5 or 3.6) re-resolves the same path. We never write to the cache directly.
- **Why `os.replace`-style atomicity is not needed for downloads.** `huggingface_hub` already implements atomic-rename-on-complete inside its cache; partial downloads land in a sibling `.incomplete` path and are not visible as the canonical snapshot until complete. We rely on that contract.

## Handoff to downstream stories

- **4.3 (`chirp models add`)** consumes `validate_repo`, `infer_role`, `download_model`, the four typed exceptions, and the `ProgressCallback` Protocol.
- **4.5 (`chirp models pull`)** consumes `download_model` only.
- **4.4 (`chirp models list`)** and **4.6 (Typer wiring + completion)** do **not** consume this module — they're registry-read-only and daemon-query.

The stable contract from this story: four functions (`validate_repo`, `infer_role`, `download_model`, plus the implicit `ProgressCallback` adapter inside `download_model`), four typed exceptions, and two dataclasses. Future enhancements (private repos, alternate cache locations, resume from partial) extend this surface without breaking consumers.
