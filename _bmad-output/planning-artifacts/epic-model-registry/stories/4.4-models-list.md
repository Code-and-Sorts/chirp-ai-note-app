# Story 4.4 — `chirp models list` subcommand

- **Status:** Done
- **Epic:** [EPIC-MODEL-REGISTRY](../epic.md)
- **Depends on:** 4.1 (registry shape + reader contract via CHIRPD-CORE 3.5), 4.3 (shared `RichProgressCallback` and error-mapping helpers), EPIC-CHIRPD-CORE story 3.7 (`model.list` daemon op + `llm.client.model_list()`)
- **Blocks:** 4.6

## User story

As a Chirp user, I want `chirp models list` to print every model I've registered with its role, default-flag, and currently-loaded state, so I can see at a glance which model is the default and which is warm in the daemon. As a script author, I want `chirp models list --json` to emit a clean JSON document I can pipe into `jq`.

## Context

`models list` is the primary diagnostic command of the registry. It's what Priya runs after `chirp models add fast` to confirm both her 7B and her 3B are registered and to see which is currently resident in the daemon. It's also what `chirp init` (in EPIC-INIT-AND-MIGRATION) calls indirectly to decide whether to prompt the user to `chirp models add`.

Two data sources:
1. **`models.toml`** via `llm.registry.read_registry()` (CHIRPD-CORE 3.5) — the registered models, the defaults.
2. **Daemon `model.list` op** via `llm.client.model_list()` (CHIRPD-CORE 3.7) — the currently-loaded aliases and their per-model RSS / idle countdown. This is a daemon-side query; if the daemon isn't running, the command **does not** spawn one — loaded state is rendered as "—" (or `null` in JSON) and the command still succeeds.

The output is a Rich table on TTY and a single JSON document on `--json`. Implements FR26 (list with role/default/downloaded/loaded), FR31 (`--json`).

## Acceptance criteria

- **AC-1** `@app.command("list")` registered on the same `llm/cli/models.py` Typer app from story 4.3.
- **AC-2** Command signature:
  ```
  chirp models list [--json]
  ```
  `--json` is a boolean flag, default `False`.
- **AC-3** Execution:
  1. Read the registry: `registry = llm.registry.read_registry()`. If the file doesn't exist (fresh install), proceed with an empty `Registry()`.
  2. Query the daemon for loaded state: call `llm.client.model_list(spawn_if_absent=False)`. The boolean parameter (or its equivalent in the CHIRPD-CORE client API) instructs the client to **not** lazy-spawn the daemon — connect only if a daemon is already running. On `LLMDaemonUnreachable`, set `loaded_state = {}` (no models loaded as far as we can tell) and continue.
  3. Compose the output rows: one row per registered alias. Per-row fields:
     - `alias` — registry key.
     - `role` — `chat` or `embed` from registry.
     - `default` — `★` if this alias is `default_chat` or `default_embed` (TTY), `True`/`False` (JSON).
     - `loaded` — `True` if alias appears in `loaded_state.loaded_aliases`, `False` otherwise.
     - `hf_repo` — registry value.
     - `cache_path` — resolved via `huggingface_hub`'s cache layout helper, or `None` if not cached locally. (Use `huggingface_hub.try_to_load_from_cache` or equivalent — daemon-side lookup pattern, but it's `local_files_only` equivalent so it's allowed in the CLI process too. If pulling this convenience adds complexity, **omit `cache_path` from the list view** and surface it only in `show` — implementer's call. Update AC-7 tests accordingly.)
- **AC-4** Rendering on TTY (`sys.stdout.isatty()` true; `--json` not set):
  - A Rich `Table` titled `Models` with columns: `alias`, `role`, `default`, `loaded`, `hf_repo`.
  - Rows sorted by `(role, alias)` ascending — embed models first, then chat (or vice versa; pick one and document); within a role, alias alphabetical.
  - `default` column renders `★` (or some unambiguous TTY marker) for the default rows.
  - `loaded` column renders `●` for loaded and `—` for not-loaded — high-contrast at a glance.
  - If the registry is empty: print to stderr `No models registered. Run \`chirp models add <hf-repo>\` to get started.` and exit 0 (not an error — the empty state is valid).
  - If the daemon was unreachable: print one stderr line **before** the table: `(daemon not running — loaded state unknown)`. The `loaded` column shows `—` for every row.
- **AC-5** Rendering on `--json`:
  - A single JSON document to stdout, ending in a trailing newline. No Rich rendering, no progress, no log lines on stdout.
  - Schema:
    ```json
    {
      "schema_version": 1,
      "default_chat": "gemma-4-4b-it-4bit",
      "default_embed": "bge-small-en-v1.5",
      "models": [
        {
          "alias": "gemma-4-4b-it-4bit",
          "role": "chat",
          "default": true,
          "loaded": true,
          "hf_repo": "mlx-community/gemma-4-4b-it-4bit"
        }
      ],
      "daemon_reachable": true
    }
    ```
  - `default_chat` / `default_embed` are `null` (JSON) when unset.
  - `models` is an array — empty when no models registered.
  - `daemon_reachable` is `false` when the daemon was unreachable; the per-row `loaded` is `null` (JSON null) for every row in that case (not `false` — we don't know).
  - Exit code 0 in all non-error cases including empty registry and unreachable daemon.
- **AC-6** Output discipline:
  - **TTY mode:** Rich table on **stdout**; diagnostic preamble lines (e.g., "daemon not running") on **stderr**.
  - **JSON mode:** exactly one JSON document on **stdout**, no Rich rendering, no stderr noise unless an actual error occurred. The output must be `jq -e .` parseable.

## Dev notes

- **Why no lazy-spawn on `list`.** `list` is the diagnostic command a user runs when something is wrong. Lazy-spawning a daemon would mask the "is the daemon running?" question that `list` is supposed to answer. The PRD's daemon-status command (`chirp daemon status`, owned by DAEMON-LIFECYCLE) is the explicit lazy-spawn-friendly diagnostic; `models list` is the registry-side one.
- **Why exit 0 on empty registry and on daemon-unreachable.** Both are valid states. Empty registry on fresh install is the Maya journey's normal precondition. Daemon-unreachable is fine if the user is operating the registry offline (e.g., adding models to register but not yet warming them). Exit codes 3 (daemon unreachable) and 5 (model not found) are reserved for **failed user intent**, not "I observed an absence."
- **JSON schema stability.** The schema in AC-5 is the wire contract for downstream consumers (scripts, future GUIs). Adding new fields is non-breaking; renaming or removing fields requires a version bump on the JSON envelope. Don't add a `version` field yet — when we need to break the schema we'll add it and the absence-of-field is implicitly v1.
- **Sort order.** The implementer picks one — embed-first-then-chat, or chat-first-then-embed. Document the choice in a one-line comment in `_compose_rows`. Stable sort across runs matters; choosing which class goes first does not.
- **`★` vs `*` for default marker.** Rich tables render unicode fine on macOS terminals. `★` is the visual choice; `*` is the boring fallback. Either is acceptable per the wireframe-alignment epic's conventions (which use `✅`, `→`, etc. liberally).
