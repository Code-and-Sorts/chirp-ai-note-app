# Story 8.1 — Packaging & distribution correctness

- **Status:** in-review — implemented 2026-06-15 on `feat/story-8.1-packaging-correctness` (see Dev Agent Record); `make check` clean, wheel tag verified, awaiting review/merge.
- **Epic:** [EPIC-PRODUCTION-HARDENING](../epic.md)
- **Depends on:** —
- **Blocks:** the first real PyPI release (this is the only hard release blocker; epic §4: "8.1 lands first … nothing else can ship to PyPI safely without it")

## User story

As a **Linux / Windows / Intel-Mac user**, when I run `pip install chirp-notes-ai` I want pip to **refuse the install at resolution time** with a "no matching distribution" error, so I never get a "successful" install that bundles an arm64 Mach-O binary and then dies at runtime with `CaptureAudio.app is not bundled…`. The package is Apple-Silicon-only by design ([Source: prd.md#NFR-C2], [Source: architecture.md L69]); the wheel should advertise that, not lie with `py3-none-any`.

As an **Apple-Silicon (arm64) user on macOS 13+**, I want the wheel I install to actually contain a working, executable, correctly-signed `capture_audio` helper, so `chirp record` works on first run and the screen-recording / microphone prompts attribute to **CaptureAudio.app** (TCC identity `com.codeandsorts.chirp.capture-audio`), not to my terminal.

As a **maintainer cutting a release**, I want `uv build` to produce a single platform wheel tagged `macosx_*_arm64` (never `py3-none-any`), I want the publish flow to never push a source distribution that silently installs a chirp with no audio helper, and I want a CI test that **fails the build if the tag regresses** — because the current packaging test asserts the binary is present but never checks the tag, which is exactly how the mistag slipped past CI.

## Context

Chirp is an honestly-versioned alpha (`0.0.1a0`, [Source: pyproject.toml L7]). The packaging Critical is the single hard blocker before any real PyPI release ([Source: epic.md §2, §4]). Two distinct packaging defects plus three supporting gaps are in scope. All five were verified directly against current source on 2026-06-14.

### How the wheel is built today (verified)

- **Build backend:** hatchling. [Source: pyproject.toml L1-3] `requires = ["hatchling"]`, `build-backend = "hatchling.build"`.
- **Wheel target packages:** [Source: pyproject.toml L37-38] `[tool.hatch.build.targets.wheel]` lists the ten runtime packages. There is **no** `pure-python` / `[tool.hatch.build.targets.sdist]` / `[tool.hatch.build.targets.wheel].pure-python` key anywhere — verified by `grep -n "sdist\|targets\|pure" pyproject.toml` (only `targets.wheel` exists).
- **Custom build hook:** [Source: pyproject.toml L40-41] `[tool.hatch.build.hooks.custom]` → `hatch_build.py`. The hook ([Source: hatch_build.py L17-23], verified current) is:
  ```python
  class CustomBuildHook(BuildHookInterface):
      def initialize(self, version: str, build_data: dict) -> None:
          app_src = Path(__file__).parent / "audio_capture" / "CaptureAudio.app"
          if app_src.is_dir():
              build_data["force_include"]["audio_capture/CaptureAudio.app"] = (
                  "audio_capture/CaptureAudio.app"
              )
  ```
  It **only** force-includes the prebuilt bundle when it already exists. It never touches `build_data["pure_python"]` or `build_data["infer_tag"]`, and it never invokes the Swift compiler.

### Why the tag is wrong (CRITICAL #1)

With no `pure_python`/`infer_tag` signal, hatchling defaults to a pure-Python wheel: `Root-Is-Purelib: true`, `Tag: py3-none-any`, producing `chirp_notes_ai-0.0.1a0-py3-none-any.whl`. Yet the same wheel bundles `audio_capture/CaptureAudio.app/Contents/MacOS/capture_audio`, a **Mach-O 64-bit arm64** executable (force-included by the hook). A `py3-none-any` wheel tells PyPI "this runs on every Python ≥ 3.11 on every OS/arch." So `pip install chirp-notes-ai` would *succeed* on Linux, Windows, and Intel macOS, then fail only at runtime when `_resolve_binary_path()` can launch nothing usable — note that even the runtime guard's message ([Source: audio_capture/__init__.py L126-131]) says "The wheel must be built on macOS," i.e. it assumes the wrong-platform case can't happen, which is precisely the hole. The platform-gated deps (`mlx-lm`, `mlx-embeddings`, `huggingface_hub`) carry `; sys_platform == 'darwin' and platform_machine == 'arm64'` markers ([Source: pyproject.toml L27-29]), so off-target they are simply dropped — they do **not** make pip refuse the install. Only the wheel *tag* can do that.

**Fix:** make the wheel non-purelib and platform-tagged `macosx_*_arm64` via the build hook.

### Why the sdist can't build from source (CRITICAL #2)

- The prebuilt bundle is gitignored: [Source: .gitignore L210] `audio_capture/CaptureAudio.app/`.
- The hook force-includes it **only if it already exists** at build time (above) and never compiles it.
- The Swift source *is* tracked: `audio_capture/swift/capture_audio.swift`, `Info.plist`, `Makefile`.
- There is no `[tool.hatch.build.targets.sdist]` config, so hatchling produces a default sdist that contains the `audio_capture/swift/` sources but **not** a build step to turn them into `CaptureAudio.app`.

Net effect: an sdist (`chirp_notes_ai-0.0.1a0.tar.gz`) built from a clean checkout ships `capture_audio.swift` but no compiled helper. If pip ever falls back to the sdist — `pip install --no-binary chirp-notes-ai`, a yanked/absent wheel, or a Python/macOS combo with no matching wheel — the install **succeeds** with no helper, and `chirp record` dies at runtime with the bundled error: [Source: audio_capture/__init__.py L126-131]
```python
raise RuntimeError(
    "CaptureAudio.app is not bundled in this installation. "
    "The wheel must be built on macOS via `python -m audio_capture.build` "
    "before installation."
) from exc
```
**This is not hypothetical for the publish flow:** [Source: .github/workflows/shared-publish-package.yaml L50] runs `twine upload … dist/*.whl dist/*.tar.gz` — the broken sdist is uploaded to PyPI alongside the wheel.

**Fix (decide + justify in this story):** either (a) compile the Swift helper inside the build hook on macOS (reusing `audio_capture/build.py` logic) so the sdist is buildable from source, or (b) explicitly suppress the sdist from the publish flow and document the wheel-only distribution policy. See AC-2 and Dev notes for the recommended path.

### Why the mistag slipped past CI (TEST GAP #3)

The packaging test [Source: tests/test_audio_capture.py L561-602] (`test_wheel_bundles_executable_helper`, verified current line range) runs `uv build --wheel`, then asserts the helper path is **present** in the zip (L594) and has an **execute bit** (L599) — but it **never asserts the wheel filename or `WHEEL` tag**. So a `py3-none-any` wheel passes this test. The release/PR build path runs the Swift build then `uv build` ([Source: .github/workflows/shared-build-and-test.yaml L149-154]), and nothing downstream inspects the tag.

### Unused direct dependency (LOW #4)

[Source: pyproject.toml L19] declares `"requests>=2.31.0"` in `[project.dependencies]`. Verified: **no production module imports it.** `grep -rn "import requests\|from requests\|requests\." --include="*.py" .` (excluding tests) returns nothing; the only hits are in `tests/` (`test_conventions.py`, which actively *guards against* `requests.post/get` mocks for the migrated LLM paths — [Source: tests/test_conventions.py L30,L52]). `requests` is pulled in transitively by `chromadb`/`huggingface_hub`. The `types-requests` dev stub is also declared ([Source: pyproject.toml L51, L178]); since it only types a now-removed direct dep, drop it too unless mypy still needs it for the transitive surface (verify).

### Bundled-binary reproducibility & TCC identity (MED #5)

- The helper is host-built and **ad-hoc** codesigned (`--sign -`): [Source: audio_capture/build.py L81-83] `codesign --force --deep --sign - <bundle>`, mirrored in [Source: audio_capture/swift/Makefile L16-17]. The comment ([Source: audio_capture/build.py L75-80]) explains the bundle-level ad-hoc signature is what binds `Info.plist` and makes the TCC identity `com.codeandsorts.chirp.capture-audio` the code identity macOS attributes prompts to.
- The bundle version is stamped from pyproject: [Source: audio_capture/swift/Makefile L9-10, L32-39] reads `version = "…"` from `../../pyproject.toml` via `awk` and `sed`s `__CHIRP_VERSION__` → that value into `Info.plist` (`CFBundleShortVersionString` / `CFBundleVersion`, [Source: audio_capture/swift/Info.plist L15-18]).
- **Release-flow ordering is currently correct but unguarded.** In [Source: .github/workflows/shared-build-and-test.yaml]: the release-tag version bump (L143-147, `update_release_version.py`) runs **before** the Swift build (L149-151, `uv run python -m audio_capture.build`), which runs **before** `uv build` (L153-154). Because the Makefile reads the version at build time, the helper's `Info.plist` gets the bumped version. **But** this correctness is incidental to step ordering in one YAML file — there is no guard, no assertion, and the PR build path (`update_pr_version.py`, L136-141) likewise runs before the Swift build. If a future edit reorders these steps, the helper would be stamped with the stale pre-bump version and nothing would catch it. The reproducibility risk: the signed bundle is whatever the build host's toolchain + Swift version produce, with no pinned identity beyond ad-hoc.

## Dev notes

- **Hatchling platform-wheel mechanics.** Hatchling's wheel builder asks the build hook for `build_data`. The two relevant keys: `pure_python` (bool; `False` ⇒ `Root-Is-Purelib: false` and the wheel is treated as platform-specific) and `infer_tag` (bool; `True` ⇒ hatchling computes the tag from the running interpreter via `packaging.tags`, e.g. `cp311-cp311-macosx_14_0_arm64`). You can alternatively set `build_data["tag"]` to an explicit tag string. The current hook sets *neither*, so hatchling falls back to the pure-Python default `py3-none-any` even though it force-includes a Mach-O binary. The minimal correct change is `pure_python=False` + `infer_tag=True`. (Verify the exact key spelling against the installed hatchling version before finalizing — `uv run python -c "import hatchling, inspect; ..."` or the hatchling docs — the keys have been stable but confirm.)
- **Python-agnostic vs CPython-pinned tag.** The wheel contains no compiled *Python* extension — the only non-pure artifact is a standalone Mach-O *executable* invoked via `subprocess`, not loaded as a C-extension. So the wheel is ABI-independent; a `py3-none-macosx_*_arm64` tag is the most honest (works on any CPython ≥ 3.11 on arm64 macOS, refuses everything else). `infer_tag` may produce a `cp311`-pinned tag, which over-constrains (a 3.12 user would be refused unnecessarily). If you want the broader tag, set `build_data["tag"] = "py3-none-macosx_11_0_arm64"` (pick the floor macOS version deliberately — runtime requires macOS 13+ per `check_macos_version`, but the *wheel* platform floor is a packaging choice; `macosx_11_0_arm64` is the conventional arm64 floor). Document whichever you choose.
- **Why sdist policy B (wheel-only) is the pragmatic alpha choice.** The helper requires a macOS host with Xcode CLT (Swift 5.9+) to compile and an ad-hoc `codesign` to get the TCC identity. A buildable sdist (policy A) means *every* installer needs Xcode CLT, which contradicts the PRD's "zero third-party install requirements beyond `pip install chirp`" goal ([Source: prd.md L49, L67]). For an Apple-Silicon-only, wheel-distributed alpha, shipping a platform wheel and **not** publishing a half-built sdist is simpler and safer. Policy A is the "proper" long-term answer but adds build-time Swift-toolchain coupling for marginal benefit while the project is wheel-first. Whichever you pick, the non-negotiable is AC-2's failure-mode elimination.
- **What NOT to do:**
  - **Do not hand-edit the wheel filename or the `WHEEL` `Tag:` line.** A renamed `py3-none-any` wheel with a `macosx` filename but `Root-Is-Purelib: true` metadata is still wrong and pip/PyPI may reject or mis-resolve it. The tag must come from hatchling build data so filename and metadata agree.
  - **Do not ship a broken sdist silently.** That's the current state and the whole point of AC-2.
  - **Do not relax the platform markers on `mlx-lm`/`mlx-embeddings`/`huggingface_hub`** ([Source: pyproject.toml L27-29]) to "fix" off-platform installs — they correctly drop off-target; the wheel *tag* is the gate, not the deps.
  - **Do not introduce Developer ID / notarized signing** — out of scope; keep the existing ad-hoc `--sign -` contract, just guard its ordering.
  - **Do not delete `CaptureAudio.app` from `.gitignore`** — it stays a build artifact ([Source: .gitignore L210]); the wheel includes it via the build hook, not via git.
- **Alpha tradeoffs.** Version `0.0.1a0` with no backwards-compat obligation ([Source: prd.md §Alpha-stage simplifications L602-604]). This permits an aggressive, correct packaging change with no deprecation dance. Keep the change tight; this story is the release gate, not a packaging refactor.
- **Runtime guard already exists.** `_resolve_binary_path()` ([Source: audio_capture/__init__.py L118-150]) raises a clear `RuntimeError` if the bundle is missing — but its message presumes the wheel was built on macOS, i.e. it's a *defense*, not the *fix*. The fix is to never ship an installable artifact to the wrong platform (the tag) and to never ship a helper-less artifact at all (the sdist policy).
- **CI ordering is currently correct but fragile.** Verified: in `shared-build-and-test.yaml`, version bump (L136-147) → `python -m audio_capture.build` (L149-151) → `uv build` (L153-154). Because the Makefile reads the version at Swift-build time ([Source: audio_capture/swift/Makefile L9-10, L35-39]), the helper's `Info.plist` is correctly stamped. AC-5 makes this guaranteed instead of incidental.
