## User story

As a user who records daily, I want `chirp record` and `chirp devices` to release the PyAudio/PortAudio handle the moment they're done, so I never get re-prompted for microphone permission because a leaked process is still holding the audio subsystem open. (This project has a documented history of leaked processes re-triggering the macOS mic-permission (TCC) prompt; this is the most likely regression of that exact pain.)

As a first-run user whose Whisper model download fails mid-session (no network, Hugging Face rate-limit, disk full), I want a clear, actionable "couldn't download the Whisper model" message — not a raw traceback that abandons a recording I've already started — and I want the model validated *before* the microphone opens, so a download failure never aborts an already-capturing session.

As a user whose live transcript must be complete and uncorrupted, I want the final transcription pass to finish before the file is written (no torn/partial transcript, no `RuntimeError: list changed size during iteration`), and I want to be told when the machine is too slow to keep up and live transcript content is being dropped — while understanding the saved `audio.wav` itself is always intact.

## Context

This story owns the **audio/transcription reliability** findings from the 2026-06-14 production-readiness audit. Per the epic's findings → story map, that is: *"HIGH PyAudio/DeviceManager leak + dead-code removal; MED Whisper load/download typed error + actionable message + load-before-capture ordering; MED live-transcript finalize race (join timeout / lock-guarded export); MED queue-full drop surfacing; LOW explicit Whisper model teardown."* [Source: _bmad-output/planning-artifacts/epic-production-hardening/epic.md#3-findings-story-map]

### The capture architecture: Swift helper, not PyAudio

EPIC-AUDIO-CAPTURE replaced BlackHole + PyAudio capture with a first-party Swift helper. The locked decision: *"The recorder modules no longer touch PyAudio for capture; PyAudio stays in `device_manager.list_devices()` (the read-only enumeration used by `chirp devices`) since that command remains useful."* [Source: _bmad-output/planning-artifacts/epic-audio-capture/epic.md#audio-capture-call-sites-that-move-to-audio_capture]

That decision is the key to understanding finding 1. After the cutover, capture flows entirely through `audio_capture.AudioCapture` (the Swift subprocess), and `DeviceManager` (PyAudio) survives only for:
- `chirp devices` enumeration (`chirp/cli.py:1108` → `device_manager.list_devices()` / `get_default_input_device()` / `get_default_output_device()`).
- The cosmetic mic-name lookup `_resolve_mic_name(device_manager)` (`chirp/cli.py:117`), called from `record` at `chirp/cli.py:301` to populate the dashboard's "mic:" label.

**Verified dead-code claim (the audit asked us to confirm before recommending removal):**

`grep -rn "self.device_manager\." recorder/` returns **zero** call sites. `DeviceManager` is constructed and threaded through three recorder constructors but never *invoked* for capture:
- `recorder/audio_recorder.py:48-50` — `AudioRecorder.__init__(self, settings, device_manager)` stores `self.device_manager = device_manager`, then `_capture_worker` opens `AudioCapture()` at `recorder/audio_recorder.py:125`. `self.device_manager` is never read in the capture path.
- `recorder/live_audio.py:47` — `LiveAudioStream.__init__(..., device_manager=None)` accepts it; capture goes through the Swift helper, not PyAudio.
- `recorder/live_session.py:46,54,77` — `LiveTranscriptionSession` stores `self.device_manager` and forwards it to `LiveAudioStream`, which never uses it for capture.

So `DeviceManager` is **dead weight in the capture path** (both offline `record` and live `record --live-transcribe`). It is *not* dead overall — `chirp devices` and `_resolve_mic_name` legitimately use it.

**The leak.** `DeviceManager()` is constructed at `chirp/cli.py:267` (in `record`) and `chirp/cli.py:1108` (in `devices`) and is **never** `.close()`d nor used as a context manager. It relies solely on `__del__` → `close()` → `self.audio.terminate()` (`recorder/device_manager.py:38-39`, calling `close()` at `recorder/device_manager.py:27-30`). CPython does not guarantee prompt `__del__`, so the PortAudio instance leaks until GC. `DeviceManager` already implements `__enter__`/`__exit__` (`recorder/device_manager.py:32-36`) — the context-manager support exists; the call sites just don't use it.

### Whisper load is unguarded and ordered after capture starts

`WhisperTranscriber.__init__` calls `_load_model()` (`transcriber/whisper_transcriber.py:18-21`), which constructs `WhisperModel(...)` at `transcriber/whisper_transcriber.py:27-32` with **no try/except**. A first-run download failure raises a raw exception.

In the live path this is worse because of ordering: `LiveTranscriber.__init__` constructs `WhisperTranscriber(settings)` at `recorder/live_transcriber.py:49`, and `LiveTranscriptionSession.run()` constructs the `LiveTranscriber` at `recorder/live_session.py:117` — **after** `self.audio_stream.start()` at `recorder/live_session.py:85` has already opened the Swift capture helper. So a model-download failure aborts a session that is **already capturing**, surfacing as a generic `RecordingError`/traceback with no "couldn't download the Whisper model" message anywhere.

`audio_capture/__init__.py` already defines typed errors — `AudioCaptureStartTimeout`, `AudioCaptureCrashed`, `AudioCaptureCorrupt` (`audio_capture/__init__.py:101-109`) and raises `PermissionError` with System-Settings instructions. There is **no** equivalent typed error for Whisper model load/download. That is the gap.

### Live finalize race

`LiveTranscriber` guards `_segments` behind a lock via the `segments` property (`recorder/live_transcriber.py:56-59`) and mutates `_segments` under that lock inside `_maybe_transcribe` (`recorder/live_transcriber.py:180-188`). But `export_transcript` (`recorder/live_transcriber.py:266-274`) reads `self._segments` **directly, without the lock**.

`LiveTranscriptionSession.run()` stops the pipeline with `transcriber.join(timeout=1)` (`recorder/live_session.py:198`, inside `_stop_pipeline`), then reads `self.transcriber.total_words` / `.segments` and calls `export_transcript` at `recorder/live_session.py:176-180`. The final pass `_maybe_transcribe(force=True)` runs at `recorder/live_transcriber.py:92` after the run loop breaks — a full Whisper pass on CPU int8 that routinely exceeds 1s. So the 1-second join can time out with the worker thread **still mutating `_segments`** (`recorder/live_transcriber.py:183`) while `export_transcript` iterates the same list → `RuntimeError: list changed size during iteration` or a torn/partial saved transcript.

### Bounded queues silently drop speech

All live queues are bounded: `frame_queue` (maxsize 500), `chunk_queue` (maxsize 50), `event_queue` (200), `level_queue` (50) — `recorder/live_session.py:62-65`. Every producer drops on overflow with no record:
- `recorder/live_audio.py:222-229` — `frame_queue.put_nowait(frame)` / `level_queue.put_nowait(peak)`, each `except queue.Full: pass`.
- `recorder/vad_chunker.py:142-154` — `chunk_queue.put_nowait(chunk)`, `except queue.Full: pass`.
- `recorder/live_transcriber.py:103-106` — `event_queue.put_nowait(event)`, `except queue.Full: pass`.

On a slow CPU-int8 Whisper, `chunk_queue` (maxsize 50) fills and **speech chunks are dropped silently** → the live transcript loses content. **Important nuance:** the saved `audio.wav` is written by `LiveAudioStream._publish_mixed_frame` *before* the frame is enqueued (`recorder/live_audio.py:210-211` writes the wave frame; the `put_nowait` at 222 is after). So the WAV is unaffected by chunk-queue drops — only the *live transcript* loses content. Don't over-fix the WAV path.

### Whisper model never explicitly freed

`WhisperTranscriber.__del__` does `del self.model` (`transcriber/whisper_transcriber.py:328-330`) — `__del__`-dependent. `LiveTranscriber` constructs a `WhisperTranscriber` (`recorder/live_transcriber.py:49`) with no explicit teardown; `LiveTranscriptionSession` closes `self.audio_stream` (`recorder/live_session.py:170`) but never the transcriber. The CTranslate2 model (hundreds of MB) lingers until GC.

### Dead CUDA branch + wrong comment

`_get_optimal_device` hard-returns `"cpu"` on Darwin (`transcriber/whisper_transcriber.py:37-38`); the `cuda`/`torch.cuda.is_available()` branch (`:39-44`) is unreachable on the only supported platform (macOS-only — [Source: epic-audio-capture/epic.md#3-locked-decisions], decision 1). `_get_compute_type` (`:46-51`) returns `float16` for the (unreachable) GPU branch. Separately, `transcriber/batch_processor.py:189-192` has a TODO comment claiming *"both Whisper and chirpd target Metal"* — Whisper does **not** target Metal here; it runs CPU int8 on Darwin per `_get_optimal_device`. The comment is wrong.

### `check_permissions` uncaught `TimeoutExpired`

`check_permissions` runs `subprocess.run([...], timeout=3, ...)` at `audio_capture/__init__.py:497-503` with **no** `except subprocess.TimeoutExpired`. A wedged helper propagates a raw `TimeoutExpired` to its callers: `chirp/init_flow.py:186` (`chirp init`) and `chirp/cli.py:1168` (`chirp devices`). Note the codebase already catches `TimeoutExpired` in the streaming/teardown paths (`audio_capture/__init__.py:371,408,446,471,478`) — `check_permissions` is the lone omission.

## Acceptance criteria

- **AC-1 — PyAudio/PortAudio handle is released deterministically; DeviceManager is removed from the capture path.**
  - **AC-1a (release):** Every `DeviceManager()` construction is deterministically closed — either via `with DeviceManager() as device_manager:` or an explicit `device_manager.close()` in a `finally`. Specifically: `chirp/cli.py:1108` (`devices`) and the surviving cosmetic use in `record` (`chirp/cli.py:267`). No code path may rely on `__del__` for PortAudio teardown.
  - **AC-1b (remove from capture path):** Stop threading `DeviceManager` through the capture classes that never use it. Remove the `device_manager` parameter/attribute from `AudioRecorder` (`recorder/audio_recorder.py:48-50`), `LiveAudioStream` (`recorder/live_audio.py:47`), and `LiveTranscriptionSession` (`recorder/live_session.py:46,54,77`) — the recommended approach per the verified dead-code finding (`grep -rn "self.device_manager\." recorder/` → zero hits). Update `chirp/cli.py` `record` (`:300`, `:408-410`) accordingly. **Do not** delete `DeviceManager` the class — `chirp devices` (`chirp/cli.py:1106-1112`) and `_resolve_mic_name` (`chirp/cli.py:117-120`) still need it; just stop passing it where it's dead, and scope it so its handle is closed (AC-1a). (DECISION LOCKED 2026-06-15: do AC-1b — remove `DeviceManager` from the capture path, not merely scope it. AC-1a is still required for the surviving `devices` / mic-name uses.)
  - **Tests must NOT touch real audio devices.** Follow the existing pattern in `tests/test_device_manager.py`: `patch("recorder.device_manager.pyaudio.PyAudio")` so no real PortAudio instance is created. Assert `close()`/`terminate()` is called exactly once on the mock (e.g. via `with`-exit or explicit close), proving the handle is released. Never instantiate a real `DeviceManager` against hardware.

- **AC-2 — Whisper model load/download failure raises a typed, actionable error, and is validated before capture opens in the live path.**
  - Wrap `WhisperModel(...)` construction in `_load_model` (`transcriber/whisper_transcriber.py:23-32`) in a try/except that re-raises a typed error (e.g. a new `WhisperModelLoadError`/`ModelDownloadError` in `chirp/exceptions.py`, mirroring how `audio_capture` defines `AudioCaptureCrashed` etc. at `audio_capture/__init__.py:101-109`). The message must name the failure as a Whisper model download/load problem and suggest a remedy (check network / retry / disk space / the configured model name `self.settings.models.whisper`).
  - **Ordering fix (live path):** In `LiveTranscriptionSession.run()`, the Whisper model must be loaded/validated **before** `self.audio_stream.start()` (`recorder/live_session.py:85`). Today `LiveTranscriber` (which constructs `WhisperTranscriber` at `recorder/live_transcriber.py:49`) is built at `recorder/live_session.py:117`, after capture starts. Restructure so a model-load failure surfaces the typed error *before* the mic/screen-recording helper is opened — never abort an already-capturing session on a download failure. A clean approach: construct/load the `WhisperTranscriber` (or pre-warm it) up front, then start capture.
  - The offline `record` path (`chirp/cli.py` → `AudioRecorder` → `transcribe` later) should surface the same typed error with the same actionable message.
  - **Tests:** mock the model. Use `patch` so `WhisperModel(...)` raises (network/disk-full simulation) and assert the typed error + message; assert in the live path that capture is **not** started when load fails (the audio stream's `start()` mock is not called). Reuse the `tests/test_whisper_transcriber.py` `mock_settings`/`mock_whisper_model` fixtures. **No real model download; no real audio.**

- **AC-3 — Live-transcript finalize is race-free: the final pass completes and the export is consistent.**
  - The worker's final `_maybe_transcribe(force=True)` (`recorder/live_transcriber.py:92`) must complete before the transcript is exported. Fix `LiveTranscriptionSession._stop_pipeline` (`recorder/live_session.py:191-198`): the `self.transcriber.join(timeout=1)` (`recorder/live_session.py:198`) must not return while the worker is mid-pass — either remove the 1-second timeout (join unbounded, or with a generous bound that accommodates a full CPU-int8 Whisper pass), or otherwise guarantee the thread has finished before reading its segments at `recorder/live_session.py:176-180`.
  - **And** guard `export_transcript` with the lock: `export_transcript` (`recorder/live_transcriber.py:266-274`) must read `self._segments` through the lock-guarded `segments` property (`recorder/live_transcriber.py:56-59`) or take `self._lock` itself, so iterating the list while the worker mutates it (`recorder/live_transcriber.py:183`) can never raise `RuntimeError: list changed size during iteration` or write a torn transcript. ## Dev notes

- **The Swift teardown is excellent — do not disturb it.** EPIC-AUDIO-CAPTURE's helper lifecycle is the strong part of the subsystem and is already hardened: `_atexit_cleanup` does `terminate → wait(_PROC_WAIT_TIMEOUT) → kill → wait` (`audio_capture/__init__.py:462-483`), and `LiveAudioStream.stop()` does `proc.terminate()` → join mixer thread (with a logged timeout warning) → `cap_ctx.__exit__(...)` in the right order, with a deliberate comment about not closing stdout while `_read_frame` blocks (`recorder/live_audio.py:231-259`). This story does **not** touch the Swift helper, its `Popen` lifecycle, the framing parser, or the broken-pipe/SIGTERM handling. The PyAudio leak (finding 1) is a *separate* resource from the Swift helper — don't conflate them.
- **Saved-WAV-is-unaffected nuance (finding 4).** The live transcript and the saved `audio.wav` are independent. The WAV frame is written at `recorder/live_audio.py:210-211` *before* the frame is enqueued for transcription (`:222`). Chunk-queue / frame-queue drops only degrade the *live transcript*, never the WAV. The AC requires the user-facing warning to say so — do not "fix" the WAV path or add blocking backpressure that could stall the WAV write cadence.
- **Why load-before-capture matters (finding 2).** It is acceptable for a Whisper download to fail; it is not acceptable for that failure to abandon an in-progress recording. The fix is ordering, not retry logic. Today the model is constructed at `recorder/live_session.py:117` after `start()` at `:85`; flip that. Keep it minimal — pre-warm/validate, surface the typed error, then start capture.
- **`DeviceManager` is not entirely dead — verify before deleting the class.** The audit asked to verify the dead-code claim; it's confirmed dead *in the capture path* (zero `self.device_manager.` call sites in `recorder/`) but live in `chirp devices` (`chirp/cli.py:1106-1112`) and `_resolve_mic_name` (`chirp/cli.py:117-120`). Do **not** delete the class or its `list_devices`/`get_default_*` methods. AC-1b removes it only from the three capture constructors.
- **Reuse existing patterns, don't reinvent.** Typed audio errors already exist (`audio_capture/__init__.py:101-109`); add the Whisper-load error in the same spirit (most naturally in `chirp/exceptions.py` alongside `RecordingError`/`AudioDeviceError`). The `except subprocess.TimeoutExpired` pattern already exists five times in `audio_capture/__init__.py` (`:371,408,446,471,478`) — AC-7 just adds the sixth at `check_permissions`. The lock-guarded read pattern already exists (`segments` property, `:56-59`) — `export_transcript` should use it.
- **What NOT to do:** don't add CUDA/Metal GPU support to Whisper (AC-6 is comment/dead-branch cleanup only — the platform is CPU int8); don't add a config flag for the queue sizes; don't introduce a new threading model for the live pipeline; don't change the `audio.wav` format or the framing protocol; don't refactor the dashboard rendering beyond adding the drop indicator.
