# Story 8.3 — chirpd daemon & LLM client reliability

- **Status:** ready-for-dev
- **Epic:** [EPIC-PRODUCTION-HARDENING](../epic.md)
- **Depends on:** [EPIC-CHIRPD-CORE](../../epic-chirpd-core/epic.md) + [EPIC-DAEMON-LIFECYCLE](../../epic-daemon-lifecycle/epic.md) — both already shipped; this story **hardens** the surface they built (the daemon process, the NDJSON wire protocol, the `llm.client` library, the per-model idle-unload scheduler, the LaunchAgent path). It does not introduce new ops or change the envelope shape.
- **Blocks:** —

## User story

As a user whose `chirp ask` (or note generation, or auto-index) calls into a locally-spawned `chirpd`, I want a request to a wedged daemon to **fail loudly with an actionable error within a bounded time** rather than hang my terminal forever, so that a stuck model load or a deadlocked generation never leaves me with a frozen CLI and a `^C` that doesn't return a prompt.

As a user upgrading chirp (`pip install -U`) where the new release is a cosmetic/patch bump with a **byte-identical wire protocol**, I want the running daemon to stay up and keep my multi-GB warm model resident, so that a docs-only or dependency-bump release doesn't silently evict my model and force a 5–10 s cold reload on my next question.

As an operator running an isolated test/second instance via `CHIRP_DAEMON_SOCKET=/tmp/chirpd-test.sock`, I want that override to actually produce a **genuinely independent daemon** — its own lock, its own socket, no contention with my primary daemon — so that I can run a throwaway daemon for a test fixture or a manual repro without killing the daemon serving my real `chirp ask` workflow.

## Context

**This story is grounded in the real CHIRPD-CORE contract — every line number below was re-verified against `main` on 2026-06-14.** Prior daemon-lifecycle stories drifted from the actual `client`/`dispatcher`/`state`/`server` signatures; the audit's line numbers were spot-checked and corrected here. Read this section before touching ACs.

### How the IPC / handshake / cancellation actually work today

- **Wire protocol** — NDJSON over a unix socket, one JSON object per line, one request per connection. Op/event constants and the envelope codec live in `llm/protocol.py`. The package version is read via `package_version()` ([`llm/protocol.py:21`](../../../../llm/protocol.py)) from the `chirp-notes-ai` distribution; current version is `0.0.1a0` (`pyproject.toml:7`). There is **no `PROTOCOL_VERSION` constant** — the package version is the only version that exists.
- **Handshake** — every connection begins with `hello`. `chirpd/server.py:_handle_hello` ([line 182](../../../../chirpd/server.py)) compares `client_version == daemon_version` ([line 192](../../../../chirpd/server.py)). Both sides obtain their version from `package_version()` ([`chirpd/dispatcher.py:40`](../../../../chirpd/dispatcher.py), [`chirpd/state.py:56`](../../../../chirpd/state.py)). On match → `ready`; on mismatch → emit `version_mismatch`, set the server's `shutdown_event` ([server.py:219](../../../../chirpd/server.py)), daemon exits 0. The client (`llm/client.py:_request`, [lines 353–394](../../../../llm/client.py)) waits for the socket to vacate (`_wait_for_socket_gone`), lazy-spawns the new version, and retries **exactly once**.
- **Client read loop** — `llm/client.py:_run_request_on_connection` ([lines 560–586](../../../../llm/client.py)) writes the request envelope, then loops `event = await _read_event(reader)` until `EVENT_DONE`. `_read_event` ([lines 589–611](../../../../llm/client.py)) does `await reader.readuntil(b"\n")` **with no timeout**. A daemon that accepts the connection, completes the `hello`, then stalls (deadlocked model load, hung generation, runaway `mlx_lm` call) leaves this `readuntil` awaiting forever. The only timeouts in the client are `DEFAULT_SPAWN_TIMEOUT_S = 3.0` (spawn poll) and `_wait_for_socket_gone` — **neither bounds an in-flight inference read.**
- **Sync wrappers** — `chat_sync` / `chat_stream_sync` / `embed_sync` / `cancel_sync` ([`llm/client.py:272`, `:281`, `:324`, `:350`](../../../../llm/client.py)) all drive the same `_read_event` path, so the hang is inherited by every consumer:
  - `notes/note_generator.py:373` — `client.chat_stream_sync(...)` (note generation during `chirp transcribe`).
  - `notes_chat/prompting.py:62` — `llm.chat_sync(...)`; `:80` and `:116` — `chat_stream_sync(...)` (the `chirp ask` paths).
  - `notes_chat/index.py:338` — `self._llm_client.embed_sync(...)` (indexer embeddings).
- **Cancellation** — `chat_stream` / `chat_stream_sync` accept a **caller-supplied** `request_id` ([`llm/client.py:249`, `:287`](../../../../llm/client.py)). The dispatcher's chat handler requires it to be a string ([`chirpd/dispatcher.py:295`](../../../../chirpd/dispatcher.py)) and registers a `should_stop` event keyed by it: `state.register_cancellation(request_id, should_stop)` ([dispatcher.py:319](../../../../chirpd/dispatcher.py)). `DaemonState.register_cancellation` ([`chirpd/state.py:252`](../../../../chirpd/state.py)) does a plain `self._cancellation_events[request_id] = event` — **it overwrites by key with no duplicate-in-flight check**. The chat handler's `finally` calls `state.clear_cancellation(request_id)` ([dispatcher.py:425](../../../../chirpd/dispatcher.py)), a `dict.pop`. `cancel` ([dispatcher.py:511–547](../../../../chirpd/dispatcher.py)) looks up `get_cancellation(target_id)` and `.set()`s it. The real `chirp ask` interactive path generates a fresh id per query (`req_id = new_request_id()`, `notes_chat/prompting.py:175`, passed at `:117`) — so today's *call site* is safe, but the daemon trusts whatever key the client sends; a duplicate/fixed id (a buggy or hostile client, a re-issued id) cross-cancels or evicts another in-flight request's event.
- **Idle-unload** — `LoadedModel` carries `last_used`, `loaded_at`, an `asyncio.Lock`, and an optional `idle_unload_task` ([`chirpd/state.py:26–34`](../../../../chirpd/state.py)). `schedule_idle_unload` ([state.py:261–282](../../../../chirpd/state.py)) **returns immediately for any non-chat role** (`if model.role != "chat": return`, [state.py:266](../../../../chirpd/state.py)) — embed models are never idle-unloaded by design (FR6 pin), but there is also **no cap on resident models and no reaction to memory pressure**. `status()` ([state.py:215](../../../../chirpd/state.py)) only *reports* `rss_bytes`. `_delayed_unload` ([state.py:284–295](../../../../chirpd/state.py)) sleeps `delay`, then a guard at [state.py:293](../../../../chirpd/state.py) re-checks `(now - model.last_used).total_seconds() + 1e-6 < delay` before unloading.
- **The idle-unload-vs-long-generation race.** In `_handle_chat`, `state.load(...)` ([dispatcher.py:317](../../../../chirpd/dispatcher.py)) is called **before** the `async with loaded.lock` streaming block ([dispatcher.py:326](../../../../chirpd/dispatcher.py)). For a chat model, `load()` itself (re)schedules the idle timer at load time ([`chirpd/state.py:140` and `:155`](../../../../chirpd/state.py)) and sets `last_used` at load. `state.touch(loaded)` (which advances `last_used`) runs **only after** the lock block exits ([dispatcher.py:374](../../../../chirpd/dispatcher.py)). So a generation longer than `idle_timeout_s` lets the `_delayed_unload` sleep elapse; the task then blocks on `model.lock`, and once the generation releases it the guard at [state.py:293](../../../../chirpd/state.py) sees `last_used` (set at load) older than `delay` and unloads — the next request pays a full reload. (Note: `schedule_idle_unload` cancels the prior task before creating a new one, so the only window is when the *single* scheduled task outlives a long generation; the post-completion reschedule in the `finally` at [dispatcher.py:427](../../../../chirpd/dispatcher.py) replaces it, but the unload may already have happened during the lock wait.)
- **Late-cancel-as-error.** After the stream loop, `_handle_chat` checks `if should_stop.is_set()` ([dispatcher.py:379](../../../../chirpd/dispatcher.py)) and emits a `MODEL_CANCELLED` **error** event ([dispatcher.py:380–389](../../../../chirpd/dispatcher.py)). If a `cancel` arrives after the last token but the generator already exited normally, the full answer streamed and *then* an error event fires. The interactive consumer (`notes_chat/interactive.py:264`) prints every `error` event as `console.print(f"\n[red]{error_msg}[/red]")` — so a fully-answered query gets a spurious red error tail.
- **Error-code fidelity.** The client maps incoming error codes via `CODE_TO_EXCEPTION` ([`llm/exceptions.py:92–99`](../../../../llm/exceptions.py)); an **unknown** code degrades to `LLMMalformedResponse` ([`llm/client.py:618–623`](../../../../llm/client.py)), discarding the daemon's real `message` — exactly the wrong behavior during a version skew where the daemon may emit a code the client doesn't know. The dispatcher's outer `except Exception` ([dispatcher.py:98–117](../../../../chirpd/dispatcher.py)) maps **every** unexpected exception to `MODEL_GENERATION_FAILED`. `cancel` reuses `MODEL_NOT_FOUND` ([dispatcher.py:539](../../../../chirpd/dispatcher.py)) for "no in-flight request to cancel".
- **Single-instance lock vs socket path.** `single_instance_lock(lock_path=None)` ([`chirpd/lifecycle.py:23–33`](../../../../chirpd/lifecycle.py)) defaults to `paths.LOCK_PATH` (`~/Library/Application Support/chirp/chirpd.lock`, a single global path — [`chirpd/paths.py:10`](../../../../chirpd/paths.py)). The function **accepts** a `lock_path` argument, but `chirpd/__main__.py:48` calls `single_instance_lock()` with **no argument**, while `_resolve_socket_path()` ([`__main__.py:31–32`](../../../../chirpd/__main__.py)) honors the `CHIRP_DAEMON_SOCKET` override. Net effect: the socket is per-path but the lock is global, so a second daemon launched with a different `CHIRP_DAEMON_SOCKET` **loses the flock to the primary and exits 0 immediately** — its socket never appears, and the client polling that custom path times out. The override **cannot** isolate a second instance today.
- **Override-socket directory perms.** `ensure_runtime_dirs()` ([`chirpd/lifecycle.py:16–20`](../../../../chirpd/lifecycle.py)) only `mkdir(mode=0o700)`s `APP_SUPPORT_DIR` and `LOG_DIR`. `serve()` ([`chirpd/server.py:33–47`](../../../../chirpd/server.py)) binds `socket_path` then `socket_path.chmod(0o600)` at [server.py:46](../../../../chirpd/server.py) — but it does **not** create or chmod the *parent directory* of a `CHIRP_DAEMON_SOCKET` override, and there is a sub-millisecond window between `start_unix_server` ([server.py:43](../../../../chirpd/server.py)) and the `chmod(0o600)` ([server.py:46](../../../../chirpd/server.py)) where the socket exists with the process umask's default mode.
- **Stale narrative docstrings.** `llm/cli/daemon.py` opens "This module is the **eventual** home of the seven `chirp daemon` subcommands … Story 5.6 wires `daemon_app` into the top-level CLI; **until then** the subapp is reachable only through its Typer instance" — but `daemon_app` is **already** wired (`chirp/cli.py:536–538`) and all subcommands exist. `llm/cli/models.py` similarly says "the **eventual** home of all six … Story 4.3 adds `add`…" though all are implemented and wired (`chirp/cli.py:531`). `llm/registry.py:77–80` raises a schema-version error pointing users at **`chirp models init`** — a command that does not exist (the registry CLI ships `add`/`list`/`show`/`default`/`remove`/`pull`, no `init`).

### Locked contract you must NOT break (from CHIRPD-CORE / DAEMON-LIFECYCLE)

- **Single OS process, single asyncio event loop**; blocking inference wrapped in `asyncio.to_thread`, tokens streamed over `asyncio.Queue` via `loop.call_soon_threadsafe`. [Source: epic-chirpd-core/epic.md §3 decision 1]
- **One request per connection**, NDJSON, envelope keys `id`/`op`/`event`/`error`. [Source: epic-chirpd-core/epic.md §3 decision 3]
- **Version handshake is alpha-simplified — immediate exit on mismatch, no drain.** [Source: epic-chirpd-core/epic.md §3 decision 4] — this story changes *what* is compared (protocol vs package), not the exit-on-mismatch mechanism.
- **Request id format** `r-` + 12 hex chars, `secrets.token_hex(6)`; **daemon echoes, never invents** an id. [Source: epic-chirpd-core/epic.md §3 decision 5] — the daemon must keep echoing the client id; the duplicate-rejection fix must work *within* that constraint (reject/namespace, not regenerate).
- **Error codes live only in `llm/error_codes.py`**, SCREAMING_SNAKE_CASE, imported by both sides; the `code → exception` table is `llm/exceptions.py:CODE_TO_EXCEPTION`. [Source: epic-chirpd-core/epic.md §3 decision 6] — any new code (timeout, request-conflict) is added there.
- **Exception hierarchy** `LLMError → LLMTransportError / LLMProtocolError / LLMModelError`; never raise the base class, never raise `ValueError`/`RuntimeError` at the LLM layer. [Source: epic-chirpd-core/epic.md §3 decision 7]
- **Embed models are pinned (FR6)** — do not idle-unload them blindly; AC-5's memory policy must respect the pin (evict under pressure only as a deliberate, last-resort policy, never on a plain idle timer). [Source: epic-chirpd-core/epic.md §3 decision 8; epic-daemon-lifecycle/epic.md §3 decision 7]
- **Daemon never auto-exits on idle** — only *models* unload; the process stays up. [Source: epic-daemon-lifecycle/epic.md §3 decision 7]
- **No daemon network traffic** (NFR-S3); socket mode `0600` (NFR-S2). [Source: epic-chirpd-core/epic.md SC-8, SC-9]

## Acceptance criteria

- **AC-1 — Configurable inference read timeout, surfaced as a typed exception.** The client bounds the per-event read in the inference loop. `_read_event` (or `_run_request_on_connection`'s read) wraps the `await reader.readuntil(b"\n")` in `asyncio.wait_for(...)` (or `asyncio.timeout`) with a configurable budget. On timeout it raises a **new typed exception** in the `LLMTransportError` subtree (e.g. `LLMInferenceTimeout`) with an actionable message naming the timeout and pointing at `chirp daemon status` / `chirp daemon restart`. The budget resolves via env → config → default, mirroring the existing idle-timeout precedent: a new `CHIRP_INFERENCE_TIMEOUT` env var (`config/settings.py`, alongside `CHIRP_MODEL_IDLE_TIMEOUT`, [settings.py:13](../../../../config/settings.py)), an `LLMSettings.inference_timeout_seconds` field ([settings.py:104–107](../../../../config/settings.py)), and a `resolve_inference_timeout_seconds()` helper modeled on `resolve_idle_timeout_seconds()` ([settings.py:33–40](../../../../config/settings.py)). The timeout MUST be **per inter-event read, not per whole request** — a long but healthy stream emits a token well within the budget on each read, so a generous default never trips on a slow-but-alive generation. `chat_sync`, `chat_stream_sync`, `embed_sync`, and the consumers at `notes/note_generator.py:373`, `notes_chat/prompting.py:62/80/116`, `notes_chat/index.py:338` all inherit the bound automatically (no call-site change needed). **(OQ1 RESOLVED 2026-06-15: default 60 s per inter-event read, with a larger budget for the first event to cover cold load — see Dev notes.)**

- **AC-2 — Handshake on `PROTOCOL_VERSION`, not package version.** Add a `PROTOCOL_VERSION` constant to `llm/protocol.py` (a small integer or short string bumped only when the wire format actually changes — NOT derived from `package_version()`). The `hello` envelope carries the client's protocol version; `chirpd/server.py:_handle_hello` ([server.py:192](../../../../chirpd/server.py)) compares **protocol versions**. A cosmetic package bump (`0.0.1a0 → 0.0.1a1`) with an unchanged `PROTOCOL_VERSION` produces a `ready` handshake against a daemon spawned by the prior release — the warm model is **not** evicted. A genuine protocol-format change bumps `PROTOCOL_VERSION` and still triggers the existing exit-and-respawn path unchanged. `package_version()` may still be reported in `health`/`status` for diagnostics, but it MUST NOT gate the handshake. The existing `test_hello_with_matching_version_returns_ready` ([tests/chirpd/test_server.py:49](../../../../tests/chirpd/test_server.py)) and `test_hello_with_mismatched_version_returns_version_mismatch_and_daemon_exits` ([test_server.py:87](../../../../tests/chirpd/test_server.py)) are updated to drive protocol version, and a new test asserts a package-only skew handshakes `ready`.

- **AC-3 — Lock path derived from socket path so `CHIRP_DAEMON_SOCKET` truly isolates an instance.** `chirpd/__main__.py:main` ([__main__.py:48](../../../../chirpd/__main__.py)) passes a lock path derived from the resolved socket path into `single_instance_lock(lock_path=...)` (the parameter already exists, [lifecycle.py:24](../../../../chirpd/lifecycle.py)). The derivation is deterministic (e.g. sibling `<socket>.lock`, or a hash of the absolute socket path under `APP_SUPPORT_DIR`), and the default (no override) yields **exactly today's** `paths.LOCK_PATH` so the no-override path is byte-compatible. With `CHIRP_DAEMON_SOCKET=/tmp/chirpd-test.sock`, a second daemon acquires its **own** lock (not the global one), binds its socket, and serves — concurrently with the primary daemon on the default socket/lock. Two daemons on the **same** socket still contend (exactly one wins the flock; the loser exits 0).

- **AC-4 — Daemon rejects a duplicate in-flight request id; cancellation never cross-fires.** The chat handler (or `DaemonState.register_cancellation`) refuses to register a `request_id` that is **already in flight**: if `get_cancellation(request_id)` is non-`None` at chat-handler entry ([dispatcher.py:319](../../../../chirpd/dispatcher.py)), the daemon emits a typed protocol error (a new `PROTOCOL_REQUEST_CONFLICT` code in `llm/error_codes.py`, or a reuse with a clear message — implementer documents the choice) **before** loading/streaming, instead of silently overwriting the prior request's `should_stop` event. The `finally` `clear_cancellation` ([dispatcher.py:425](../../../../chirpd/dispatcher.py)) must only clear the entry **this** request registered (guard against clobbering a concurrently-registered same-id request — e.g. capture a token and verify identity before pop). The daemon continues to **echo** the client id (CHIRPD-CORE decision 5) — it does not invent or rewrite ids. A duplicate id can no longer (a) cross-cancel another request, nor (b) leave a request uncancellable because its event was overwritten.

- **AC-5 — Memory-pressure backpressure + embed idle/eviction policy.** Embed models no longer pin forever with no escape valve. Implement **one** of (implementer + maintainer pick; document the decision): (a) a configurable resident-model cap with LRU eviction when a new load would exceed it; (b) a memory-pressure check (e.g. against `psutil` available memory, reusing the `self._proc` instance already in `DaemonState`, [state.py:57](../../../../chirpd/state.py)) that evicts the LRU non-in-flight model before a load that would risk OOM; and/or (c) an opt-in idle policy for embed models. The chosen policy MUST respect the embed-pin contract — never idle-unload an embed model on a plain timer the way chat models unload; eviction is a deliberate memory-pressure / cap action, and a model holding its `LoadedModel.lock` (in-flight) is never evicted. An OOM that would otherwise surface as a generic `LLMModelLoadFailed` instead triggers an eviction-then-retry (or a typed, actionable error explaining the resident set is full). `status()` ([state.py:215](../../../../chirpd/state.py)) gains enough signal (resident count / cap, or eviction reason) for `chirp daemon status` to explain an eviction. **(OQ2 RESOLVED 2026-06-15: configurable resident cap — default 1 chat + 1 embed — with LRU eviction of non-in-flight models, falling back to a typed actionable error when every resident model is in-flight — see Dev notes.)**

- **AC-6 — Idle-unload does not race a long generation.** A chat generation that runs longer than `idle_timeout_s` does **not** get its model unloaded out from under (or immediately after) it. Fix by either: touching `last_used` at **stream start** (before/at the top of the `async with loaded.lock` block, [dispatcher.py:326](../../../../chirpd/dispatcher.py)) so the `_delayed_unload` guard at [state.py:293](../../../../chirpd/state.py) sees recent activity; **or** having `_delayed_unload` skip the unload while `model.lock.locked()` (contended) and reschedule. After this fix, a request whose generation exceeds the idle timeout completes and the model **remains resident** for the next request (no surprise reload). Verified with `FakeBackend(generation_delay_s=...)` and a short configured `idle_timeout_s` so the test runs fast.

- **AC-7 — A late cancel is graceful, not an error.** If `should_stop` is set **after** the generation loop has already exited normally (the full answer streamed and `done` would be emitted), `_handle_chat` ([dispatcher.py:379](../../../../chirpd/dispatcher.py)) classifies it as a normal completion — it emits `done` (with usage), **not** a `MODEL_CANCELLED` error event. Only a cancel that actually **interrupted** generation mid-stream (broke the loop before exhaustion) emits `MODEL_CANCELLED`. Distinguish the two (e.g. track whether the loop `break`ed on `should_stop` vs ran to exhaustion). The interactive consumer (`notes_chat/interactive.py:264`) therefore never prints a spurious red error after a fully-streamed answer.

- **AC-8 — Error-code fidelity preserved; mapping tidied.** Three fixes:
  - **Client unknown-code preservation.** `_exception_for_error_event` ([client.py:614–624](../../../../llm/client.py)) no longer swallows the daemon's `message` when the code is unknown. It raises a typed `LLMError`/`LLMProtocolError` whose message **includes the daemon's original message** (and code), so a version-skew error stays legible instead of becoming a bare `LLMMalformedResponse`.
  - **Dispatcher generic catch.** The outer `except Exception → MODEL_GENERATION_FAILED` ([dispatcher.py:98–117](../../../../chirpd/dispatcher.py)) is tightened so genuinely-non-model failures (e.g. a state/protocol bug) are not mislabeled as a generation failure — at minimum, map `LLMError` subtypes by their own `code` (as `_write_error_for_typed` already does for `LLMModelError`, [dispatcher.py:96–97](../../../../chirpd/dispatcher.py)) before the catch-all, and keep `MODEL_GENERATION_FAILED` only for true inference failures.
  - **Cancel-not-found code.** `cancel` ([dispatcher.py:539](../../../../chirpd/dispatcher.py)) stops reusing `MODEL_NOT_FOUND` for "no in-flight request to cancel"; introduce a dedicated code (e.g. `REQUEST_NOT_FOUND`) in `llm/error_codes.py` with its own `CODE_TO_EXCEPTION` mapping, so a failed cancel is not confused with a missing model.

- **AC-9 — Override-socket directory perms + chmod window.** When `CHIRP_DAEMON_SOCKET` points at a path whose parent does not yet exist (or is not `0700`), `serve()` (or startup) **creates and chmods the parent directory to `0o700`** before binding — matching `ensure_runtime_dirs()`'s treatment of `APP_SUPPORT_DIR` ([lifecycle.py:16–20](../../../../chirpd/lifecycle.py)). The window between socket bind ([server.py:43](../../../../chirpd/server.py)) and `chmod(0o600)` ([server.py:46](../../../../chirpd/server.py)) is tightened so the socket is never world-reachable (e.g. set umask before bind, bind into a `0700` parent, or create-and-chmod atomically). After startup, `stat` on the socket reports `0600` (preserving CHIRPD-CORE SC-9) and the parent dir reports `0700`, for both the default path and an override path.

- **AC-10 — Stale docstrings / messages corrected.**
  - `llm/cli/daemon.py` module docstring: drop the "eventual home … Story 5.6 wires … until then" framing; describe the *implemented* state (the subapp is wired into `chirp/cli.py` and all subcommands exist).
  - `llm/cli/models.py` module docstring: drop "eventual home … Story 4.3 adds `add`…" narrative; describe the implemented command set.
  - `llm/registry.py:77–80` schema-version error message: stop pointing at the nonexistent `chirp models init`; point users at `chirp models add` (the real registry entry point) and drop the "(coming in EPIC-MODEL-REGISTRY)" parenthetical (that epic shipped).

- **AC-11 — Quality gates.** `make check` and `make test` pass. `mypy` clean on `chirpd/` and `llm/`. New behavior is covered by tests (AC-1…AC-9). No regression in the existing `tests/chirpd/*` and `tests/llm/*` suites; the unchanged-default paths (no env override) behave byte-identically (lock path, socket path, handshake on equal versions).

## Dev notes

- **Re-verify before you trust line numbers.** Per project memory (`project_daemon_lifecycle_contract_drift`, `project_integration_cutover_client_drift`), the daemon/client surface has drifted from prior specs. Every line number in this story was re-checked against `main` on 2026-06-14, but re-open `chirpd/dispatcher.py`, `chirpd/state.py`, `chirpd/server.py`, `llm/client.py` before editing — the real API is `chat_stream_sync(...) → Iterator[str]` and `cancel_sync(target_id)`, the dispatcher requires a **string** `request_id` for chat, and `stream_generate(handle, messages, options, should_stop, usage_out)` takes a 5-arg signature (the dispatcher passes `usage_out` as the 5th arg, [dispatcher.py:328–329](../../../../chirpd/dispatcher.py)).
- **PROTOCOL_VERSION design (AC-2).** The wire format hasn't changed since CHIRPD-CORE shipped, so seed `PROTOCOL_VERSION = 1` (or `"1"`). The whole point: it changes **only** when the envelope/op/event grammar changes, decoupled from the marketing/package version. The existing exit-on-mismatch + lazy-respawn machinery (CHIRPD-CORE decision 4) is preserved unchanged — we only change the comparand. Keep reporting `package_version` in `health`/`status` so `chirp daemon status` still shows the human-facing version.
- **Lock-path derivation rationale (AC-3).** The lock exists to enforce single-instance *per socket*, but today it's keyed to a global constant while the socket is overridable — the two keys disagree, which is the bug. Deriving the lock from the socket path realigns them: one socket ⇒ one lock ⇒ one daemon, and a different socket ⇒ a different lock ⇒ a genuinely separate daemon. **Default-path invariance is a hard requirement** — when `CHIRP_DAEMON_SOCKET` is unset, the derived lock MUST equal today's `paths.LOCK_PATH` so existing installs and the LaunchAgent see no change. Prefer a readable sibling (`<socket-stem>.lock` next to the socket) over a hash if the override socket lives in a writable dir; fall back to a hash under `APP_SUPPORT_DIR` if the override parent might be read-only. The `single_instance_lock` parameter already exists and `mkdir`s the lock's parent ([lifecycle.py:34](../../../../chirpd/lifecycle.py)) — so passing a derived path is a one-line caller change plus the helper.
- **What NOT to do.**
  - Do **not** make the inference timeout per-whole-request — a healthy long answer must not trip it. It is a per-inter-event idle bound; a generous default (tens of seconds) only fires when a *stalled* daemon stops emitting anything.
  - Do **not** regenerate or rewrite the client request id on the daemon to solve the duplicate-id problem — CHIRPD-CORE decision 5 mandates the daemon echoes, never invents. Reject the duplicate instead.
  - Do **not** idle-unload embed models on a plain timer — that violates the FR6 pin. Eviction under memory pressure is a separate, deliberate policy and must skip in-flight (lock-held) models.
  - Do **not** change the exit-on-version-mismatch behavior (no drain) — alpha simplification is locked (CHIRPD-CORE decision 4); only the comparand changes.
  - Do **not** add network calls, telemetry, or a wire `shutdown` op — shutdown is signal-based (`SIGTERM`/`SIGINT` in `chirpd/__main__.py:81`), and NFR-S3 forbids network traffic.
- **Audit accuracy notes (what was confirmed / refined).** All ten findings reproduce against `main`. Refinements: (finding #4) the real interactive `ask` call site generates a **fresh** id per query (`notes_chat/prompting.py:175` → `:117`), so today's call site doesn't itself cross-cancel — the defect is that the daemon *trusts the client key* and would mis-handle a duplicate/reused id from any client; the fix hardens the daemon, it is not fixing a current crash. (finding #6) `load()` reschedules the chat idle timer at load *and* the `finally` reschedules post-completion ([dispatcher.py:427](../../../../chirpd/dispatcher.py)) — the race window is the single scheduled `_delayed_unload` task whose sleep elapses *during* a long generation while it waits on `model.lock`; `schedule_idle_unload` already cancels prior tasks, so this is the only window. (finding #10) `daemon_app`/`models_app` are confirmed wired (`chirp/cli.py:531`, `:536`) — the docstrings are merely stale narrative, not a wiring gap; `chirp models init` confirmed nonexistent.
- **Idle-timeout / env precedent.** `config/settings.py` already implements the env→config→default resolution for idle timeout (`CHIRP_MODEL_IDLE_TIMEOUT`, [settings.py:13/23–40](../../../../config/settings.py)). The inference-timeout config MUST follow that exact shape, including the bare-`except Exception` fallback comment "config failures must not block daemon start".
- **OQ1 — inference-timeout default.** Proposed default: **60 s** per inter-event read (generous — a healthy stream emits a token every few hundred ms; 60 s only fires on a genuinely wedged daemon). Confirm with maintainer; a too-tight default risks false trips on a cold model load that takes several seconds to first token (the *first* read after sending the request spans the load + first-token latency, which CHIRPD-CORE SC-3 budgets at up to ~10 s cold). Consider a separate, larger budget for the **first** event vs subsequent deltas if a single value can't cover both.
- **OQ2 — memory-pressure policy.** Evict-LRU-then-retry (transparent, but can thrash with two large models alternating) vs typed-error-on-pressure (predictable, but surfaces a failure the user must resolve). Recommend a configurable resident cap (default generous, e.g. 1 chat + 1 embed) with LRU eviction of non-in-flight models, falling back to a typed actionable error if every resident model is locked/in-flight.
