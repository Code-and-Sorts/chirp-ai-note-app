# Story 8.2 — Retrieval & note-generation correctness and scale

- **Status:** ready-for-dev
- **Epic:** [EPIC-PRODUCTION-HARDENING](../epic.md)
- **Depends on:** —
- **Blocks:** —

## User story

As a user who asks "what changed last week?", I want the time filter to key off the actual **meeting date** (not the file's mtime) and I want the most relevant notes back — not whichever source happened to produce a numerically larger raw score — so that `chirp ask "what did we decide last week" --when "last week"` returns the right meetings and the right answer.

As a user with ~5k notes, I want `chirp ask` to stay fast: it should not re-`stat()` every note, re-read and re-tokenize the entire BM25 corpus, and rebuild the lexicon from scratch on every single query and every single note save — so that retrieval stays sub-second on a real corpus, not just a demo-sized one.

As a user who switches chat or embed models (`chirp models default <alias>`) or edits the system prompt, I want the answer cache to recognize that the inputs changed and recompute — so I never get a stale answer generated by the old model or the old prompt.

## Context

`chirp ask` is the headline retrieval feature. Its design docs promise true hybrid fusion and correct time filtering; the current implementation delivers neither, and it does not scale past a demo corpus. This story closes the RAG correctness/scale gaps and the note-generation correctness gaps owned by 8.2 in the [epic findings → story map](../epic.md#3-findings--story-map). Two of the gaps (fusion, date extraction) were verified directly in source during the 2026-06-14 audit and are re-verified below with current line numbers.

The retrieval path is: `notes_chat/cli.py` `ask` → `retrieve_context` (`notes_chat/retrieval.py:17`) → `build_index(force=False)` (freshness) → `_search_chroma` + `_search_bm25` → `_merge_and_dedupe` → `_build_context` → grounded answer via `notes_chat/prompting.py`. Indexing is `notes_chat/index.py` `IndexManager.build_index`; the lexical side is `notes_chat/bm25.py`; the answer cache is `notes_chat/cache.py`. Note generation is `notes/note_generator.py` (which also auto-indexes on save). Time parsing is `notes_chat/time_ranges.py`.

Design docs this story must satisfy:

- `.docs/hybrid-retrieval.md` — "Fusion: simple score normalization or Reciprocal Rank Fusion (RRF) keeps logic robust." [Source: .docs/hybrid-retrieval.md#tuning-tips]
- `.docs/embeddings.md` — invites swapping the embed model behind a stable call site; `content_hash` unchanged, "only the embedding vectors change." [Source: .docs/embeddings.md#extensibility]
- `.docs/chunking.md` — `content_hash` is the stable dedupe signature; do not change it. [Source: .docs/chunking.md#edge-cases--notes]

Files in scope:

- **`notes_chat/retrieval.py`** — fusion, tz-aware where-clause, per-query scaling, bare `except:`.
- **`notes_chat/index.py`** — date extraction, atomic `--force`, manifest/Chroma drift, embed-model fingerprint, BM25 rebuild cadence.
- **`notes_chat/bm25.py`** — per-query reload/re-tokenize/reconstruct.
- **`notes_chat/cache.py`** — cache key, TTL/eviction, clear-on-`--force`.
- **`notes/note_generator.py`** — transcript cap, auto-index drift, XML-parse junk-note.
- **`notes_chat/prompting.py`** — question length-bound + delimiting; keep grounding guardrails.
- **`utils/file_utils.py`** — `_resolve_created_at` is the existing canonical date convention to reuse (read-only reference; do not change its contract).
- **Tests** — `tests/test_retrieval_coverage.py`, `tests/test_retrieval_merge.py`, `tests/test_cache.py`, `tests/test_note_generator.py`, plus new fusion/date/scale tests.

## Acceptance criteria

- **AC-1 — Hybrid fusion no longer starves semantic hits (Finding 1, HIGH, VERIFIED).** `_merge_and_dedupe` (`notes_chat/retrieval.py:158-188`) currently concatenates Chroma results — whose score is `1.0 - cosine_distance` (`retrieval.py:126`, range ~0..1) — with **raw, unbounded** BM25 scores (`BM25Okapi.get_scores`, `notes_chat/bm25.py:69`) and sorts by raw score (`retrieval.py:174`). With no normalization and no rank fusion, any BM25 hit with a raw score > 1.0 outranks every semantic hit (the existing `test_merge_score_ordering` even asserts a raw BM25 `1.5` beats a semantic `0.95`). Replace the raw-score sort with **Reciprocal Rank Fusion** (default; `score = Σ 1/(k_rrf + rank_i)` across sources, `k_rrf = 60`) so a chunk's contribution is its **rank** in each list, not its source-specific magnitude. Dedupe by `(path, content_hash)` is preserved exactly; the fused score is attached for ordering only. After the change, a top-ranked semantic chunk and a top-ranked BM25 chunk are interleaved by rank, not dominated by BM25's scale. `.docs/hybrid-retrieval.md` promises this. [Source: .docs/hybrid-retrieval.md#tuning-tips]

- **AC-2 — Time-range filtering keys off the meeting date, not file mtime (Finding 2, HIGH, VERIFIED).** `_extract_metadata` (`notes_chat/index.py:208-247`) parses the date with `re.search(r"(\d{4}-\d{2}-\d{2})", file_path.name)` (`index.py:214`). Notes live at `<slug>/notes.md`, so `file_path.name` is **always** `"notes.md"` → the regex never matches → the date falls back to **file mtime** (`index.py:217-219`). Fix: derive the date from the canonical meeting-date source — reuse the existing convention in `utils/file_utils.py` `_resolve_created_at` (`file_utils.py:121`), which prefers `meta.toml`'s `date` and falls back to the dated slug / dir mtime — instead of regexing `notes.md`. After the change, a note whose `meta.toml`/slug says `2025-01-15` but whose `notes.md` was last touched today indexes its `date` metadata as `2025-01-15`, and `--when "on:2025-01-15"` finds it.

- **AC-3 — Stored dates and where-clause dates are tz-consistent (Finding 2 compound, HIGH, VERIFIED).** The stored `date` metadata is **naive** (`index.py:348` `chunk.meta.date.isoformat()`, and `meta.date` originates as a naive `datetime` at `index.py:216`/`219`), while the time-range `where` clause builds **tz-aware** ISO strings (`retrieval.py:94-98` from `time_ranges.parse_time_range`, which uses `datetime.now(tz.tzlocal())` at `time_ranges.py:20`). Chroma compares these strings **lexicographically**, so `"2025-01-15T00:00:00"` vs `"2025-01-15T00:00:00-08:00"` mis-compare and the filter is inconsistent. Standardize on **naive local** datetimes end-to-end (matching `_resolve_created_at`'s `_as_naive` convention, `file_utils.py:124/129`): store naive ISO in metadata **and** strip tzinfo from the where-clause bounds (or build both from the same naive-local source). After the change, the stored `date` string and the `$gte`/`$lt` bounds have identical shape and the lexical comparison is correct.

- **AC-4 — Un-mocked tests catch Findings 1 & 2 (Finding 3, TEST GAP).** The current suite hides both bugs: `tests/test_retrieval_coverage.py` mocks `_search_chroma`/`_get_query_embedding` and feeds `isoformat`-stubbed naive strings (`test_builds_where_clause_when_time_range_provided`, ~`:243-264`), and `tests/test_retrieval_merge.py` asserts the **buggy** raw-score ordering (`test_merge_score_ordering` `:146-185` asserts BM25 `1.5` outranks semantic `0.95`). Add tests that exercise the real code paths: (a) real date extraction from a `<slug>/notes.md` fixture with a stale mtime, asserting the indexed `date` equals the meeting date; (b) real fusion ordering on the new RRF, asserting a top-ranked semantic chunk is not buried under a high-magnitude BM25 chunk; (c) tz-consistency: the stored metadata date string and the where-clause bound string have matching shape. Rewrite (do not delete) `test_merge_score_ordering` to assert the new RRF behavior.

- **AC-5 — Per-query work is bounded; the BM25 model is cached (Finding 4, MED).** Today every query: (a) calls `build_index(force=False)` (`retrieval.py:32`) which `stat()`s every `*/notes.md` (`index.py:131-137`); (b) constructs a fresh `BM25Index(bm25_file)` (`retrieval.py:146`) whose `load()` re-reads the full JSON, re-tokenizes the whole corpus, and reconstructs `BM25Okapi` (`bm25.py:20-34`); (c) runs a **second** full notes scan via `_build_note_index` → `list_notes` (`retrieval.py:238-251`). Reduce per-query cost: cache/persist the constructed `BM25Okapi` (or the tokenized corpus) keyed by the bm25.json mtime/hash so an unchanged index is not re-tokenized; make the freshness check cheap (e.g. a lightweight signature/short-circuit instead of a full stat sweep on every query); and cache the slug→display-index map for the duration of a query rather than scanning notes twice. Measured against a synthetic corpus, repeated queries against an unchanged index must not re-tokenize the corpus or re-scan the notes tree more than once.

- **AC-6 — BM25 rebuild is decoupled from per-note save (Finding 4, MED).** `_rebuild_bm25` (`index.py:354-362` → `bm25.py:86-112`) pulls the **entire** Chroma collection into memory (`chroma_collection.get()`, `bm25.py:89`), re-tokenizes everything, and rewrites `bm25.json` — and it runs after **every** `build_index` (`index.py:95`) **and** after **every** auto-indexed note save (`note_generator.py:498`). Batch/defer the rebuild so a single note save does not trigger a full-corpus re-tokenize and rewrite (e.g. incremental append to the lexicon, or a deferred/coalesced rebuild). A burst of N note saves must not perform N full-corpus rebuilds.

- **AC-7 — Cache key includes model + embed + prompt-version; cache is bounded; `--force` clears it (Finding 5, MED).** `_generate_cache_key` (`notes_chat/cache.py:57-62`) hashes only `question + sorted(retrieved_ids)`, so after a `chirp models default <alias>` switch or a `SYSTEM_PROMPT`/grounded-prompt edit the cache returns a **stale** answer generated by the old model/prompt. Include the resolved chat model, the resolved embed model, and a prompt-version token in the key. Add TTL/size-based eviction so `cache/*.json` cannot grow unbounded (`cache.py:36-48` writes one file per key, never evicts). Wire `clear_cache` (`cache.py:65`, currently called by **no** production code — only tests) into the `--force` reindex path so a forced rebuild invalidates the cache.

- **AC-8 — `--force` rebuild is atomic (Finding 6, MED).** `_reset_index` (`index.py:109-123`) deletes the Chroma collection, then unlinks `manifest.json` and `bm25.json` **up front**, then re-adds notes one by one. A crash/Ctrl-C mid-rebuild leaves a partial collection, no manifest, and no bm25.json → the next `ask` hits `if not index_manager.manifest_file.exists()` (`retrieval.py:24`) and reports "No search index found". Build the new index into a temp location and atomically swap it into place (or make the rebuild transactional) so an interrupted `--force` leaves the previous working index intact.

- **AC-9 — Only successfully-indexed files are recorded in the manifest (Finding 7, MED).** `build_index` writes `new_manifest = current_files` **wholesale** (`index.py:93-94`) after the add loop, but `_add_to_index` returns `False` on embedding failure **without aborting** (`index.py:176-180`) — so a file that failed to embed is still recorded as indexed and, because its signature now matches, is **never retried**. The auto-index path has the same shape (`note_generator.py:487-496`). Record in the manifest only files that actually indexed successfully; surface (log/print) which files failed so a failed embed is retried on the next run.

- **AC-10 — Embedding dimension / model mismatch is detected, not silently wrong (Finding 8, MED).** The Chroma collection is created once with cosine space (`index.py:35-37`/`116-118`) and never records which embed model/dimension produced its vectors. `.docs/embeddings.md` explicitly invites swapping the embed model. New-dimension vectors raise inside `collection.add` (swallowed as a generic "Failed to index", `index.py:191-194`), and querying a new-dim query against old vectors silently returns garbage. Store an embed-model fingerprint (resolved embed alias + vector dimension) in the collection metadata; on index/query, detect a mismatch and either auto-reset (rebuild from scratch) or fail with an actionable message ("embed model changed; run `chirp index --force`"). Do not change `content_hash`. [Source: .docs/embeddings.md#extensibility]

- **AC-11 — Long transcripts are windowed; the question is length-bounded and delimited (Finding 9, MED).** Note generation injects the **entire** transcript into the prompt (`note_generator.py:342-349`) with only a **lower** bound (reject `< 50` chars, `note_generator.py:217`) and no upper cap; only the **output** is bounded (`num_predict`/`max_tokens`, `note_generator.py:363`), so a long transcript is silently truncated by the model mid-generation. Cap/window the transcript before generation and **warn** when truncating. Separately, the user `question` is interpolated **raw** into `SYSTEM_PROMPT.format(...)` (`notes_chat/prompting.py:46`) and `_grounded_answer_prompt` (`prompting.py:88`) with no length cap and no delimiting. Length-bound the question and delimit it (so a question that contains prompt-shaped text cannot smuggle instructions), and **keep** the existing grounding guardrails prose (`prompting.py:14-20`) intact.

- **AC-12 — XML-parse fallback does not write/index a junk note (Finding 10, MED).** `_parse_fallback_response` (`note_generator.py:463-477`) returns a note whose `executive_summary` is the first 200 chars of raw output and whose only highlight is the literal `"Unable to parse structured notes from AI response"` — which `_generate_for_record` then **writes to disk and auto-indexes** (`note_generator.py:257-259`), polluting retrieval. Retry the structured generation once on parse failure; if it still fails, mark the note **degraded** and **skip** writing/indexing it, and surface the degradation to the user (don't silently emit a junk note that later poisons `ask`).

- **AC-13 — No bare `except:` in retrieval (Finding 11, LOW).** `_create_chunk_header` (`retrieval.py:348`) and `_generate_suggestion`'s manifest read (`retrieval.py:372`) use bare `except:` which swallow `KeyboardInterrupt`/`SystemExit`. Narrow both to `except Exception`.

- **AC-14 — Quality gates.** `make check` and `make test` pass. New behavior is covered by the AC-4 un-mocked tests plus the fusion-ordering, date-filter, and scale-smoke tests in the Testing section. No test asserts the old raw-score ordering or the old mtime-derived date.

## Implementation tasks

1. **RRF fusion (AC-1).** In `_merge_and_dedupe`, compute each chunk's rank within its source list (Chroma list and BM25 list are each already rank-ordered), fuse with RRF (`k_rrf = 60`), dedupe by `(path, content_hash)` keeping the best-ranked instance, and order by fused score. Keep the existing `signature` dedupe and the `source` tagging. Do not alter `_build_context`'s budgeting.

2. **Meeting-date extraction (AC-2).** Replace the `re.search(... file_path.name)` date logic in `_extract_metadata` with a call into the canonical date source. Prefer reusing `utils/file_utils._resolve_created_at` (it already reads `meta.toml`'s `date`, falls back to the dated slug dir / mtime, and returns **naive**). If a direct reuse is awkward from `index.py`, factor a small shared helper rather than duplicating the slug/meta parsing — but keep `_resolve_created_at`'s contract unchanged.

3. **Datetime standardization (AC-3).** Make stored metadata dates and where-clause bounds the same shape — **naive local**. Either strip tzinfo when building the where clause in `_search_chroma`, or build the where clause from a naive-local conversion of the `TimeRange`. Verify the stored `_chunk_to_metadata` date (`index.py:348`) and the bound strings match shape.

4. **Per-query scaling (AC-5).** Cache the constructed `BM25Okapi` / tokenized corpus keyed by `bm25.json` mtime+size (invalidate on change); make `retrieve_context`'s freshness step cheap (avoid a full stat sweep on every query — e.g. short-circuit when a cheap signature is unchanged); compute the slug→display-index map once per query (don't scan notes in both `_build_note_index` and elsewhere).

5. **BM25 rebuild cadence (AC-6).** Decouple `_rebuild_bm25` from single-note saves: append incrementally to the lexicon on auto-index, or coalesce/defer the full rebuild. Ensure a burst of saves doesn't trigger one full-corpus rebuild per save.

6. **Cache hardening (AC-7).** Extend `_generate_cache_key` to include resolved chat model, resolved embed model (from the registry — `default_chat`/`default_embed` resolution lives in `llm/registry.py:resolve_alias`), and a prompt-version constant bumped whenever `SYSTEM_PROMPT`/grounded prompt changes. Add TTL or LRU/size eviction to `cache_answer`. Call `clear_cache()` from the `--force` index path.

7. **Atomic `--force` (AC-8).** Rework `_reset_index`/`build_index(force=True)` to build into a temp dir/collection and swap atomically, leaving the prior index intact on interruption.

8. **Manifest correctness (AC-9).** In `build_index`, accumulate only files for which `_add_to_index` returned `True` into the saved manifest (don't write `current_files` wholesale). Mirror the fix in `_auto_index_note`. Surface failed files.

9. **Embed-model fingerprint (AC-10).** Write the resolved embed alias + vector dimension into the Chroma collection metadata on creation; on build/query detect mismatch and auto-reset or raise an actionable error. Keep `content_hash` stable.

10. **Transcript window + question bounding (AC-11).** Add an upper bound / windowing to `_generate_structured_notes` with a truncation warning; length-bound + delimit `question` in `build_chat_messages` and `_grounded_answer_prompt`. Leave guardrail prose intact.

11. **Degraded-note handling (AC-12).** Retry once in `_parse_xml_response`/`_generate_structured_notes`; on persistent failure, return a degraded result that `_generate_for_record` does **not** write/index, and surface it to the user.

12. **Narrow bare excepts (AC-13).** Change the two bare `except:` blocks in `retrieval.py` to `except Exception`.

13. **Tests (AC-4, AC-14).** Add the un-mocked date/fusion/tz tests; rewrite the mocked seams that hid the bugs; add scale-smoke tests. See Testing.

## Dev notes

- **RRF vs min-max normalization (AC-1).** RRF is the default choice: it's parameter-light (`k_rrf=60` is the canonical value), needs no per-source score statistics, is robust to the BM25 scale being unbounded, and matches what `.docs/hybrid-retrieval.md` names first-class. Min-max normalization per source is the documented alternative; it's acceptable but more fragile (a single outlier BM25 score skews the normalization, and a one-result list degenerates). Pick RRF. If a weighted blend is later wanted, RRF accepts a per-source weight (`Σ wᵢ/(k_rrf+rankᵢ)`) — the audit notes `.docs/hybrid-retrieval.md`'s "boost BM25 weight for ID-heavy queries" as a future routing hook, **out of scope** here.
- **alpha tradeoffs.** Don't introduce a tunable `alpha`/weight knob in this story unless an AC needs it — equal-weight RRF is the baseline. Adding config surface (and a `config/settings.py` field) is scope creep; the epic's CLI/config story (8.6) owns config resilience.
- **Where the canonical meeting date lives (AC-2).** It is **not** `notes.md`'s name, and it is **not** reliably the last token of the slug (collision suffixes append `-2`, `-3` — see `slugify`, `file_utils.py:48-51`). The authoritative source already exists: `_resolve_created_at` (`file_utils.py:121-135`) prefers `meta.toml`'s `date`, then falls back to parsing the dir / mtime. Reuse it; do not re-implement slug-date parsing. `meta.toml` is written by `note_generator._update_meta` (`note_generator.py:268-284`) and the front-matter `note_date` by `_format_generated_note` (`note_generator.py:286-292`).
- **datetime standardization decision (AC-3).** Standardize on **naive local**, not tz-aware. Rationale: the stored dates are already naive (`_chunk_to_metadata` → `meta.date` naive), `_resolve_created_at` deliberately returns naive (`_as_naive`), and Chroma's metadata filter is a **lexical string** comparison — the cheapest correct fix is to make both sides naive-local so the strings sort consistently. Converting everything to aware-UTC would also work but requires touching `_resolve_created_at`'s public contract and re-indexing; avoid that.
- **scale strategy (AC-5/AC-6).** The cheap wins: (1) don't reconstruct `BM25Okapi` when `bm25.json` is unchanged; (2) don't rebuild the entire lexicon on a single note save; (3) don't scan the notes tree twice per query. Persisting the `BM25Okapi` object is fine in-process; across processes, cache the tokenized corpus + a fingerprint so reload skips re-tokenization. Note: `bm25.py`'s `BM25Okapi` is built once in the constructor's `load()` (not per `get_scores` call), so the cost is in `BM25Index(bm25_file)` per query (`retrieval.py:146`), not inside `search`.
- **What NOT to do.** Don't change `content_hash` or the chunking algorithm (`.docs/chunking.md` and dedupe depend on stable hashes). Don't add a tz/`alpha`/embed-model **config field** (8.6 owns config). Don't widen scope into the daemon read-timeout (8.3 owns the `llm.client` seam) — if a stalled daemon hangs `ask`, that's 8.3. Don't delete the mocked tests wholesale; rewrite them so the seams exercise real code. Don't "fix" the cache by disabling it — the goal is correct keying + bounding, not removal.
- **If a finding is already fixed at execution time:** re-grep before implementing each AC (line numbers drift). If, e.g., `_merge_and_dedupe` already does RRF or `_extract_metadata` already reads `meta.toml`, note it in the Dev Agent Record and skip that AC rather than re-doing it.

## Testing

- **Replace the mocked seams (AC-4).** `tests/test_retrieval_coverage.py::test_builds_where_clause_when_time_range_provided` (~`:243-264`) stubs `isoformat` with naive strings and mocks `_get_query_embedding` away — it never sees the tz mismatch. Add a companion test that drives the **real** `TimeRange` from `time_ranges.parse_time_range` through `_search_chroma`'s where-clause builder and asserts the bound strings match the stored metadata-date shape. `tests/test_retrieval_merge.py::test_merge_score_ordering` (`:146-185`) asserts the **buggy** raw ordering (BM25 `1.5` > semantic `0.95`) — rewrite it to assert RRF ordering (rank-interleaved, not magnitude-dominated). Keep `test_dedupe_by_path_and_content_hash` and the `_build_context` budgeting tests as-is.
- **Fusion-ordering test.** Construct Chroma + BM25 result lists where the raw BM25 scores dwarf the semantic scores; assert the top semantic chunk survives into the top of the fused list (it would be buried under the old code). Cover the dedupe-across-sources case (same `(path, content_hash)` from both lists collapses, best rank wins).
- **Date-filter test (un-mocked).** Create a real `<slug-2025-01-15>/notes.md` + `meta.toml` fixture, `os.utime` the `notes.md` to a different day, run `_extract_metadata`/index, and assert the stored `date` equals `2025-01-15` (today's mtime must NOT leak in). Then assert `--when "on:2025-01-15"` retrieves it and `--when "on:<mtime-day>"` does not.
- **Scale-smoke test.** Synthesize a corpus of N notes; assert that repeated `retrieve_context` calls against an **unchanged** index do not re-tokenize the BM25 corpus or scan the notes tree more than once (patch/spy the tokenizer + `list_notes` and count calls). Assert a burst of auto-index saves doesn't trigger one full-corpus rebuild per save (spy `rebuild_bm25_index` / the corpus tokenizer).
- **Cache-keying test.** Extend `tests/test_cache.py`: same question + same retrieved_ids but different resolved chat model (or bumped prompt version) → different cache key → no stale hit. Add an eviction/TTL test. Add a test that `--force` reindex clears the cache.
- **Manifest-correctness test.** Simulate `_add_to_index` returning `False` (embedding failure) for one file; assert that file is **not** in the saved manifest and is retried on the next `build_index`.
- **Atomic-rebuild test.** Simulate an interruption mid-`--force` (raise inside the add loop); assert the previous manifest/collection/bm25 are still usable (next `ask` does not report "No search index found").
- **Embed-fingerprint test.** Index with a fake embed model/dimension, change the fingerprint, and assert the mismatch is detected (auto-reset or actionable error) rather than silently querying mismatched vectors.
- **Note-generation tests.** XML-parse-failure path retries once and, on persistent failure, does **not** write/index a junk note (assert no `notes.md` written, no auto-index, degradation surfaced). Long-transcript path warns and windows rather than silently truncating.
