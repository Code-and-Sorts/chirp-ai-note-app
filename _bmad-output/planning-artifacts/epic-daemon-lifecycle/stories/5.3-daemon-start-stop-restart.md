# Story 5.3 — `chirp daemon start | stop | restart`: manual lifecycle controls

- **Status:** Draft
- **Epic:** [EPIC-DAEMON-LIFECYCLE](../epic.md)
- **Depends on:** 5.2 (the `daemon_app` Typer instance and the `LLMClient` interaction pattern exist in `llm/cli/daemon.py`); EPIC-CHIRPD-CORE (lazy-spawn via `chirpd` console script; shutdown op or signal-based stop path; `flock` single-instance enforcement)
- **Blocks:** 5.6 (Typer registration)

## User story

As Sam, when I'm troubleshooting something — I just edited `models.toml`, I just did a `pip install -U chirp`, I'm trying to reproduce a bug — I want explicit `chirp daemon start`, `stop`, and `restart` commands so I don't have to remember `pkill chirpd` or `launchctl kickstart` semantics. These commands should be idempotent (running `start` when already running is a no-op, not an error) and prompt (no waiting for in-flight requests to finish — alpha simplification).

## Context

The PRD describes these as "rarely needed; lazy handles it" (§CLI Tool Specific Requirements → Command Structure). They exist for the cases where lazy-spawn isn't enough:

- **`start`** — when you want the daemon up *now*, not on next `chirp ask`. Useful before running a script that needs a warm daemon.
- **`stop`** — when you want to free RAM, or when you want to reset state. Per FR41 and PRD §Alpha-stage simplifications: **no graceful drain**. In-flight requests at the moment of `stop` fail with `MODEL_GENERATION_FAILED` cause `daemon_shutdown`. The CLI surfaces this clearly.
- **`restart`** — `stop` + `start`. Useful after editing `models.toml`, since the daemon does not hot-reload (PRD §Out of Scope).

CHIRPD-CORE delivers the building blocks:

- The `chirpd` console script on PATH, lazy-spawnable via `subprocess.Popen(["chirpd"], start_new_session=True)`.
- The `flock` lockfile that guarantees single-instance — running `start` when already running results in the second process exiting cleanly within 1 s (NFR-R4).
- A shutdown mechanism. The architecture's wire protocol does not list a public `shutdown` op explicitly, but the daemon must support an authenticated-via-local-socket shutdown to let `chirp daemon stop` work without resorting to PID-based signals. **This story assumes CHIRPD-CORE exposes either:** (a) a `shutdown` op on the wire protocol that triggers immediate `exit(0)`, or (b) the CLI sends `SIGTERM` to the PID reported by `health`, and the daemon's signal handler triggers a clean asyncio loop stop. Either is acceptable; this story uses whichever CHIRPD-CORE ships. Default assumption: option (b), since signals are simpler and the daemon's flock-based startup already implies a stable PID-on-disk model.

The commands share file structure with story 5.2's `status`: they live in `llm/cli/daemon.py`, use `llm.client.LLMClient` for any socket-based interaction, and rely on the Typer outer wrapper for exit-code mapping.

## Acceptance criteria

- **AC-1** `llm/cli/daemon.py` defines three new commands on `daemon_app`: `start`, `stop`, `restart`. Each is a separate `@daemon_app.command(...)` function with its own help text. Implements FR40, FR41, FR42.

- **AC-2** **`chirp daemon start` semantics.**
  - If the daemon is already running (lazy `LLMClient.health()` returns OK), prints `daemon is already running` to stderr, exits 0. **Idempotent.**
  - Otherwise spawns `chirpd` via `subprocess.Popen([shutil.which("chirpd")], start_new_session=True, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)`. Closes the parent's relation to the new process's stdio; the daemon writes to its own log file per story 5.1.
  - Polls the socket path (`~/Library/Application Support/chirp/chirpd.sock`) with 50 ms backoff for up to 5 s (matches lazy-spawn timeout in CHIRPD-CORE).
  - On socket-accepting, issues one `health` request to confirm. On success, prints `daemon started (pid=<int>)` to stdout (or `pid <int>` on the `--json` form — see AC-9). Exits 0.
  - On timeout: prints `daemon failed to start within 5 seconds — check ~/Library/Logs/chirp/chirpd.log` to stderr. Exits 1.
  - If `shutil.which("chirpd")` returns None: prints `chirpd binary not found on PATH — is chirp installed correctly?` to stderr. Exits 1.

- **AC-3** **`chirp daemon stop` semantics.**
  - If the daemon is not running (`LLMClient.health()` raises `LLMDaemonUnreachable` and lazy-spawn is suppressed for `stop`): prints `daemon is not running` to stderr, exits 0. **Idempotent.**
  - If the daemon is running, retrieves `pid` from `health`, then triggers shutdown. Two paths depending on what CHIRPD-CORE delivers:
    - **Preferred (op-based):** issues a `shutdown` op via `LLMClient.shutdown()`. The daemon responds `done` and exits within 2 s.
    - **Fallback (signal-based):** sends `SIGTERM` via `os.kill(pid, signal.SIGTERM)`. The daemon's signal handler stops the asyncio loop; exits 0 within 2 s.
  - Polls the socket path for up to 5 s, expecting it to disappear (or refuse connections) as the daemon exits. On success, prints `daemon stopped` to stdout, exits 0.
  - On timeout: escalates with `SIGKILL` after 5 s if the process is still alive (defensive), then prints `daemon did not stop within 5 seconds — sent SIGKILL` to stderr. Exits 1.
  - Implements FR41, NFR-R6.

- **AC-4** **`chirp daemon stop` does NOT lazy-spawn.** The `LLMClient` used in `stop` must be configured with `lazy_spawn=False` (or equivalent — coordinate with CHIRPD-CORE's client API). It would be absurd to spawn a daemon just to ask it to stop. If the daemon isn't running, the command says so and exits.

- **AC-5** **In-flight request behavior on `stop` (alpha simplification — document explicitly).** When `chirp daemon stop` is invoked while another CLI invocation has a streaming `chat` in flight against the daemon:
  - The daemon exits immediately. No drain.
  - The in-flight `chat`'s socket connection is closed mid-stream. The client (in the other CLI process) raises `LLMConnectionLost` and the CLI maps it to a user-facing error containing the code `MODEL_GENERATION_FAILED` with cause `daemon_shutdown`.
  - This story's `stop` command does NOT print a special warning about in-flight requests; it just stops. The other CLI process surfaces its own error.
  - Implements PRD §Alpha-stage simplifications, NFR-R6.

- **AC-6** **`chirp daemon restart` semantics.** Sequentially runs the equivalent of `stop` then `start`:
  - If the daemon is not running, prints `daemon is not running — starting fresh instance...` to stderr, then runs the `start` path. Exit code matches `start`.
  - If the daemon is running, runs the `stop` path. On success, immediately runs the `start` path (with a small 100 ms sleep to give the socket cleanup time to complete). On combined success, prints `daemon restarted (pid=<int>)` to stdout. Exit code 0.
  - On `stop` failure: prints the `stop` failure message and exits 1 — does NOT attempt `start`.
  - On `start` failure (post-`stop`): prints `daemon was stopped but did not restart — check ~/Library/Logs/chirp/chirpd.log` to stderr. Exits 1.
  - Implements FR42.

- **AC-7** **No silent state.** None of the three commands touch `models.toml`, `~/.chirp/config.toml`, the chroma index, or any user data. They only manage the process. (Defensive note for reviewers.)

- **AC-8** **Diagnostic logging via `log_op_event`.** Each command emits one logfmt line on completion:
  - `start`: `op=daemon_start duration_ms=<int> result=spawned|already_running|failed`
  - `stop`: `op=daemon_stop duration_ms=<int> result=stopped|not_running|killed|failed`
  - `restart`: `op=daemon_restart duration_ms=<int> result=ok|stop_failed|start_failed`
  - The `result` field is a new optional logfmt field; story 5.1's `LOGFMT_OPTIONAL_FIELDS` set needs `result` added. Add it in this story's PR. Update story 5.1's documented optional fields accordingly (or, equivalently, in this story add `result` to the helper and document the addition in `llm/cli/daemon.py`'s docstring).

- **AC-9** **`--json` flag** on all three commands. Emits a single JSON document on success:
  - `start`: `{"action": "start", "running": true, "pid": <int>, "spawned": <bool>}`. `spawned=false` means "was already running."
  - `stop`: `{"action": "stop", "running": false, "was_running": <bool>, "killed": <bool>}`. `killed=true` means SIGKILL had to escalate.
  - `restart`: `{"action": "restart", "running": true, "old_pid": <int>|null, "new_pid": <int>}`.
  - On failure (any non-zero exit), JSON is still emitted with `"running": <current state>` and an `"error": {"code": "<CODE>", "message": "<str>"}` field. Stdout-only; never mixes JSON and Rich.

- **AC-10** **Exit codes.**
  - `0` — success (including idempotent no-ops).
  - `1` — operational failure (timeout, missing binary, child died).
  - `3` — `LLMDaemonUnreachable` propagating from `start`'s post-spawn `health` probe. Should be rare.
  - `2` — Typer usage error.

- **AC-11** **`--help` output discipline.** Each command's help text is one short summary line plus the `--json` flag. Verified live via `python -m llm.cli.daemon start --help` etc.

  ```
  $ chirp daemon start --help
  Usage: chirp daemon start [OPTIONS]

    Spawn the daemon process. No-op if already running.

  Options:
    --json    Emit machine-readable JSON to stdout.
    --help    Show this message and exit.
  ```

  Mirror for `stop` and `restart`. Confirm against `chirp daemon --help` (which lists summaries) before sign-off.

## Implementation tasks

1. **Pick the shutdown mechanism.** Before writing the `stop` command, confirm what CHIRPD-CORE delivers:
   - If a `shutdown` op exists on the wire protocol with a client method `LLMClient.shutdown()`, use it (preferred — surfaces clean shutdown in the daemon's logs, no signal racing).
   - Otherwise use `os.kill(pid, signal.SIGTERM)`. The daemon's signal handler (CHIRPD-CORE) must stop the asyncio loop and exit cleanly. Verify by reading the CHIRPD-CORE story for the signal-handling work.
   - Document which path was chosen in `llm/cli/daemon.py`'s docstring so future maintainers know.

2. **Implement the three commands.** Each is a short function (~30–50 lines). Factor a shared helper `_wait_for_socket(socket_path: Path, *, present: bool, timeout: float) -> bool` that returns True if the socket-state transition occurred within the timeout. Both `start` and `stop` use it (with `present=True` and `present=False` respectively).

3. **Add `result` to the logfmt optional fields.** Append `"result"` to `LOGFMT_OPTIONAL_FIELDS` in `chirpd/logging_setup.py` (set introduced in story 5.1's AC-9). Add a one-line note in story 5.1's documented field table — either via a follow-up edit to 5.1's story file (preferred — keep the source of truth singular) or by extending the docstring in `logging_setup.py` to list `result` as well. **In code**: a single-line addition, no logic changes to the helper.

4. **Implement `--json` output.** Reuse `_should_use_json` from story 5.2. Construct the response dict, dump with `json.dumps(payload, indent=2)`. On failure paths, build the same dict shape with an `error` sub-object.

5. **Handle the partial-restart failure case carefully.** If `stop` succeeded but `start` failed, the daemon is *down*. The user-facing message must say that clearly so they don't think the old daemon is still running. The `--json` output for this case has `"running": false` and `"error": {...}`.

6. **Write the tests.** Extend `tests/llm/test_cli_daemon.py`. Many tests patch `subprocess.Popen` and `LLMClient` methods; use `unittest.mock.patch` consistently. The `_wait_for_socket` helper is straightforward to test by patching `Path.exists` or by writing/removing a real socket file in a `tmp_path`.

7. **Manual smoke tests** (against a real daemon on a dev machine):
   - `chirp daemon stop && chirp daemon stop` — second invocation idempotent.
   - `chirp daemon start && chirp daemon start` — second invocation idempotent.
   - `chirp daemon restart` — works against both running and not-running starting states.
   - Open two terminals: in terminal A, start a long-running `chirp ask`. In terminal B, run `chirp daemon stop`. Verify terminal A's request fails with `MODEL_GENERATION_FAILED` / `daemon_shutdown` (or whatever the LLMClient surfaces); verify terminal B's `stop` returned `0` promptly.
   - `chirp daemon stop --json | jq .running` — emits `false`.

## Dev notes

- **Why `start_new_session=True` on the subprocess spawn.** Detaches the daemon from the parent CLI's process group. If the user Ctrl-C's their shell or closes the terminal, the daemon isn't killed alongside it. (Matches CHIRPD-CORE's lazy-spawn pattern.)
- **Why no drain on `stop`.** Per PRD §Alpha-stage simplifications. The drain state machine was material complexity (`Draining` state, deadline timer, "reject new connections during drain" branch). The alpha trade is: in-flight requests during stop are uncommon and the error is loud. Document, don't engineer.
- **Why escalate to `SIGKILL` after 5 s.** Defensive. A hung daemon (e.g., stuck inside `mlx_lm.load`) wouldn't respond to `SIGTERM`. The kill escalation lets the user actually free the process slot. The "sent SIGKILL" message in stderr signals that something was wrong — not the everyday case.
- **Why a 100 ms sleep between `stop` and `start` in `restart`.** The asyncio server cleanup involves removing the socket file and releasing `flock`. A new `chirpd` process would race to bind to the same socket path. Empirically 100 ms is enough; tunable.
- **Why not auto-restart on `models.toml` edit.** PRD §Out of Scope: hot-reload is explicitly excluded. The `chirp daemon restart` muscle memory is the supported way.
- **Why `--json` on all three even though they have side effects.** Consistency with `chirp daemon status --json` and `chirp models list --json` etc. — every chirp command that emits structured info supports `--json`. The `error` field convention (when present) mirrors a small structured-error pattern that could become the basis for a fuller error-output protocol later.
