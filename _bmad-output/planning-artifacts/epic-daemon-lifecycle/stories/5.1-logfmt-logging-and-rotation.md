# Story 5.1 — Logfmt logging setup, rotation, and redaction discipline

- **Status:** Draft
- **Epic:** [EPIC-DAEMON-LIFECYCLE](../epic.md)
- **Depends on:** EPIC-CHIRPD-CORE (basic logfmt formatter + `chirpd/logging_setup.py` skeleton already exist)
- **Blocks:** 5.2, 5.5 (log file path and format must be locked before `chirp daemon status` and `chirp daemon logs` can reference them)

## User story

As Sam (the troubleshooter), I want every daemon operation to land in a single greppable log file with key=value fields — operation name, model alias, request id, duration, error class — and **never** my prompt text or note content, so I can diagnose what the daemon is doing without exposing what I asked it to do, and so I can keep weeks of logs around without my disk filling up.

## Context

EPIC-CHIRPD-CORE ships a minimal `chirpd/logging_setup.py` that emits logfmt-formatted lines to stderr in dev mode. That's enough for foreground `python -m chirpd` development but is not the production logging surface required by the PRD:

- **No file output yet.** Production logs need to land at `~/Library/Logs/chirp/chirpd.log` so `chirp daemon logs` (story 5.5) and LaunchAgent-spawned daemons (story 5.4) both write to the same place. The LaunchAgent plist's `StandardOutPath` / `StandardErrorPath` (story 5.4) also point at this file as a belt-and-braces capture — if the Python handler fails for any reason, launchd still captures stderr.
- **No rotation yet.** Per NFR-O2, the file must rotate at ~10 MB with one prior generation retained. Without rotation, a long-running daemon eventually fills the disk.
- **No redaction tests yet.** NFR-S5 is a hard constraint. The minimal CHIRPD-CORE formatter has the right shape (key=value) but doesn't enforce the "no user content" rule with test coverage. This story adds the test cases that pin the rule down.
- **No log directory creation.** `~/Library/Logs/chirp/` does not exist on a fresh machine; the rotating file handler crashes if the parent directory is missing. The logging module must create the directory at first use.

The deliverable is a production-ready `chirpd/logging_setup.py`: a single `configure_logging()` entrypoint called once at daemon startup (and once at CLI startup for diagnostic logging) that wires the logfmt formatter, the rotating file handler, the redaction-aware helper functions, and the directory-creation step. The module must remain import-safe (no I/O on import) so unit tests can manipulate the file path before configuration runs.

The architecture lists the required and optional logfmt fields in § Implementation Patterns → Logging Discipline; this story implements them verbatim.

## Acceptance criteria

- **AC-1** `chirpd/logging_setup.py` exposes one public entrypoint `configure_logging(*, log_dir: Path | None = None, level: str = "INFO", to_stderr: bool = False) -> None`. Calling it more than once is idempotent (re-applying handlers replaces the existing ones; no duplicate output). Implements NFR-O1.

- **AC-2** Default log path is `~/Library/Logs/chirp/chirpd.log` (expanding `~` to the current user's home). If `log_dir` is provided, the log lands at `<log_dir>/chirpd.log` instead — used by tests and by `python -m chirpd --log-dir /tmp/...` dev invocations. The parent directory is created with `parents=True, exist_ok=True` if missing; the function does not crash if the directory already exists. Implements FR16.

- **AC-3** File handler is `logging.handlers.RotatingFileHandler` with `maxBytes=10 * 1024 * 1024` (10 MB) and `backupCount=1`. Rotation produces `chirpd.log.1`; no `chirpd.log.2` or beyond is retained. Implements NFR-O2.

- **AC-4** Log format is logfmt — one line per record. Every line emits, in order, **at minimum**:

  ```
  ts=<ISO-8601 UTC with milliseconds, Z suffix> level=<lowercase> component=<dotted> msg=<short>
  ```

  Example: `ts=2026-05-15T14:32:01.234Z level=info component=chirpd msg="health ok"`. Optional fields appear after `msg=` in arbitrary order, but the four required fields lead every line in the order shown. Implements NFR-O1.

- **AC-5** Optional fields (used when present in the `extra=` dict on the logging call) are emitted as `<key>=<value>` after `msg=`. The standard set, documented in the module docstring:

  | Field | When emitted | Example |
  |-------|--------------|---------|
  | `req_id` | Every daemon request handler line | `req_id=r-7c4a91b3de02` |
  | `op` | Every line tied to a specific op | `op=chat` |
  | `model` | When the line concerns a specific model | `model=gemma-4-4b-it-4bit` |
  | `duration_ms` | Op completion lines | `duration_ms=612` |
  | `tokens` | Op completion lines for chat/embed | `tokens=412` |
  | `err_code` | Error lines | `err_code=MODEL_LOAD_FAILED` |
  | `err_type` | Error lines | `err_type=LLMModelLoadFailed` |

- **AC-6** Values containing spaces, `=`, `"`, or `\n` are double-quoted with backslash escaping (`\"` for inner quote, `\\` for backslash, `\n` for newline). Values without those characters are emitted bare. A `logfmt_escape(value: str) -> str` helper performs this consistently and is the only place quoting logic lives. Tested by AC-15.

- **AC-7** Timestamps are produced via `datetime.datetime.now(timezone.utc)` formatted as `%Y-%m-%dT%H:%M:%S.%f` truncated to milliseconds, with a literal `Z` suffix. No local-time variant. Tests assert the `Z` suffix and millisecond precision.

- **AC-8** When `to_stderr=True`, an additional `StreamHandler` writes to `sys.stderr` with the same formatter. Used by `python -m chirpd` foreground dev runs. The rotating file handler is always installed regardless of `to_stderr`. Implements the dev workflow in architecture § Development Workflow Integration.

- **AC-9** **Redaction discipline — log helper API.** The module exposes `def log_op_event(logger, level, msg, *, req_id, op, model=None, duration_ms=None, tokens=None, err_code=None, err_type=None, **extra)` as the **only** sanctioned way to emit op-related log lines from `chirpd/`. The helper passes its keyword arguments into the underlying `logger.log(level, msg, extra=...)` call. Critically:
  - `**extra` accepts only declared metadata keys. The helper raises `ValueError` at runtime if a caller passes a key not in the documented optional-field set (see AC-5).
  - The `msg` argument is bounded to 200 characters; longer messages are truncated with `…`. Prevents accidentally logging a full prompt as the message body.
  - The module docstring explicitly forbids `**extra` containing user prompt text, chat messages, note content, embed input text, or transcript text. Enforced by AC-16's tests.

- **AC-10** **Redaction discipline — direct-logger paths.** When code in `chirpd/` calls `logger.info(...)` / `logger.error(...)` directly (i.e. outside the `log_op_event` helper — used for startup/shutdown lines, lifecycle events, and the like), the formatter's `format()` method strips any record field whose key matches `r"prompt|message[s]?|content|text|note|transcript"` (case-insensitive) **defensively**. If such a field is somehow attached via `extra=`, it is replaced with `<redacted>` and a single warning-level line is emitted with `err_type=RedactionViolation` and the offending key name. Implements NFR-S5 as defense-in-depth.

- **AC-11** **Apple Silicon / macOS-only log directory.** On non-macOS hosts (`sys.platform != "darwin"`), the default log path falls back to `~/.cache/chirp/chirpd.log` (XDG-ish) rather than the macOS-specific `~/Library/Logs/`. This is a developer-ergonomic concession — the daemon itself fails fast on non-Apple-Silicon at startup, but unit tests and CI may run on Linux and need a sane default path. Tests cover both branches.

- **AC-12** Log directory creation is **lazy**: `configure_logging` creates `<log_dir>/` only when called, not at module import. Importing `chirpd.logging_setup` performs zero I/O. Tested by AC-15.

- **AC-13** When the log file cannot be opened (e.g., permission denied on the parent directory), `configure_logging` raises `OSError` with the underlying error chained — it does **not** silently fall back to stderr-only. Callers (daemon `__main__`, CLI startup) decide how to surface this. Prevents silently losing logs.

- **AC-14** Module-level `logger = logging.getLogger("chirpd")` and `logger = logging.getLogger("chirp.llm")` are the two roots the formatter knows about. `configure_logging` attaches handlers to both. Lines from other loggers (e.g. third-party `huggingface_hub`) are passed through but at WARN-or-higher only, to keep the log file focused on chirp activity.

## Implementation tasks

1. **Extend `chirpd/logging_setup.py`.** Replace the stderr-only minimal version from EPIC-CHIRPD-CORE with the full implementation. Module surface:
   - `DEFAULT_LOG_DIR_DARWIN = Path.home() / "Library" / "Logs" / "chirp"`
   - `DEFAULT_LOG_DIR_FALLBACK = Path.home() / ".cache" / "chirp"`
   - `LOGFMT_REQUIRED_FIELDS = ("ts", "level", "component", "msg")`
   - `LOGFMT_OPTIONAL_FIELDS = frozenset({"req_id", "op", "model", "duration_ms", "tokens", "err_code", "err_type"})`
   - `FORBIDDEN_EXTRA_KEY_PATTERN = re.compile(r"prompt|message|content|text|note|transcript", re.IGNORECASE)`
   - `class LogfmtFormatter(logging.Formatter)` — implements `format()` with the field-order and escaping rules; performs defensive redaction per AC-10.
   - `def logfmt_escape(value: object) -> str` — the only place quoting lives.
   - `def configure_logging(...) -> None` — the public entrypoint.
   - `def log_op_event(logger, level, msg, *, req_id, op, model=None, ...) -> None` — the sanctioned op-line emitter; validates kwargs against `LOGFMT_OPTIONAL_FIELDS` and raises `ValueError` on unknown keys.

2. **Wire `configure_logging` into the daemon startup.** In `chirpd/__main__.py`, before any other module imports that might log, call `configure_logging(to_stderr=<true if foreground>)`. The "foreground" check uses `sys.stdout.isatty()` as a proxy. (When LaunchAgent spawns the daemon, stdout is the log file per the plist; `isatty()` is False and stderr-mirroring is skipped — launchd captures stderr directly.)

3. **Add the `RedactionViolation` defensive path.** Inside `LogfmtFormatter.format`, walk `record.__dict__` for keys matching `FORBIDDEN_EXTRA_KEY_PATTERN`. For each match: replace the value with `"<redacted>"`, accumulate the key name. After formatting the original line, if any redaction occurred, write a second line via the same logger at WARNING level with `err_type=RedactionViolation` and `extra={"redacted_keys": ",".join(keys)}`. Use a thread-local flag to prevent recursion (the violation line itself must not trigger another violation line).

4. **Quiet third-party loggers.** Inside `configure_logging`, set `logging.getLogger("huggingface_hub").setLevel(logging.WARNING)` and similar for any other transitively-imported library that's chatty by default (`urllib3` is the usual suspect — handle defensively).

5. **Write the test file.** `tests/chirpd/test_logging_setup.py`. Use `tmp_path` for log directories. Use a fresh `logging.getLogger("chirpd.test." + uuid)` per test to avoid handler bleed between tests. Restore handlers in a fixture teardown.

6. **Document the module.** A short module-level docstring naming the public surface, the redaction rule, and a one-line example of a logged op event. The docstring is the place callers learn the rules; per CLAUDE.md, prefer docstrings to inline comments.

7. **Verify by hand.** Run `python -m chirpd --log-dir /tmp/chirpd-test` in a foreground terminal; issue a `health` op from a second terminal; verify a logfmt line appears both on stderr and in `/tmp/chirpd-test/chirpd.log`. Truncate the log to 1 KB, set `maxBytes=512` in a one-shot Python REPL test, force a rotation, verify `chirpd.log.1` is present.

## Dev notes

- **Why a single `log_op_event` helper rather than calling `logger.info(...)` everywhere.** The helper is the bottleneck where the "no user content" rule lives. Callers can't accidentally pass `messages=<list of chat messages>` because the helper rejects unknown keys. The defensive formatter-side redaction is a backstop for the cases where someone bypasses the helper (third-party logger, future contributor, etc.).
- **Why a forbidden-key regex rather than an allowlist.** An allowlist exists — `LOGFMT_OPTIONAL_FIELDS`. The regex is the formatter's *defensive* layer for direct `logger.info(..., extra={...})` paths that bypass the helper. Defense in depth.
- **Why model alias is safe to log but model "name" is not.** Aliases are user-chosen strings tied to a model identity (e.g. `gemma-4-4b-it-4bit`). They are not user content. Op-level metadata is, by design, all of this kind — operations, identifiers, counts, durations, error classifications. None of those are user prose.
- **Why ms timestamps, not seconds or nanoseconds.** Logfmt convention is human-skim-friendly first, machine-parseable second. Milliseconds align with `duration_ms`; we don't gain anything from microseconds for log tailing.
- **Why the helper is in `chirpd/logging_setup.py` and not a separate `chirpd/log.py`.** One module per concern. The configuration *and* the emitter both live in the logging module; nothing else in `chirpd/` needs to know about logging beyond `from chirpd.logging_setup import log_op_event, logger`.

## Testing

- **Unit:** the cases in AC-15 + AC-16. ~16 tests, all CI-safe (no real macOS paths required — `tmp_path` and platform-patch fixtures cover the surface).
- **Manual:** the one-shot REPL rotation check in implementation task 7. Useful as a smoke test that `RotatingFileHandler` is actually rotating, since the behavior is hard to spot at production volumes.
- **Coverage:** target ≥ 95% on `chirpd/logging_setup.py` (NFR-M1 says 90% on new modules; this one is small and easily testable, so aim higher).

## Handoff to story 5.2 / 5.5

- **Log file path is locked at `~/Library/Logs/chirp/chirpd.log`** (with `.1` for the prior generation). Story 5.5 (`chirp daemon logs`) reads from this exact path. Story 5.4 (LaunchAgent plist) sets `StandardOutPath` and `StandardErrorPath` to this same file.
- **Log format is locked at logfmt with the field order in AC-4.** Story 5.5 does not parse the lines (it just cats / tails them); story 5.2 reads `health` and `model.status` via the op protocol, not by parsing logs. But any future feature that *does* parse logs can rely on logfmt + the documented field set.
- **`log_op_event` is the single emitter for op metadata.** Stories landing later (in any epic) that emit op-level log lines from `chirpd/` must use this helper, not bare `logger.info(...)`.
