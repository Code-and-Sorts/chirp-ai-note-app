# Story 5.6 — Hidden Typer registration in `chirp/cli.py`

- **Status:** Review
- **Epic:** [EPIC-DAEMON-LIFECYCLE](../epic.md)
- **Depends on:** 5.2, 5.3, 5.4, 5.5 (all seven subcommands must be real and tested before they're surfaced behind `chirp daemon ...`)
- **Blocks:** —

## User story

As Sam, I want to be able to type `chirp daemon status` (and the other six daemon subcommands) at my shell and have them just work — but I do **not** want `daemon` cluttering the output of `chirp --help` and confusing new users who don't need it. The command group should be invisible by default and discoverable via `chirp daemon --help` once a user knows it exists.

## Context

This is the final wire-up story. Until this PR lands, the `daemon` subapp built across stories 5.2–5.5 exists as a Typer instance in `llm/cli/daemon.py` but is not connected to the top-level CLI. Tests reach it via `typer.testing.CliRunner` invoking the subapp directly. End users cannot run `chirp daemon status` at the shell.

The PRD specifies (§CLI Tool Specific Requirements): "`chirp daemon` — daemon lifecycle and diagnostics. **Hidden** because happy-path users never need it; surfaced when troubleshooting." `chirp/cli.py` already registers three hidden maintenance commands (`config`, `devices`, `index`) via the same Typer mechanism. This story adds `daemon` to that same hidden tier.

The visible 7-command surface (`record`, `transcribe`, `notes`, `ask`, `search`, `init`, `about`) is **locked by EPIC-WF-ALIGN** and is not touched. Adding `daemon` as a hidden subapp does not affect what shows in `chirp --help`.

This is intentionally a small, contained story — one Typer-registration line in `chirp/cli.py`, plus a few small confirmations (the seven subcommand summaries read well in `chirp daemon --help`, the visible help is unchanged, the existing hidden-command tests still pass).

## Dev notes

- **Why hidden, not visible.** PRD §CLI Tool Specific Requirements is explicit: happy-path users never need this group. The PRD's success criteria include "Daemon is invisible when things work. Users running `record`, `transcribe`, `notes`, `ask`, `search` never need to interact with `chirp daemon` directly." Adding the group to the visible help would invite users to think about the daemon, which is the opposite of the design intent.
- **Why a single subapp registration rather than seven flat hidden commands.** Grouping under `chirp daemon <subcommand>` is the natural shape — they share the diagnostic / lifecycle theme. Flat commands would crowd the hidden tier and create misleading completions like `chirp s<TAB>` returning `search status stop start` together. The subapp keeps them properly namespaced.
- **Why this story is so small.** Most of the work happened in stories 5.2–5.5. This is the wire-up. Keeping it as its own story makes the dependency graph honest (every preceding story is independently demonstrable via direct subapp invocation; this story is what makes them user-reachable).
- **Why no test that "all seven commands are runnable via the top-level dispatch."** Two smoke tests (AC-8 `test_chirp_daemon_status_dispatch` and `test_chirp_daemon_logs_dispatch`) cover the dispatching mechanism. Replicating that across all seven would be redundant — Typer's `add_typer` is a tested library boundary; we don't need to re-validate it for each subcommand.
- **Why `CLAUDE.md` and not `AGENTS.md`.** The "Current CLI Surface" list is in `CLAUDE.md` (per the current file's contents). `AGENTS.md` mentions hidden commands more generally ("Hidden maintenance commands such as `config`, `devices`, and `index` exist...") — that line could be updated too if the maintainer prefers to keep both in sync, but per the project convention `AGENTS.md` is the canonical guide and `CLAUDE.md` mirrors a thin slice. Add `daemon` to wherever the surface list lives; leave the prose intact.
