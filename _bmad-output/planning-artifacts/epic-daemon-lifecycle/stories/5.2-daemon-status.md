## User story

As Sam, when `chirp ask` feels slow or weird, I want to run `chirp daemon status` and immediately see whether the daemon is up, what version it is, which models are loaded, how much RAM each is using, and how much idle time each has left before unload — without reading source code or grepping logs — so I can decide whether to wait, restart the daemon, or file an issue. And when I want to plug that information into a script or a dotfile dashboard, I want `--json` to emit the same data in a machine-parseable form.

## Context

This is the diagnostic surface NFR-M5 calls for. Per the PRD's Sam journey: "Monday morning, the LaunchAgent (which he enabled with `chirp daemon enable`) is running again — `chirp daemon status` shows: 'Running, uptime 4m 12s, no model loaded, idle 4m.' His first `ask` takes the cold-start pause, then runs normally." That exact information shape is what this story implements.

The command does two things:

1. **Issue `health` and `model.status` ops via `llm.client.LLMClient`.** The client (delivered by EPIC-CHIRPD-CORE) handles socket discovery, lazy-spawn, and one-shot retry on version mismatch. If the daemon is genuinely down and lazy-spawn fails, the client raises `LLMDaemonUnreachable` — this command catches that and renders a "daemon not running" message instead of propagating an exit-code-3 traceback.
2. **Render the result.** On a TTY, a compact Rich table. On `--json` or in a non-TTY, a single JSON document on stdout. Diagnostic / progress lines go to stderr (e.g., "daemon not running — lazy-spawning..." if the client spawns one during the call).

The command intentionally has no side effects beyond the ops it issues. It does not start, stop, or modify daemon state. (Side note: by issuing `health`, it may cause a lazy-spawn — which is a one-time side effect users expect from any chirp command that needs the daemon. There's no `--no-spawn` flag in MVP.)

This story creates the file `llm/cli/daemon.py` for the first time. Story 5.3 / 5.4 / 5.5 extend it with sibling commands. The Typer subapp registration in `chirp/cli.py` is deferred to story 5.6 — for the duration of this story's PR, the command is callable only via `python -m llm.cli.daemon status` for testing, or by running the subapp's Typer instance directly in unit tests.

## Acceptance criteria

- **AC-1** `llm/cli/daemon.py` exists and defines `daemon_app = typer.Typer(help="Daemon lifecycle and diagnostics", no_args_is_help=True)`. Implements the Typer subapp pattern used elsewhere in the codebase. (Implements the structural anchor for FR39–FR45.)

- **AC-2** `daemon_app` defines exactly one command in this story: `status`. The function signature is `def status(json_output: bool = typer.Option(False, "--json", help="Emit machine-readable JSON to stdout."))`. Calls `llm.client.LLMClient()` (default socket path), issues `health`, then issues `model.status`, then renders the combined result. Implements FR39.

- **AC-3** **Rich-table output (TTY, no `--json`).** Renders a Rich table with the following rows in order. Empty / null values display as `—`.

  ```
  daemon         running                   (red "stopped" if not running)
  pid            <int>
  uptime         <h>h <m>m <s>s            (formatted compactly; "12m 3s" if under 1h)
  version        <str>                     (the daemon's reported version)
  total RSS      <human-readable bytes>    ("142.3 MB")
  last request   <relative time>           ("2m 14s ago"; "—" if never)
  ```

  Followed by a second table titled "Loaded models" (omitted if zero models loaded):

  ```
  alias                              role     RSS         last used        idle in
  gemma-4-4b-it-4bit           chat     4.1 GB      2m 14s ago       2m 46s
  bge-small-en-v1.5                  embed    180 MB      4m 02s ago       pinned
  ```

  Embed-role models display `pinned` in the "idle in" column (since they are never unloaded — FR6). Chat models display the live countdown from the `idle_countdown_seconds` field.

- **AC-4** **JSON output (`--json` or non-TTY).** Emits a single JSON document to stdout, matching the schema locked in the epic's §3 decision 10:

  ```json
  {
    "running": true,
    "pid": 12345,
    "uptime_seconds": 723.42,
    "version": "0.7.0",
    "loaded_models": [
      {
        "alias": "gemma-4-4b-it-4bit",
        "role": "chat",
        "rss_bytes": 4408481792,
        "last_used": "2026-05-15T14:32:01.234Z",
        "idle_countdown_seconds": 166.8
      }
    ],
    "last_request_at": "2026-05-15T14:32:01.234Z",
    "total_rss_bytes": 4558481792
  }
  ```

  - In `--json` mode, **no Rich rendering** appears on stdout (NFR-A1 / PRD §Output Formats).
  - Diagnostic notices ("daemon not running — attempting lazy-spawn...") go to stderr in plain text.
  - The JSON document is the only thing on stdout — pipeable into `jq` without preamble.
  - Implements FR31, NFR-O3.

- **AC-5** **Daemon-not-running rendering.** When `LLMClient` raises `LLMDaemonUnreachable` (after the lazy-spawn-and-retry has exhausted), the command renders:
  - TTY: a single-row table with `daemon  stopped` (red), followed by a line: `the daemon is not running and could not be spawned. try: chirp daemon start` — printed to stderr.
  - JSON: `{"running": false, "pid": null, "uptime_seconds": null, "version": null, "loaded_models": [], "last_request_at": null, "total_rss_bytes": null}` on stdout.
  - Exit code: `3` (daemon unreachable, per PRD §Scripting Support). The Typer outer wrapper converts the caught `LLMDaemonUnreachable` to exit 3.

- **AC-6** **Lazy-spawn was needed.** If the daemon was not running at the start of the command but lazy-spawn succeeded mid-call, render the table normally on TTY but print one line to stderr first: `daemon was not running — started a new instance.` (Rationale: Sam needs to know that a fresh process just landed, because uptime will be near-zero and "loaded models" will be empty — these are not bugs, they reflect the just-spawned state.) Suppress this notice in `--json` mode (the `uptime_seconds` near 0 is the machine-readable signal).

- **AC-7** **Version mismatch was resolved.** If the client's one-shot retry on `version_mismatch` succeeded (the daemon respawned with a matching version), render the table normally but print one line to stderr first: `daemon was restarted to match this CLI's version.` Suppress in `--json` mode. (The `LLMClient` returns success to the caller; the caller can tell a respawn happened by checking a `daemon_respawned: bool` field on the client's last-call metadata — exposed by CHIRPD-CORE; story 5.2 wraps that.)

- **AC-8** **Output-rendering helpers** are factored into two functions for testability:
  - `render_status_table(payload: dict, console: Console) -> None` — TTY path.
  - `render_status_json(payload: dict, stream: IO[str]) -> None` — JSON path. Uses `json.dumps(payload, indent=2)` with a trailing newline.
  Both functions accept a plain dict (the merged `health` + `model.status` result), making them unit-testable without a live daemon.

- **AC-9** **Human-readable formatters.**
  - `format_bytes(n: int) -> str` — emits `"142.3 MB"`, `"4.1 GB"`, `"180 MB"` style; uses 1024-based units; one decimal place; `"<1 KB"` for sub-kilobyte values. Used for both RSS columns.
  - `format_uptime(seconds: float) -> str` — emits `"4m 12s"` (under 1 hour), `"2h 14m 03s"` (under 1 day), `"5d 3h 21m"` (1+ days). Used for the `uptime` row.
  - `format_relative_time(iso_timestamp: str | None, now: datetime) -> str` — emits `"2m 14s ago"`, `"—"` for None, `"just now"` if < 1 second. Used for `last used` and `last request`.
  - All three are pure functions in `llm/cli/daemon.py` (private — leading underscore). Tested via parameterized cases.

- **AC-10** **Exit codes.**
  - `0` — daemon reachable, status rendered.
  - `3` — daemon unreachable (`LLMDaemonUnreachable`).
  - `1` — any other `LLMError` subclass (e.g., `LLMProtocolError` on a malformed `model.status` response). User-facing stderr message includes the exception's `code` attribute when present.
  - `2` — Typer usage error (default behavior).
  - All exit codes traced from PRD §Scripting Support. The Typer outer wrapper handles the conversion; this command does not call `sys.exit(N)` directly.

- **AC-11** **Diagnostic logging.** Issuing the command emits one logfmt line via `chirpd.logging_setup.log_op_event` (from story 5.1) to the **CLI-side** log (not the daemon's log — that's emitted by the daemon when it handles the `health` / `model.status` ops). The CLI line is at `level=info`, `component=chirp.llm.cli.daemon`, `op=status`, with `duration_ms` measuring the round-trip and `daemon_running` true/false. **No prompt or model content is touched** — the call payload is metadata only, so the NFR-S5 redaction rules are trivially satisfied here.

## Dev notes

- **Why issue `health` and `model.status` separately rather than one combined op.** The two ops exist for different reasons — `health` is the `chirp init` doctor probe (lightweight, no model state), and `model.status` is the model-introspection op. Combining them would couple two boundaries. The CLI calls both because it shows both kinds of info, but that's the CLI's concern, not the protocol's.
- **Why not auto-respawn on `LLMDaemonUnreachable`.** The client already attempts lazy-spawn internally (per `chirp.llm` contract — FR19). If that fails, the daemon is genuinely broken (bad binary, permissions, etc.) and the right answer is to surface the problem to the user, not to retry. `chirp daemon start` is the explicit "try harder" command.
- **Why format the table on TTY but JSON when piped.** Matches PRD §Output Formats and existing chirp conventions. `chirp daemon status | jq` should work without `--json`; the non-TTY auto-switch covers this. The `--json` flag is for forcing JSON in interactive shells (e.g., for testing).
- **Why `last_request_at` is null when never used.** A freshly-spawned daemon hasn't seen requests yet. Distinguishing "never" from "long ago" matters for diagnosing "did my CLI even reach the daemon?". The null serializes cleanly in JSON and renders as `—` in the table.
- **Why pin embed models' `idle_countdown_seconds` to `null`, not infinity.** Embed models are pinned indefinitely (FR6). `null` is the honest representation; rendering `pinned` in the table is a UX choice tied to that semantic. JSON consumers should special-case `null` for embed models.

## Verification (as-built)

The story was drafted against an assumed CHIRPD-CORE contract that the merged code only partially provides. Trivial naming/location mismatches were absorbed in `_collect_status`; three substantive gaps were resolved per the maintainer's **hybrid** decision (fill the cheap upstream gaps, defer the expensive one):

- **Field reconciliation (no behavior change).** `model.status` returns `models` (not `loaded_models`), `daemon_version` (not `version`), and `rss_bytes` (daemon-total, mapped to `total_rss_bytes`); `pid` and total RSS live on `model.status`, not `health` as the task-2 pseudocode assumed. `running` is inferred by the CLI (true on success, false on `LLMDaemonUnreachable`). `_collect_status` maps real → locked schema and `_normalize_model` reshapes each model to the AC-4 key set.
- **`last_request_at` (AC-3/4/5) — filled upstream.** The daemon tracked no last-request time. Added `DaemonState.mark_request()` (stamps `datetime.now(UTC)`), called from the chat and embed dispatcher handlers only (not `health`/`model.status`, which would make status always report itself), and surfaced as `last_request_at` in `state.status()`.
- **Lazy-spawn / respawn notices (AC-6/7) — filled upstream.** `LLMClient` exposed no call metadata. Added latched `daemon_lazy_spawned` (set in `_spawn_daemon`) and `daemon_respawned` (set on both version-mismatch retry paths). The CLI checks `daemon_respawned` first (a respawn also lazy-spawns the replacement), so AC-7's message wins over AC-6's when both are set.
- **Per-model `rss_bytes` (AC-3/4) — DEFERRED (follow-up).** The daemon reports only total process RSS; per-model RSS is genuinely hard for MLX and out of scope for this epic. `_normalize_model` emits `rss_bytes: null`; the table renders `—`. **Follow-up to file against CHIRPD-CORE:** add per-model RSS accounting, then the column/JSON field light up with no CLI change. AC-3/4's "non-empty RSS value" is satisfied today only by the `total RSS` row.
- **AC-11 logging.** `log_op_event`'s strict NFR-S5 allowlist (from 5.1) rejects a `daemon_running` extra, so reachability rides in the (content-free) message text (`"daemon status: running|stopped"`) instead of a field. `op="status"` and `duration_ms` are emitted as fields. `configure_logging` is best-effort (a diagnostic command must not die because it can't open its own log file).
- **AC-13 help.** Verified via `CliRunner`; summary mentions "loaded models" and "idle"; `--json` listed. Usage line shows the subapp prog name until story 5.6 registers it under `chirp`.
