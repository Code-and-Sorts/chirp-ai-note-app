# Story 5.5 — `chirp daemon logs` with `-f` / `--follow` and `-n`

- **Status:** Draft
- **Epic:** [EPIC-DAEMON-LIFECYCLE](../epic.md)
- **Depends on:** 5.1 (log file path and rotation behavior locked at `~/Library/Logs/chirp/chirpd.log` with `.1` for the prior generation)
- **Blocks:** 5.6 (Typer registration)

## User story

As Sam, when `chirp ask` fails with "Model failed to load: unsupported architecture. Run `chirp daemon logs` for details," I want `chirp daemon logs` to dump the log file the way `cat` would, `chirp daemon logs -n 200` to show me just the last 200 lines, and `chirp daemon logs -f` to follow new output in real time — including across rotation boundaries when the log rolls over from `chirpd.log` to `chirpd.log.1`. I should not have to learn `tail -f` or know where the log lives.

## Context

This is the diagnostic-tail UX described in PRD §User Journeys (Sam) and FR45. The implementation is genuinely close to `tail`'s `-F` (follow-by-name) mode, with a couple of chirp-specific niceties:

1. **Default behavior with no flags** = `cat`. Print the whole file to stdout, exit 0. (For most users, the file is small enough that this is fine; for the rare case where it's grown to ~10 MB, the user can pipe to `less` themselves.)
2. **`-n <N>`** prints the last N lines and exits. Behaves like `tail -n N`.
3. **`-f` / `--follow`** prints from a starting offset and then follows new output. Re-opens by name across rotation boundaries (per AGENTS.md / the architecture's `RotatingFileHandler` setup) — this is `tail -F` semantics, not naive `tail -f` semantics.
4. **`-f` combined with `-n N`** prints the last N lines first, then follows. (Mirrors `tail -n N -f`, the most common interactive pattern.)
5. **Ctrl-C exits cleanly** with exit code 0 (not 130). The user requesting an interactive follow doesn't want a Python KeyboardInterrupt traceback.

The architecture's rotation policy (story 5.1's `RotatingFileHandler` at 10 MB, 1 backup) means the worst case during follow is: the file rotates from `chirpd.log` to `chirpd.log.1`, and a fresh `chirpd.log` starts at offset 0. A naive `tail -f` holding the original file descriptor would silently fall off the end of the old (now-`.1`) file. The follow loop must `stat` the file periodically by name and re-open when the inode changes.

The PRD also locks logfmt as the on-disk format (NFR-O1, OQ3) — `chirp daemon logs` does not parse this; it cats/tails it. JSON output is deferred (PRD §Open Questions, §Alpha simplifications). The command's output is whatever's in the log file, line for line.

This command is intentionally simple. It does **not** filter by `req_id`, color-code by `level`, or summarize — those are Growth-tier ideas (PRD §Product Scope → Growth Features → "telemetry surface"). The MVP value is "the user can see the logs without leaving chirp."

## Acceptance criteria

- **AC-1** `llm/cli/daemon.py` adds one new command on `daemon_app`: `logs`. Signature:

  ```python
  @daemon_app.command()
  def logs(
      follow: bool = typer.Option(False, "-f", "--follow", help="Follow the log file for new output. Re-opens across rotation."),
      lines: int = typer.Option(None, "-n", "--lines", help="Show only the last N lines (or last N before following with -f)."),
  ) -> None:
      ...
  ```

  Implements FR45.

- **AC-2** **Log file path resolution.** Resolves the log path via `chirpd.logging_setup.resolve_log_path()` (a new helper added in this story, or inline if simpler) — returns `~/Library/Logs/chirp/chirpd.log` on Darwin and `~/.cache/chirp/chirpd.log` elsewhere (matches story 5.1's AC-11 fallback). The resolution function is the single source of truth shared between `chirpd/logging_setup.py` (story 5.1, writer side) and this command (reader side); duplicating the path string in two modules would invite drift.

- **AC-3** **Default behavior (no flags).** If the log file exists, opens it, reads to EOF, writes to stdout, closes, exits 0. Streaming-read (line-by-line) — does not load the whole file into memory. Implements FR45's default mode.

- **AC-4** **`-n N` behavior.** Reads the last N lines from the file and writes them to stdout, then exits 0. Implementation uses a small bounded-deque scan (reads the whole file but keeps only the last N lines in memory via `collections.deque(maxlen=N)`). Acceptable for ~10 MB files; do not implement a reverse-byte-seek `tail` algorithm unless profiling shows it matters (it won't).

- **AC-5** **`-f` behavior (without `-n`).** Opens the file at the **end** (offset = file size at open time), then loops:
  1. Sleep 200 ms.
  2. Re-stat the file by name. If the file's inode differs from the one we hold (i.e. rotation happened), close the current handle and open the new `chirpd.log`. Reset offset to 0 (the new file is fresh).
  3. If the current handle's file size has grown, read from the current offset to EOF, write to stdout, update offset.
  4. If the current handle's file size has shrunk (also rotation, less common — should be caught by inode check), close and re-open.
  5. Continue until `KeyboardInterrupt` (Ctrl-C).

  Implements FR45's `-f` mode. Matches `tail -F` (capital F) semantics.

- **AC-6** **`-f` with `-n N`.** First prints the last N lines (as `-n` alone would), then enters the follow loop **starting from current EOF** (not from where the deque left off — new lines appended after the dump are the follow target). The transition between dump and follow is seamless from the user's perspective.

- **AC-7** **Ctrl-C exits 0, not 130.** Wrap the follow loop in `try/except KeyboardInterrupt: pass` and return normally. The user's interactive `^C` is not an error condition. (Standard chirp convention — matches `chirp ask` interactive chat behavior.)

- **AC-8** **Missing log file.** If the log file does not exist:
  - Without `-f`: print `no log file at <resolved-path> yet. logs are written when the daemon runs.` to stderr. Exit 0.
  - With `-f`: enter a polling loop waiting for the file to appear (1 s interval). Print `waiting for log file at <resolved-path>...` to stderr once. On Ctrl-C, exit 0. Once the file appears, enter the normal follow loop.

  Rationale: a user running `chirp daemon logs -f` immediately after `pip install chirp` (before any chirp command has spawned the daemon) shouldn't see an error — they want to watch the first log line appear.

- **AC-9** **Stdout discipline.** Lines from the log are written **byte-for-byte** to stdout, including their trailing newline. No reformatting, no coloring, no Rich rendering. `chirp daemon logs | grep err_code` works as expected. `chirp daemon logs -f | awk -F= '...'` works as expected.

- **AC-10** **No `--json` flag.** The log file is logfmt, not JSON. A `--json` flag would imply translation, which is deferred to a Growth-tier story per PRD OQ3 resolution. The `--help` text does not mention JSON.

- **AC-11** **Rotation handling — the load-bearing test.** A test in `tests/llm/test_cli_daemon.py` (or a dedicated `tests/llm/test_cli_daemon_logs.py` to keep the file manageable) exercises the inode-change path:

  1. Create a temp file at the resolved log path with three lines.
  2. Start the follow loop in a background thread, redirecting stdout to a `StringIO`.
  3. Wait until the loop's "initial-EOF-seek" phase has completed (the StringIO is empty).
  4. Append a new line to the file. Wait for the loop to pick it up (StringIO contains the new line).
  5. **Rotate**: rename the file to `chirpd.log.1`, create a fresh `chirpd.log` with a new first line.
  6. Wait for the loop to detect the inode change and start reading from the new file. Assert the new line eventually shows up in StringIO.
  7. Send a sentinel to stop the loop; join the thread; assert no exceptions.

  This test pins the rotation-resilience contract in code.

- **AC-12** **Polling cadence is configurable for tests.** The 200 ms sleep in the follow loop and the 1 s sleep in the "waiting for log file" loop are read from module-level constants `_FOLLOW_POLL_INTERVAL_SECONDS = 0.2` and `_WAIT_FILE_POLL_INTERVAL_SECONDS = 1.0`. Tests can monkeypatch these to 0.01 to keep the test suite fast.

- **AC-13** **Diagnostic logging.** Emits one logfmt line via `log_op_event` on **command start** (not on exit — the user may run `-f` indefinitely):
  - `op=daemon_logs duration_ms=0 result=cat|tail|follow|missing` (`duration_ms=0` because the log line is emitted at command start, before the operation completes — this is acceptable for command-start logging).
  - Optional: emit a second line on graceful exit (Ctrl-C from `-f`) with `duration_ms` measuring the actual follow duration. Skipped if non-essential — first-line-on-start is the meaningful audit event.

- **AC-14** **Exit codes.**
  - `0` — success, including the missing-file case (which is "informational," not an error).
  - `2` — Typer usage error (negative `-n`, etc.). Typer handles this automatically.
  - `1` — IOError reading the log file (permission denied, disk error). Rare; surface with `couldn't read log file: <error>` to stderr.

- **AC-15** **`--help` text:**

  ```
  $ chirp daemon logs --help
  Usage: chirp daemon logs [OPTIONS]

    Print the daemon log file. Tail with -f; show last N with -n.

  Options:
    -f, --follow      Follow the log file for new output. Re-opens across rotation.
    -n, --lines N     Show only the last N lines (or last N before following with -f).
    --help            Show this message and exit.
  ```

  Verified live before sign-off.

- **AC-16** **Unit tests** in `tests/llm/test_cli_daemon.py` (or split out — see AC-11):
  - `test_logs_default_cats_full_file` — write 5 lines; run `logs`; assert stdout matches verbatim; exit 0.
  - `test_logs_with_n_shows_last_n_lines` — write 100 lines; run `logs -n 10`; assert stdout has exactly the last 10 lines; exit 0.
  - `test_logs_with_n_larger_than_file_shows_all` — write 3 lines; run `logs -n 100`; assert stdout has all 3 lines; exit 0.
  - `test_logs_missing_file_default_prints_notice` — no file; run `logs`; assert stderr contains `"no log file"` and the resolved path; exit 0.
  - `test_logs_missing_file_with_follow_waits` — no file; run `logs -f` in a thread; create the file with a line after 50 ms; assert stdout eventually shows the line; cancel via Ctrl-C-equivalent (set a stop event); exit 0.
  - `test_logs_follow_picks_up_appended_lines` — pre-create file with 1 line; start `logs -f` in a thread; append a second line; assert stdout shows the second line within 1 s; stop the thread.
  - `test_logs_follow_with_n_dumps_then_follows` — pre-create file with 5 lines; start `logs -f -n 3` in a thread; assert stdout starts with the last 3 lines; append a 6th line; assert stdout eventually contains it.

## Implementation tasks

1. **Add `resolve_log_path()` to `chirpd/logging_setup.py`** (or place it in `llm/cli/daemon.py` if cleaner — coordinate with story 5.1's surface). Returns the `Path` to `chirpd.log` per the platform-aware rules in story 5.1's AC-2 and AC-11. Replace duplicated path constants in both writer (story 5.1) and reader (this story) with this helper.

2. **Implement `logs` in `llm/cli/daemon.py`.** Branch on the four cases:
   - No flags → `_cat_log_file(path)`.
   - `-n N` only → `_tail_last_n_lines(path, n)` then print.
   - `-f` only → `_follow_log_file(path, start_at_end=True)`.
   - `-n N -f` → `_tail_last_n_lines(path, n)`, then `_follow_log_file(path, start_at_end=True)` (don't re-read the dumped lines).

3. **Implement `_follow_log_file(path, start_at_end)`.** The follow loop. Pseudocode:

   ```python
   while not path.exists():
       print(f"waiting for log file at {path}...", file=sys.stderr)
       time.sleep(_WAIT_FILE_POLL_INTERVAL_SECONDS)
       # if KeyboardInterrupt, return

   fh = path.open("r", encoding="utf-8", errors="replace")
   inode = path.stat().st_ino
   if start_at_end:
       fh.seek(0, os.SEEK_END)

   try:
       while True:
           line = fh.readline()
           if line:
               sys.stdout.write(line)
               sys.stdout.flush()
               continue
           # No new data — sleep and check for rotation
           time.sleep(_FOLLOW_POLL_INTERVAL_SECONDS)
           try:
               new_inode = path.stat().st_ino
           except FileNotFoundError:
               # File temporarily gone during rotation; keep polling
               continue
           if new_inode != inode:
               fh.close()
               fh = path.open("r", encoding="utf-8", errors="replace")
               inode = new_inode
               # Don't seek to end on the new file — read from start
   except KeyboardInterrupt:
       pass
   finally:
       fh.close()
   ```

   Notes:
   - `errors="replace"` is defensive against weird bytes that might end up in a log file (shouldn't happen with logfmt, but cheap insurance).
   - The "wait for file" outer loop covers the AC-8 case.

4. **Implement `_tail_last_n_lines(path, n)`.** `collections.deque` with `maxlen=n`; iterate the file once; print the deque. Returns nothing — caller prints.

5. **Implement `_cat_log_file(path)`.** `shutil.copyfileobj(fh, sys.stdout)` is simplest, but we want a final flush to avoid block-buffering on pipes. A line-by-line `for line in fh: sys.stdout.write(line)` loop with a trailing `sys.stdout.flush()` is fine.

6. **Wire diagnostic logging.** One `log_op_event` call at the top of the function with the appropriate `result` value.

7. **Write the tests.** The rotation test (AC-11) is the most intricate; use `threading.Thread` to run the follow loop, communicate via a shared `StringIO` and a `threading.Event` for stop signals. Monkeypatch `sys.stdout` to the StringIO for the duration of the test. Use the `_FOLLOW_POLL_INTERVAL_SECONDS = 0.01` override to keep tests fast.

8. **Manual smoke tests.**
   - With the daemon running, run `chirp daemon logs` — assert reasonable output.
   - Run `chirp daemon logs -f` in one terminal; in another, run `chirp ask "hi"`. Verify the chat-op line appears.
   - Force a rotation: append 11 MB of bogus content to the log file (`yes "ts=2026-05-15T... line" | head -c 11000000 >> ~/Library/Logs/chirp/chirpd.log`). Wait for the daemon to log something — the rotation should trigger on the next log line. Verify `chirpd.log.1` appears. Run `chirp daemon logs -f` and verify it tracks correctly across the rotation. (This test pins the AC-11 contract in real use.)
   - Run `chirp daemon logs | grep err_code` — verify it works (no exception, no Rich preamble polluting stdout).

## Dev notes

- **Why a Python-side tail loop instead of shelling out to `tail -F`.** Portability and testability. `tail -F` exists on macOS but the behavior across BSDs vs GNU tail diverges (`-F` is BSD; `--follow=name --retry` is the GNU equivalent). Our user is on macOS, so `tail -F` would work — but unit-testing it requires real `subprocess` + real `tail`, which is fiddly in CI. A Python implementation is ~40 lines, testable, and gives us control over the inode-change detection.
- **Why poll instead of using `kqueue`/`fsevents`.** Polling at 200 ms is plenty responsive for log-tailing UX. macOS-specific event APIs would tighten the latency but add platform-specific code and require careful resource cleanup. Polling is the right cost/value trade for the alpha.
- **Why no log filtering, coloring, or pretty-printing in MVP.** PRD §Out of Scope and §Product Scope → Growth: telemetry/diagnostics enrichment is post-MVP. The current command is "show me what's in the file." Adding filters, level highlighting, or req_id grouping is appealing but pulls UX surface into a hidden command (the user-facing tier is `record`/`transcribe`/`notes`/`ask`/`search`/`init`/`about`; investing in `daemon logs` styling is sleeve-rolling no user has asked for).
- **Why a separate `resolve_log_path()` rather than a constant.** The path depends on `sys.platform` (per story 5.1 AC-11). A function is the right shape; constants in modules that get imported on non-Darwin would either pick the wrong path or require duplicating the branch logic.
- **Why `errors="replace"` on file open.** A logfmt line could in theory contain a non-UTF8 byte sequence (e.g., if `logfmt_escape` failed on some pathological input). Better to render `?` than crash mid-tail.
- **Why no rate-limiting in the follow loop.** Log volume is bounded by daemon activity. The daemon emits at most a few lines per chat op. There's no scenario where the follow loop is firehose-throttling stdout. If that ever changes, revisit.
- **Why we read the post-rotation file from offset 0 rather than from the end.** After a rotation, the new `chirpd.log` is fresh (zero or near-zero bytes). Reading from offset 0 captures whatever's been written so far. Seeking to end would miss the first few lines written immediately after rotation — exactly the lines the user often cares about.

## Testing

- **Unit:** ~11 cases per AC-16. The rotation test (AC-11) is the load-bearing one.
- **Manual:** the four smoke tests in implementation task 8. The forced-rotation test exercises the same code path as AC-11 but on a real macOS file system; useful for catching inode-allocation oddities (e.g., APFS clone tricks) that a `tmp_path` might not exhibit.
- **Coverage:** target ≥ 90% on the new command body. The "waiting for file" outer loop is the trickiest branch; the AC-16 `test_logs_missing_file_with_follow_waits` test covers it.
